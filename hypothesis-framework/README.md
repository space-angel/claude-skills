# hypothesis-framework

가설을 대신 쓰지 않고, 질문으로 빈 곳을 드러내 사용자가 직접 채우게 하는 스킬입니다.

[SKILL.md](SKILL.md) · [설치](#설치) · 함께 쓰는 스킬: [po-doc-writing](../po-doc-writing/)

## 구성

hypothesis-framework는 네 개의 게이트를 차례로 지난 뒤 결과물 두 개를 냅니다. 게이트마다 끝에서 멈추고 답을 기다립니다.

0. **분류** — 문제·솔루션·성장·가치 가설 중 무엇인지 정합니다. 반증 조건을 말할 수 없으면 가설이 아니라 할 일 목록으로 봅니다.
1. **사실과 추측 나누기** — 사용자 발화를 관찰된 사실, 추측, 미확보로 나눕니다. 관찰이 하나도 없으면 가설 대신 관찰 계획을 세웁니다.
2. **근거 심문** — 5 Why, 반례, 근거 출처 등급(강함·중간·약함·근거 아님), 목표 수치의 출처를 확인합니다.
3. **검증 가능성** — 단일 변수, 측정 가능성, 반증 조건, 검증 기간을 확인합니다.
4. **두 결과물** — 구조화된 가설 표와 취약점 리포트를 나란히 냅니다. 리포트에는 가장 약한 고리, 근거 등급, 실험 전 확보할 것, 대안 가설이 들어갑니다.

## 모드

### 문제 가설

원인이 아직 특정되지 않았을 때 씁니다. 해결책부터 들고 오면 "그 해결책은 어떤 문제를 겨냥한 건가요?"로 한 번 되짚고, 근거가 없으면 문제 가설부터 다시 세웁니다.

### 솔루션 가설

원인을 특정했고 해결책이 통할지 볼 때 씁니다. 바꾸는 변수가 둘 이상이면 묶을지 나눌지를 선택지로 넘깁니다.

### 성장 가설

특정 전략이 매출·유입·리텐션(재방문) 같은 비즈니스 지표에 미칠 영향을 볼 때 씁니다. 목표 수치의 출처를 반드시 묻습니다.

### 가치 가설

지불 의사나 핵심 가치 자체를 검증할 때 씁니다. 유형이 분명하지 않으면 추측하지 않고 선택지로 묻습니다.

## 상황별 사용

### 해결책부터 떠올랐을 때

"결제 방법을 인기순으로 재정렬하려고요"처럼 바꿀 것은 정했는데 그게 겨냥한 문제를 아직 말하지 못하는 상황입니다.

사용할 모드: 문제 가설로 되짚은 뒤 솔루션 가설

### 지표가 낮은데 이유를 모를 때

전환율이나 이탈률이 기대보다 나쁜데 원인을 특정하지 못한 상황입니다.

사용할 모드: 문제 가설

### A/B 테스트를 설계하기 전

원인은 특정했고, 무엇을 바꿔 어떤 결과를 볼지 실험 전에 정리하는 상황입니다.

사용할 모드: 솔루션 가설

### 목표 수치를 걸고 전략을 제안할 때

매출·유입·리텐션 같은 지표를 얼마나 움직일지 말해야 하는 상황입니다.

사용할 모드: 성장 가설

### 세운 가설을 기획서로 옮길 때

가설 표와 취약점 리포트가 나왔고, 이를 팀이 읽을 검증형 PRD로 넘기는 상황입니다.

함께 쓰는 스킬: [po-doc-writing](../po-doc-writing/)

## 가이드라인

### 모르는 값은 공백으로 남깁니다

친절하게 채워 주는 것이 가장 해로운 실패입니다. 지어낸 근거와 수치는 사용자가 데이터로 오해한 채 실험 설계와 개발 투입까지 따라갑니다. 대화를 몇 번 더 하는 비용이 그보다 작습니다. 모르는 값은 `[미확보: 현재 결제 완료율]`처럼 남깁니다.

### 갈림길은 선택지로, 근거는 자유 서술로 받습니다

질문 공세에 지치면 사용자는 "그냥 알아서 써 줘"로 돌아섭니다. 그래서 답이 유형화되는 갈림길은 `AskUserQuestion`(선택지 질문 도구)으로 클릭 한 번에 넘깁니다. 가설 유형, 근거 출처 등급, 변수를 나눌지 묶을지는 선택지로 묻습니다. 문제 서술, 그 근거가 왜 결론을 지지하는지, 무엇을 어떻게 바꿀지는 자유 서술로 받습니다.

### 원인 후보는 객관식으로 주지 않습니다

"① 옵션 과다 ② 정보 부족" 같은 선택지는 확증 편향을 심습니다. 원인은 사용자가 관찰에서 끌어내야 합니다.

### 급해도 미확보 표시와 취약점 리포트는 빼지 않습니다

사용자가 "빨리 초안만 줘"라고 하면 게이트를 합칩니다. 미확보 표시와 취약점 리포트는 생략하지 않습니다.

| 지양 | 권장 |
|---|---|
| 바로 솔루션 가설을 완성한다 | "그 해결책은 어떤 문제를 겨냥한 건가요? 그게 원인이라는 건 뭘 보고 판단하셨어요?"부터 묻는다 |
| 근거 칸을 "옵션이 많으면 이탈한다"로 채운다 | 발화를 관찰된 사실 / 추측 / 미확보로 나눠 되돌려 준다 |
| 목표를 "결제 완료율 15% 상승"으로 지어 넣는다 | "15%는 어디서 나온 숫자인가요?"를 묻고, 답이 없으면 `[미확보: 목표 수치 산출 근거]`로 남긴다 |
| 순서 재정렬과 혜택 문구를 한 가설에 묶는다 | 묶을지 나눌지 트레이드오프를 선택지로 넘긴다 |
| 완성된 가설 한 장으로 끝낸다 | 가설 표 옆에 취약점 리포트를 함께 낸다 |

표의 예는 "결제 방법을 인기순으로 재정렬하려고요. 가설로 만들어 줘."라는 가상의 요청입니다.

## hypothesis-framework vs po-doc-writing

| | hypothesis-framework | po-doc-writing |
|---|---|---|
| 하는 일 | 질문으로 가설의 빈 곳을 드러낸다 | 정해진 내용을 팀이 읽을 문서로 쓴다 |
| 가설을 대신 쓰는가 | 쓰지 않는다. 사용자가 채운다 | 이미 선 가설을 검증형 PRD에 옮긴다 |
| 결과물 | 가설 표, 취약점 리포트 | 기획서·PRD, 기능 명세, 회의록 등 |

가설을 아직 못 세웠으면 hypothesis-framework로 먼저 세우고, 기획서는 po-doc-writing으로 이어 씁니다.

## 명세

| 항목 | 내용 |
|---|---|
| 요청 예시 | "가설 세워 줘" · "이거 가설로 만들어 줘" · "실험 설계하려는데" · "A/B 테스트 뭐부터 해야 하지" · "이 기능 효과 있을까" · "전환율 왜 낮은지 모르겠어" · "이 가설 좀 봐 줘" · 아이디어를 말하며 "검증하고 싶다", "근거가 부족한 것 같다"고 할 때 |
| 입력 | 기능·개선·실험 아이디어와 사용자가 가진 관찰·데이터 |
| 출력 | 구조화된 가설 표, 취약점 리포트 |
| 사전 준비 | 없음. `AskUserQuestion` 도구가 있는 환경(Claude Code 등)을 전제로 합니다 |
| 외부에 쓰는가 | 쓰지 않습니다 |

## 설치

```bash
cp -r hypothesis-framework ~/.claude/skills/
```

한 프로젝트에만 쓰려면 저장소 안의 `.claude/skills/hypothesis-framework/`에 둡니다.

사전 준비는 없습니다. `AskUserQuestion` 도구가 없는 환경에서는 같은 질문을 글로 묻습니다.

## 범위와 한계

- 가설을 세우는 데까지만 다룹니다. A/B 테스트 설계, 표본 크기 계산, 결과 분석은 다음 단계로 제안만 합니다.
- 질문이 여러 번 오갑니다. 한 번에 완성된 가설을 원하는 상황에는 맞지 않습니다.
