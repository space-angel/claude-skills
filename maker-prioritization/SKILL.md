# MAKER 우선순위 설정

우선순위 설정은 "무엇을 먼저 할지"와 "이번에 무엇을 안 할지"를 같이 정하는 일이다. 이 스킬은 기법 하나를 고르고, 그 결과를 MoSCoW 네 버킷으로 모아, 실험 설계와 기획서가 그대로 받을 수 있는 한 장으로 끝낸다.

## 전제

- **버킷은 MoSCoW 하나다.** Must / Should / Could / Won't. 다른 기법의 결과(RICE 점수, 사분면, Kano 유형)는 버킷을 정하는 근거일 뿐 버킷이 아니다.
  - Must = "없으면 이번 릴리스가 실패한다". 후보의 30%를 넘지 않는다(상한). 20%보다 적은 것은 위반이 아니다.
  - Should = 중요하지만 없어도 동작한다. 임시 대안이 있다.
  - Could = 있으면 좋다. 자원이 남으면 한다.
  - Won't = 이번 릴리스에서 안 하기로 합의한 것. "절대 안 함"이 아니라 "이번엔 안 함"이다.
- **MVP = Must만.** Should를 MVP에 끼워 넣지 않는다.
- **점수가 버킷을 자동으로 정하지 않는다.** RICE 1위, Quick Win, Kano 매력 요소도 "없으면 실패하는가"를 통과해야 Must가 된다.
- **기준점은 문제 하나다.** 모든 평가는 입력으로 받은 문제 진술문(또는 HMW)에 얼마나 기여하는지로 매긴다. 문제가 없으면 먼저 묻는다.
- 필요한 정보가 없으면 한 번에 하나씩 묻고, 가능하면 선택지를 준다. 모르는 값은 추측하지 않고 `[확인 필요: …]`로 남긴다.
- 숫자 예시는 모두 가상의 예다. 사례는 예약 앱의 "예약 시간 변경" 기능 하나만 쓴다. 관찰: 변경 기능이 없어 취소 후 재예약하는 사용자가 많고, 그중 일부가 재예약하지 않고 이탈한다.

## 입력 계약

| 받는 것 | 출처 | 없으면 |
|---|---|---|
| 문제 진술문 1문장 + HMW 질문 | maker-problem-framing | "이 목록으로 어떤 문제를 풀려는지 한 문장으로 말해 줄 수 있나요?" 한 번 묻고, 답이 없으면 `[확인 필요: 문제 진술문]`로 두고 진행한다 |
| 후보 기능 목록 | 사용자, 백로그, JTBD 기회 영역, 아이디어 회의 | HMW만 있으면 후보를 5~10개 제안하고 사용자가 고르게 한다 |
| 이번 릴리스의 제약 | 사용자 | 기한, 인원, 바꿀 수 없는 결정을 묻는다 |
| 데이터(사용자 수, 공수 추정, 설문 응답) | 사용자 | 기법 고르기에서 데이터 수준으로 판단한다 |

후보마다 "한 줄 설명"이 없으면 먼저 채운다. 이름만 있는 후보는 사람마다 다르게 이해한다.

## 기법 고르기

| 상황 | 후보 수 | 데이터 | 결정 유형 | 쓸 기법 |
|---|---|---|---|---|
| 회의 한 번에 빨리 거르고 싶다 | 5~15개 | 감과 경험뿐 | 무엇부터 손댈까 | **Impact-Effort** |
| 투자 순서를 설명해야 한다, 의견이 갈린다 | 8개 이상(많아도 됨) | 사용자 수와 공수를 대략 추정할 수 있다 | 어디에 먼저 투자할까 | **RICE** |
| 신규 기능을 할지 말지, 기본기와 차별화를 가르고 싶다 | 5~20개 | 사용자 설문을 돌릴 수 있다 | 사용자가 이걸 원하는가 | **Kano** |
| 이번 릴리스에 넣을지 뺄지 | 몇 개든 | 앞 기법의 결과 또는 합의 | 포함/제외 | **MoSCoW** (항상 마지막) |
| 가설 검증용 최소 범위를 정한다 | 몇 개든 | 문제 진술문, 검증할 가정 | 최소로 무엇을 만들까 | **MVP 스코프** (MoSCoW의 Must를 받는다) |

흐름은 항상 `(Impact-Effort | RICE | Kano) → MoSCoW → MVP 스코프`다. 앞 단계는 하나만 골라도 되고 건너뛰어도 된다. 여러 개를 고르면 Kano → RICE 순서로 쓴다(Kano로 무관심·역기능을 걸러 낸 뒤 남은 것을 RICE로 비교). 15개를 넘는 목록에 Impact-Effort를 쓰면 RICE로 바꾸자고 제안한다.

사용자가 기법을 정하지 않았으면 이렇게 묻는다: "후보가 몇 개고, 사용자 수나 공수 추정이 있나요? (1) 없다, 빨리 거르고 싶다 → Impact-Effort (2) 대략 있다 → RICE (3) 설문을 돌릴 수 있다 → Kano"

## 1. Impact-Effort 매트릭스

- **목적**: 영향과 노력 두 축의 2×2로 노력 대비 효과가 큰 항목을 빠르게 찾는다.
- **언제**: 후보 15개 이내, 데이터가 거의 없고, 팀이 한자리에서 빨리 합의해야 할 때.
- **입력**: 문제 진술문, 후보 목록(한 줄 설명 포함).
- **절차와 질문**
  1. 영향 기준을 정한다. 기본은 "문제 진술문의 영향(예: 취소 후 이탈)을 얼마나 줄이는가". 다른 기준(전략 부합, 매출)을 더할지 묻는다.
  2. 노력 기준을 정한다. 개발 기간, 인원, 기술 복잡도, 외부 의존성(다른 팀, 파트너사).
  3. 항목마다 영향 1~5, 노력 1~5를 매긴다. 3 이상을 "높음"으로 본다. 점수마다 근거 한 줄을 받는다.
  4. 사분면에 배치하고 행동을 붙인다.

| 사분면 | 영향 | 노력 | 행동 |
|---|---|---|---|
| Quick Win | 높음 | 낮음 | 먼저 착수 후보 |
| Major Project | 높음 | 높음 | 쪼개거나 단계적으로 계획 |
| Fill-In | 낮음 | 낮음 | 남는 시간에 |
| Thankless | 낮음 | 높음 | 보류, Won't 후보 |

- **산출물 템플릿**

```markdown
## Impact-Effort — <문제 한 줄>
영향 기준: <…> / 노력 기준: <…> / 3 이상 = 높음
| 후보 | 영향(1~5) | 근거 | 노력(1~5) | 근거 | 사분면 |
|---|---|---|---|---|---|
```

- **유의 사항**: 평가자가 한 명이면 편향된다. 디자인·개발 관점의 점수를 따로 받는다. Quick Win은 "빨리 할 만하다"는 뜻이지 Must가 아니다. 같은 사분면 안의 순서가 필요하면 RICE로 넘긴다.
- **다음**: MoSCoW(4절).

## 2. RICE 스코어링

- **목적**: 도달·영향·확신·노력을 숫자로 만들어 투자 순서를 설명할 수 있게 한다.
- **언제**: 후보가 많고, 의견이 갈리고, 사용자 수와 공수를 대략이라도 추정할 수 있을 때.
- **입력**: 문제 진술문, 후보 목록, 기간 기준(예: 분기), 사용량 데이터, 공수 추정.
- **공식**: `RICE = Reach × Impact × Confidence ÷ Effort`
- **척도**

| 요소 | 정의 | 척도 |
|---|---|---|
| Reach | 정한 기간(예: 분기) 동안 이 기능을 만나는 사람 또는 이벤트 수. 절댓값 | 예: 분기 4,000명 |
| Impact | 한 사람이 만났을 때 문제 진술문의 지표가 움직이는 정도 | 3 = 매우 큼 / 2 = 큼 / 1 = 보통 / 0.5 = 작음 / 0.25 = 아주 작음 |
| Confidence | Reach·Impact 추정을 뒷받침하는 근거의 양 | 100% = 데이터 있음 / 80% = 일부 데이터 / 50% = 대부분 가정. 50% 미만이면 점수를 내지 않고 "검증 먼저" 표시 |
| Effort | 기획·디자인·개발·검증을 모두 합친 인원×월(person-month) | 0.5 단위. 최소 0.5 |

- **절차와 질문**
  1. 기간 기준을 하나로 정한다. 항목마다 기간이 다르면 Reach를 비교할 수 없다.
  2. Reach를 묻는다: "이 기능을 분기 동안 몇 명이 만나나요? 근거 데이터가 있나요?" 없으면 `[확인 필요]`로 두고 Confidence를 50%로 둔다.
  3. Impact는 위 다섯 값 중에서만 고르게 한다. 중간값(1.5 등)은 쓰지 않는다.
  4. Effort는 개발만이 아니라 디자인과 검증까지 포함했는지 확인한다.
  5. 점수 순으로 정렬하고 항목마다 "점수로 설명되지 않는 것"(의존성, 법규, 전략)을 한 줄 단다.
  6. Reach나 Effort가 `[확인 필요]`이거나 Confidence가 50% 미만인 항목은 점수를 계산하지 않는다. 순위 없이 표 아래에 "점수 보류(이유)"로 두고, MoSCoW 근거 칸에도 그대로 옮긴다.
- **산출물 템플릿과 예** (가상의 예, 기간 = 분기)

```markdown
## RICE — 예약 시간 변경
| 순위 | 후보 | Reach | Impact | Confidence | Effort | RICE | 점수 밖 고려 |
|---|---|---|---|---|---|---|---|
| 1 | 취소 버튼에서 변경 유도 | 6,000 | 1 | 50% | 0.5 | 6,000 | 변경 흐름이 없으면 의미 없음 |
| 2 | 업체에 변경 알림 | 4,000 | 0.5 | 100% | 0.5 | 4,000 | 없으면 업체가 변경을 모름 |
| 3 | 예약 시간 변경 흐름 | 4,000 | 2 | 80% | 2 | 3,200 | 나머지 전부가 이것에 의존 |
| 4 | 변경 정책·수수료 안내 | 4,000 | 0.5 | 80% | 0.5 | 3,200 | |
| 5 | 남은 자리 수 표시 | 4,000 | 0.5 | 50% | 1 | 1,000 | |
| 6 | 변경 이력 보기 | 800 | 0.25 | 80% | 0.5 | 320 | |
| 7 | 원하는 시간 대기 알림 | 1,500 | 1 | 50% | 3 | 250 | |
| 8 | 캘린더 앱 동기화 | 2,000 | 0.25 | 50% | 1 | 250 | |
```

- **유의 사항**: RICE는 의존성을 모른다. 위 예에서 1위는 3위가 없으면 쓸모가 없다. 점수는 순서를 설명하는 근거이고, 버킷은 MoSCoW에서 정한다. 시장·기술이 바뀌면 다시 매긴다.
- **다음**: MoSCoW(4절). Confidence 50% 항목은 maker-experiment-design으로 검증 먼저.

## 3. Kano 모델

- **목적**: 기능이 있을 때와 없을 때 사용자 만족이 어떻게 바뀌는지로 기능을 유형화해, 기본기와 차별화를 가른다.
- **언제**: 신규 기능을 할지 말지 정할 때, 사용자 만족이 핵심 지표일 때, 설문을 돌릴 수 있을 때.
- **입력**: 후보 목록, 응답자 풀(세그먼트 정의 포함).
- **절차와 질문**
  1. 기능마다 짝 질문 두 개를 만든다. 기능은 사용자가 아는 말로, 장면으로 쓴다.
     - 기능적 질문: "예약 시간을 앱에서 바로 바꿀 수 있다면 어떻게 느끼시나요?"
     - 역기능적 질문: "예약 시간을 바꾸려면 취소하고 다시 예약해야 한다면 어떻게 느끼시나요?"
  2. 두 질문 모두 같은 다섯 응답을 쓴다: ① 마음에 든다 ② 당연하다 ③ 상관없다 ④ 참을 수 있다 ⑤ 마음에 들지 않는다.
  3. 응답자를 모은다. 세그먼트마다 따로 집계한다. 응답이 적으면 분류가 흔들리니 표본 수를 결과에 같이 적는다.
  4. 응답 한 쌍을 아래 평가표로 한 글자로 바꾼다.
  5. 기능마다 가장 많이 나온 유형을 고른다. 비율은 Q를 뺀 응답 수로 계산한다. 두 유형이 비슷하면(차이 10%p 이내) M > O > A > I 순으로 정하고 "경계"라고 적는다. R이 다른 유형과 비슷하면 순서를 정하지 않고 "경계(R)"로 두고, 응답자를 나눠 볼 수 있는지 묻는다. Q가 많으면 문항을 고친다.
- **Kano 평가표 (행 = 기능적 질문 응답, 열 = 역기능적 질문 응답)**

| 기능적 \ 역기능적 | 마음에 든다 | 당연하다 | 상관없다 | 참을 수 있다 | 마음에 들지 않는다 |
|---|---|---|---|---|---|
| 마음에 든다 | Q | A | A | A | O |
| 당연하다 | R | I | I | I | M |
| 상관없다 | R | I | I | I | M |
| 참을 수 있다 | R | I | I | I | M |
| 마음에 들지 않는다 | R | R | R | R | Q |

M 기본(없으면 불만, 있으면 당연) · O 성능(많을수록 만족) · A 매력(없어도 불만 없고 있으면 크게 만족) · I 무관심 · R 역기능(있으면 오히려 불만) · Q 의심 응답(모순, 집계에서 뺌)

- **보조 지표(선택)**: 만족 계수 = (A+O) ÷ (A+O+M+I), 불만 계수 = −(O+M) ÷ (A+O+M+I). 만족 계수가 크면 넣었을 때 효과가, 불만 계수의 절댓값이 크면 뺐을 때 타격이 크다.
- **MoSCoW로 넘길 때의 기본값** (근거일 뿐 자동 배정 아님)

| Kano 유형 | MoSCoW 후보 | 확인 질문 |
|---|---|---|
| M | Must 후보 | 이번 문제 진술문의 범위 안인가? |
| O | Should 또는 Could | RICE로 순서를 정한다 |
| A | Could(차별화가 이번 목표면 Should) | 기본기(M)가 다 채워졌나? |
| I | Won't | |
| R | Won't(제거 검토) | 이미 있는 기능이면 제거 과제로 따로 올린다 |

- **산출물 템플릿**

```markdown
## Kano — <주제>
조사: 대상 <세그먼트> / 방법 <설문·인터뷰> / 응답 수 <n> (Q 제외 후 <n>)
| 기능 | M | O | A | I | R | Q | 유형 | 만족 계수 | 불만 계수 | 경계 여부 |
|---|---|---|---|---|---|---|---|---|---|---|
```

- **유의 사항**: 유형은 시간이 지나면 바뀐다(매력 → 성능 → 기본). 재조사 시점을 적는다. 세그먼트를 섞어 집계하면 유형이 상쇄되어 I로 보인다.
- **다음**: RICE(2절, 같은 유형 안 순서) 또는 MoSCoW(4절).

## 4. MoSCoW 분석

- **목적**: 모든 후보를 네 버킷에 넣어 이번 릴리스 범위를 고정하고, 범위가 늘어나는 것을 막는다.
- **언제**: 항상 마지막에. 앞 기법 없이 바로 써도 된다.
- **입력**: 후보 목록 + 앞 기법의 결과(점수·사분면·유형) + 릴리스 제약.
- **절차와 질문**
  1. 항목마다 "이게 없으면 이번 릴리스가 실패하나요?"를 묻는다. 예이면 Must 후보. 실패의 뜻은 문제 진술문이 풀리지 않는 것, 법규 위반, 기술적으로 동작하지 않는 것 셋이다.
  2. 아니면 "임시 대안이 있나요?" 있으면 Should, 대안이 필요 없을 만큼 작으면 Could.
  3. 이번에 안 할 것은 Won't에 넣고 이유와 재검토 조건을 쓴다.
  4. Must 비율을 센다. 30%를 넘으면 Must 항목마다 "이것만 빼고 출시하면 실패인가?"를 다시 물어 내린다.
  5. 버킷 안 순서는 의존성 → RICE 점수 → 합의 순서로 정한다.
- **산출물 템플릿과 예** (가상의 예, 2절의 8개)

```markdown
## MoSCoW — 예약 시간 변경 (Must 2/8 = 25%)
| 버킷 | 후보 | 근거 | 임시 대안 / 다시 볼 조건 |
|---|---|---|---|
| Must | 예약 시간 변경 흐름 | 없으면 문제(취소 후 이탈)가 그대로 | — |
| Must | 업체에 변경 알림 | 없으면 업체가 바뀐 시간을 모름 | — |
| Should | 취소 버튼에서 변경 유도 | RICE 1위지만 변경 흐름에 의존 | 없으면 메뉴에서 변경 진입 |
| Should | 변경 정책·수수료 안내 | 분쟁 예방 | 기존 정책 페이지 링크 |
| Could | 남은 자리 수 표시 | 확신 50% | — |
| Could | 변경 이력 보기 | 도달 적음 | — |
| Won't | 원하는 시간 대기 알림 | 공수 3, 확신 50% | 변경 흐름 사용률이 확인되면 |
| Won't | 캘린더 앱 동기화 | 문제와 거리가 멂 | 사용자 요청이 반복되면 |
```

RICE 1위가 Must가 아닌 이유를 이렇게 표에 남긴다.
- **유의 사항**: Must는 정치적으로 늘어나기 쉽다. 근거 칸이 비어 있는 Must는 받지 않는다. 기술·디자인·사업 관점이 모두 합의에 들어갔는지 확인한다.
- **다음**: MVP 스코프(5절), 또는 바로 산출물(6절).

## 5. MVP 스코프 정의

- **목적**: 핵심 가정을 검증하는 데 필요한 최소 범위를 Must로 고정하고, 무엇을 배우려는지와 언제 다시 판단할지를 붙인다.
- **언제**: 신규 기능처럼 불확실성이 클 때, 단계적으로 출시할 때.
- **입력**: 문제 진술문, 4절의 버킷, 사용자 흐름(maker-problem-framing의 여정 맵이 있으면 그것).
- **절차와 질문**
  1. 검증할 가정을 유형별로 적는다. 유형은 문제 / 솔루션 / 성장 / 가치 넷이다. 가정은 질문 형태로만 두고, 가설 문장은 hypothesis-framework 몫으로 넘긴다.
  2. 핵심 사용자 흐름을 처음부터 끝까지 한 줄로 쓰고(예: 예약 상세 → 시간 변경 → 새 시간 선택 → 확인 → 업체 알림), 각 단계를 받치는 Must가 있는지 확인한다. 빈 단계가 있으면 Must가 빠졌거나 흐름을 줄여야 한다.
  3. Must마다 세 질문을 통과시킨다: 가정 검증에 필수인가? 없으면 가치 제안이 불가능한가? 기술 의존성 때문에 꼭 필요한가? 셋 다 아니면 Should로 내린다.
  4. 더 적은 노력으로 같은 걸 배울 수 있는지 묻는다(예: 변경을 운영자가 수동 처리하는 컨시어지 방식). 있으면 그 방식을 MVP 범위로 적고, 4절 버킷을 다시 매겨 Must 목록과 MVP 범위를 맞춘다.
  5. 다시 판단할 시점과 기준을 적는다. 기준 지표의 설계는 maker-experiment-design으로 넘긴다.
- **유의 사항**: "최소"와 "쓸 수 있는"의 균형을 본다. 흐름이 끊긴 MVP는 아무것도 검증하지 못한다. 임시 방편이 기술 부채로 남으면 Won't에 "정리 작업"으로 적어 둔다.
- **다음**: 6절 산출물로 합친다.

## 6. 산출물 (모든 경로의 끝)

파일 하나로 저장하고 경로를 알린다. 파일명 예: `priority-<주제>-<YYYYMMDD>.md`.

```markdown
# 우선순위 — <주제>
- 문제 진술문: <maker-problem-framing에서 받은 1문장 | [확인 필요]>
- HMW: <…>
- 쓴 기법: <Impact-Effort | RICE | Kano> → MoSCoW (→ MVP 스코프)
- 기준 날짜와 기간: <YYYY-MM-DD, RICE 기간 기준>

## 1. 순위 목록
| 순위 | 후보 | 버킷 | 근거(점수·사분면·유형) | 의존 |
|---|---|---|---|---|

## 2. MVP 범위 (Must만, 후보의 n/N = x%)
| 기능 | 없으면 실패하는 이유 | 받치는 흐름 단계 |
|---|---|---|
- 검증할 가정: [문제] … / [솔루션] … / [성장] … / [가치] …
- 다시 판단할 시점: <예: 출시 4주 후>

## 3. Won't 목록 (이번 릴리스에서 하지 않음)
| 기능 | 이유 | 다시 볼 조건 |
|---|---|---|

## 4. 확인 필요
- [확인 필요: …]
```

| 받는 곳 | 가져가는 것 |
|---|---|
| maker-experiment-design | MVP 범위, 검증할 가정, 다시 판단할 시점 → 실험 설계와 지표(북극성 1, 주요 1~2, 가드레일 1~3) |
| hypothesis-framework | 검증할 가정 → 가설 문장 |
| po-doc-writing (기획서·PRD 실행형) | 문제 진술문 → "출발점이 된 문제", MVP 범위 → 해결 범위와 완료 조건, Won't 목록 → "하지 않는 것과 이미 정해진 결정" |
| po-doc-writing (결정이 필요한 질문·결정 기록) | Kano 유형·RICE 점수 → 질문의 "근거", MoSCoW 버킷과 MVP 범위 → 선택지와 추천, Won't 목록 → "검토한 선택지", 확인 필요 → "정할 것 / 확인하지 못한 것" |
| linear-sync | Must 항목 → 이슈 초안(승인 후 등록) |

노션에 올려 달라고 하면 승인을 받은 뒤 `notion-ops`로 넘긴다.

## 하지 않는 것

- 문제 정의를 대신하지 않는다. 문제 진술문을 새로 쓰는 일은 maker-problem-framing에 맡긴다.
- 가설 문장을 쓰지 않는다. hypothesis-framework로 넘긴다.
- 지표·표본 크기·실험 기간을 정하지 않는다. maker-experiment-design으로 넘긴다.
- RICE의 Reach·Effort를 지어내지 않는다. 모르면 `[확인 필요]`와 Confidence 50%.
- 점수나 사분면만 보고 Must를 정하지 않는다.
- Must가 30%를 넘는 결과를 그대로 내지 않는다.
- 실제 회사 사례나 출처 없는 성과 수치를 근거로 쓰지 않는다.
- 사용자 승인 없이 이슈 트래커나 노션에 쓰지 않는다.
