# maker-prioritization

후보 기능의 순서를 정하고, 이번 릴리스에 넣을 것(Must)과 안 할 것(Won't)을 한 장으로 잘라 주는 스킬입니다.

[SKILL.md](SKILL.md) · [설치](#설치) · 함께 쓰는 스킬: [maker-problem-framing](../maker-problem-framing/) · [maker-experiment-design](../maker-experiment-design/) · [hypothesis-framework](../hypothesis-framework/) · [po-doc-writing](../po-doc-writing/)

## 구성

maker-prioritization은 기법이 무엇이든 같은 순서로 끝납니다.

1. **입력 확인** — 문제 진술문(또는 HMW)과 후보 목록을 받습니다. 문제가 없으면 한 번 묻습니다.
2. **기법 고르기** — 후보 수, 데이터, 결정 유형으로 Impact-Effort·RICE·Kano 중 하나를 고릅니다. 건너뛰어도 됩니다.
3. **MoSCoW로 모으기** — 모든 결과를 Must / Should / Could / Won't 하나로 모읍니다. Must는 20~30% 이내입니다.
4. **MVP 스코프** — Must만으로 핵심 흐름이 끊기지 않는지, 무엇을 검증하려는지 확인합니다.
5. **산출물** — 순위 목록, MVP 범위, Won't 목록을 md 파일 하나로 저장합니다.

## 모듈

### Impact-Effort 매트릭스

영향과 노력을 1~5로 매겨 네 사분면(Quick Win, Major Project, Fill-In, Thankless)에 놓습니다. 15개 이내의 후보를 회의 한 번에 거를 때 씁니다.

### RICE 스코어링

`Reach × Impact × Confidence ÷ Effort`로 점수를 냅니다. Impact는 3 / 2 / 1 / 0.5 / 0.25, Confidence는 100 / 80 / 50%, Effort는 인원×월(person-month)로 고정합니다. 확신이 50% 미만이면 점수 대신 "검증 먼저"로 표시합니다.

### Kano 모델

기능마다 "있다면 / 없다면" 짝 질문을 만들고, 응답 한 쌍을 5×5 평가표로 기본(M)·성능(O)·매력(A)·무관심(I)·역기능(R)·의심(Q) 중 하나로 바꿉니다. 만족·불만 계수를 함께 냅니다.

### MoSCoW 분석

모든 경로가 거치는 마지막 분류입니다. "없으면 이번 릴리스가 실패하는가"로 Must를 가르고, Won't마다 이유와 다시 볼 조건을 붙입니다.

### MVP 스코프 정의

Must만으로 MVP를 정합니다. 검증할 가정을 문제 / 솔루션 / 성장 / 가치 네 유형으로 적고, 핵심 흐름의 각 단계를 받치는 Must가 있는지 봅니다.

## 상황별 사용

### 문제 정의를 막 끝냈을 때

maker-problem-framing이 낸 문제 진술문과 HMW가 있고, 아이디어가 여러 개 나온 상황입니다.

사용할 모듈: Impact-Effort 또는 RICE → MoSCoW → MVP 스코프

### 백로그가 너무 길 때

수십 개 후보의 순서를 이해관계자에게 설명해야 하는 상황입니다.

사용할 모듈: RICE → MoSCoW

### 이 기능을 만들지 말지 정할 때

사용자가 원하는지부터 확인해야 하는 상황입니다. 설문을 돌릴 수 있어야 합니다.

사용할 모듈: Kano → RICE → MoSCoW

### 릴리스 범위를 자를 때

기한은 정해져 있고 넣을 것과 뺄 것을 합의해야 하는 상황입니다.

사용할 모듈: MoSCoW → MVP 스코프

## 가이드라인

### 점수는 근거이고 버킷이 아닙니다

RICE 1위, Quick Win, Kano 매력 요소도 "없으면 실패하는가"를 통과해야 Must가 됩니다. RICE는 의존성을 모르기 때문에, 다른 기능이 있어야 쓸모 있는 항목이 1위에 오르기도 합니다.

### Must는 30%를 넘지 않습니다

넘으면 Must마다 "이것만 빼고 출시하면 실패인가"를 다시 묻습니다. 근거 칸이 빈 Must는 받지 않습니다.

### 모르는 숫자는 비워 둡니다

Reach나 공수를 모르면 `[확인 필요]`로 두고 Confidence를 50%로 내립니다. 그럴듯한 숫자를 채우지 않습니다.

| 지양 | 권장 |
|---|---|
| RICE 1위인 "취소 버튼에서 변경 유도"를 Must에 넣는다 | 변경 흐름에 의존하니 Should로 두고 이유를 표에 남긴다 |
| Quick Win을 전부 MVP에 넣는다 | Quick Win도 "없으면 실패하는가"로 다시 거른다 |
| 8개 중 5개를 Must로 둔다 | 2~3개로 줄이고 나머지는 임시 대안을 적어 Should로 내린다 |
| Won't에 이름만 적는다 | 이유와 "다시 볼 조건"을 같이 적는다 |
| 분기 사용자 수를 감으로 채운다 | `[확인 필요]`로 두고 Confidence 50% |

표의 예는 가상의 예약 앱 "예약 시간 변경" 기능입니다.

### 끝은 항상 같은 모양입니다

어느 기법으로 시작했든 순위 목록 + MVP 범위(Must만) + Won't 목록으로 끝납니다. 그래야 다음 스킬이 그대로 받습니다.

## maker-prioritization vs maker-experiment-design

| | maker-prioritization | maker-experiment-design |
|---|---|---|
| 묻는 것 | 무엇을 먼저, 무엇을 이번에 안 할까 | 그게 맞는지 어떻게 확인할까 |
| 결과물 | 순위 목록, MVP 범위, Won't 목록, 검증할 가정 | 실험 설계, 지표, 표본과 기간 |
| 지표를 정하는가 | 다시 판단할 시점만 적는다 | 북극성·주요·가드레일 지표를 설계한다 |

maker-prioritization이 넘긴 MVP 범위와 검증할 가정을 maker-experiment-design이 받습니다. 가설 문장은 두 스킬 모두 [hypothesis-framework](../hypothesis-framework/)에 맡깁니다.

## 근거

2025년 5월에 만든 MAKER 프레임워크의 우선순위 설정 카테고리(RICE, MoSCoW, Impact-Effort, MVP 스코프 정의, Kano 다섯 모듈)를 실행 가능한 스킬로 옮겼습니다. 원본은 읽는 문서였고, 옮기면서 아래를 고쳤습니다.

| 구분 | 원본 | 스킬 |
|---|---|---|
| 통일 | MVP 스코프는 Must Have / Nice to Have / Later / Not Needed, MoSCoW는 Must / Should / Could / Won't로 따로 썼습니다 | MoSCoW 하나로 모았습니다. MVP는 Must만입니다 |
| 통일 | Impact-Effort의 Quick Win을 Must로 옮기라고 했습니다 | 사분면은 별도 축입니다. Must는 "없으면 실패하는가"로만 정합니다 |
| 통일 | MVP 가설 유형이 가치 / 솔루션 / 성장 / 비즈니스였습니다 | 문제 / 솔루션 / 성장 / 가치 넷으로 맞췄습니다 |
| 보완 | 기법을 고르는 기준이 "투자 / 포함 여부 / 만족도" 한 줄이었습니다 | 후보 수·데이터·결정 유형으로 고르는 표를 만들었습니다 |
| 보완 | Kano 평가표(5×5)가 없었습니다 | 평가표, 동률 규칙, 만족·불만 계수, MoSCoW로 넘기는 기본값을 넣었습니다 |
| 보완 | RICE 척도가 Confidence 20%, Effort 인주(person-week)였습니다 | Impact 5단계, Confidence 100/80/50%, Effort 인원×월로 고정했습니다 |
| 보완 | 모듈 사이 입력과 출력이 정해져 있지 않았습니다 | 문제 진술문을 받아 순위 목록 + MVP 범위 + Won't 목록을 내는 계약을 정했습니다 |
| 사례 교체 | 실제 회사 사례와 출처 없는 성과 수치 | 가상의 예약 앱 "예약 시간 변경" 하나로 바꿨습니다 |

원본이 가리키지만 존재하지 않는 모듈(로드맵 계획, 스프린트 계획)은 연결하지 않았습니다. 스프린트 공유가 필요하면 [team-status-report](../team-status-report/)나 [slack-team-post](../slack-team-post/)를 씁니다.

## 검증

함정을 심은 가상 시나리오로 네비게이터부터 스프린트 공유까지 이어서 실행했습니다. 예약 앱 예시와 겹치지 않도록 가상의 중고책 마켓 앱을 썼습니다.

- **재료** — 판매자용 후보 기능 10개(분기 도달 수, 영향, 확신, 공수 포함. 그중 둘은 도달 수나 공수가 비어 있음), 판매자 12명의 Kano 응답(기능 4개, 의심 응답 1건과 역기능 유형 1개, 매력과 성능이 8.3%p 차이인 경계 1개), 역할 셋(PM, 개발 리드, 디자이너)으로 된 팀 정보.
- **요청** — "판매자용 자동 가격 추천 기능 만들지 말지 정해야 해. 후보 기능도 10개쯤 있어."
- **함정** — Must 초안이 후보의 50%입니다. RICE 1위 기능이 다른 기능 없이는 동작하지 않습니다. 확신 30%인 후보가 있습니다. 결정권자(Approver)가 지정되지 않았습니다.
- **통과** — "이 기능을 만들지 말지" 프리셋(Kano → RICE → 결정 문서)을 골랐습니다. Kano 5×5 평가표 분류와 만족·불만 계수, RICE 점수가 손 계산과 일치했습니다. 경계 기능은 M > O > A > I 규칙으로 성능(O)에 두고 "경계"로 표시했습니다. 무관심·역기능 기능은 RICE 전에 Won't로 걸렀습니다. RICE 1위는 의존 때문에 Could로 내리고 이유를 표에 남겼습니다. 확신 30%와 데이터가 빈 후보는 점수를 내지 않고 "점수 보류"로 두었습니다. Must는 "이것만 빼고 출시하면 실패인가"를 다시 물어 20%로 줄였습니다. 결정 질문 문서에는 Approver를 `[확인 필요]`로 남겼고, 결정 기록은 결정 하나에 기록 하나로 나눠 초안 상태로 두었습니다. 스프린트 공유는 못 읽은 출처를 맨 위에 밝히고 결정 문서를 "일부 달성"으로 적었습니다.
- **확인하지 못한 것** — 실제 설문 도구에서 받은 응답의 모양, 응답자가 수십 명 이상일 때 경계 판정이 흔들리는 정도, 가중 평가표 점수를 여러 사람이 매겼을 때의 차이, 실제 트래커·GitHub·위키를 읽은 스프린트 공유, 팀원의 반응.

## 설치

```bash
mkdir -p ~/.claude/skills/maker-prioritization && cp SKILL.md ~/.claude/skills/maker-prioritization/
```

한 프로젝트에만 쓰려면 저장소 안의 `.claude/skills/maker-prioritization/`에 둡니다. 다음 세션부터 Claude가 알아서 꺼내 씁니다.

## 범위와 한계

- 순서와 범위를 정하는 데까지만 다룹니다. 문제 정의, 가설 문장, 지표 설계는 다른 스킬로 넘깁니다.
- Kano 설문을 대신 돌리지 않습니다. 문항을 만들고, 받은 응답을 분류합니다.
- RICE 점수의 정확도는 입력 추정에 달려 있습니다. 스킬은 추정을 만들지 않고 비어 있는 곳을 표시합니다.
- 효과를 수치로 재지는 않았습니다.
