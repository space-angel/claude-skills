# po-doc-writing

기능 목록 대신 "왜 만들고 무엇을 안 만드나"에 답하는 PM/PO 문서를 쓰는 스킬입니다.

[SKILL.md](SKILL.md) · [설치](#설치) · 함께 쓰는 스킬: [ko-tech-prose](../ko-tech-prose/) · [notion-ops](../notion-ops/) · [linear-sync](../linear-sync/) · [hypothesis-framework](../hypothesis-framework/)

## 구성

po-doc-writing은 문서 유형마다 뼈대는 달라도 순서는 같습니다. 문제 → 결정 → 근거입니다. 작성은 다섯 단계로 고정합니다.

1. **문서 정하기** — 요청 문장으로 7개 유형 중 하나를 고르고, 놓일 곳에 맞춰 문체를 정합니다. 위키 기준은 평서문, 기획서·가이드는 해요체입니다.
2. **재료 읽기** — 이슈는 댓글까지, PR은 내용까지 읽습니다. 숫자는 원본에서 다시 셉니다.
3. **머리와 꼬리** — 머리에는 넣을 곳·담당·상태, "이 문서를 읽으면 ~을 알 수 있어요", 용어 정의를 둡니다. 끝에는 하지 않는 것, 다 됐다고 볼 조건, 확인하지 못한 것을 둡니다.
4. **유형별 뼈대** — 아래 모드의 뼈대로 씁니다.
5. **점검 후 초안** — 9개 항목으로 점검한 뒤 초안을 보여 줍니다. 외부 도구에는 승인 후에 올립니다.

## 모드

### A. 기획서·PRD 검증형

아직 효과를 모르는 것을 확인하려는 문서입니다. 문제, 가설 한 문장, 검증 방법, 판정 기준, 대안 가설 순서로 씁니다. 가설을 아직 못 세웠으면 hypothesis-framework로 먼저 세웁니다.

### B. 기획서·PRD 실행형

만들기로 정한 것을 디자이너와 개발자에게 넘기는 문서입니다. 해결 원칙마다 소제목을 결정 문장으로 쓰고, 하지 않는 것과 이미 정해진 결정을 앞에 둡니다.

### C. 기능 명세

기능이 하는 일과 가설 한 줄, 용어와 계산 규칙, 핵심 흐름, 예외 상황 처리 규칙을 씁니다. 다 됐다고 볼 조건은 테스트로 확인할 수 있게 체크박스로 씁니다.

### D. 결정이 필요한 질문

질문마다 지금 상황, 선택지, 근거, 추천, 정하면 풀리는 것을 같은 틀로 씁니다. 문서 맨 위에 "추천은 제안이고, 결정은 Approver가 해요"를 둡니다. 역할은 DACI(Driver 진행 / Approver 최종 결정 / Contributors 의견 / Informed 결과 전달)로 적고, 선택지가 셋 이상이면 기준·가중치·선택지별 점수로 된 가중 평가표를 붙입니다.

### E. 결정 기록

한 기록에 결정 하나를 쓰고, 값은 한 문장으로 끝냅니다. 정한 사람(DACI), 알릴 사람, 고르지 않은 선택지와 재검토 날짜를 함께 남깁니다. 지난 결정은 지우지 않고 폐기로 표시합니다.

### F. 회의록·회의 준비 시트

회의 전에는 준비 시트를 씁니다. 목적 한 줄, DACI 기준으로 꼭 필요한 참석자, 미리 읽을 자료, 안건별 시간을 적습니다. 회의 뒤에는 정한 것, 담당자별 할 일(기한 포함), 미결 사항, 후순위 순서로 씁니다. 담당자가 정해지지 않은 항목은 짐작하지 않고 "담당 미정"으로 둡니다.

### G. 가이드·온보딩·인계, 테스트 일지

가이드는 한 단계에 한 동작으로 쓰고, 버튼·화면 이름은 실제 표기 그대로 씁니다. 테스트 일지는 실제 사용자 한 명의 흐름으로 시나리오를 쓰고, 기대한 것과 실제로 된 것의 차이를 남깁니다.

## 상황별 사용

### 회의가 끝난 직후

정한 것과 담당자별 할 일을 회의에 없던 팀원에게도 공유하는 상황입니다. 할 일을 이슈로 옮길 때는 [linear-sync](../linear-sync/)가 등록합니다.

사용할 모드: F. 회의록

### 회의를 열기 전

목적이 한 줄로 서는지, 누가 꼭 와야 하는지 정하는 상황입니다. 목적이 한 줄로 서지 않으면 회의 대신 결정이 필요한 질문 문서로 비동기로 묻습니다. 정기 위클리 안건은 [team-status-report](../team-status-report/)가 만듭니다.

사용할 모드: F. 회의 준비 시트

### 디자이너와 개발자에게 넘기기 전

만들기로 정한 범위와 동작을 구현할 사람에게 넘기는 상황입니다.

사용할 모드: B. 기획서·PRD 실행형, C. 기능 명세

### 팀이 정해야 할 것이 쌓였을 때

선택지와 근거를 정리해 결정을 받아야 하는 상황입니다. 누가 최종 결정하는지(Approver)부터 정하고, 선택지가 셋 이상이면 가중 평가표로 비교합니다. 정한 뒤에는 결정 기록으로 남깁니다.

사용할 모드: D. 결정이 필요한 질문, E. 결정 기록

### 효과를 아직 모르는 아이디어가 있을 때

만들기 전에 먹힐지부터 확인하려는 상황입니다. 가설을 아직 못 세웠으면 [hypothesis-framework](../hypothesis-framework/)로 먼저 세웁니다.

사용할 모드: A. 기획서·PRD 검증형

### 새 팀원이 합류하거나 업무를 넘길 때

맥락 없는 사람이 혼자 따라 할 수 있어야 하는 상황입니다. 테스트를 마친 뒤 결과를 남길 때도 같습니다.

사용할 모드: G. 가이드·온보딩·인계, 테스트 일지

## 가이드라인

### 문제 → 결정 → 근거 순서로 씁니다

기능 목록부터 쓰면 팀이 실제로 묻는 "왜 이걸 만드나"와 "무엇을 안 만드나"에 답하지 못합니다. 그래서 회의에서 같은 질문이 다시 나옵니다. 섹션 첫 문장에 결정을 두고, 하지 않는 것을 명시합니다.

### 근거는 PR 번호가 아니라 내용으로 씁니다

"PR #18 참고" 대신 그 PR이 뒷받침하는 데이터를 씁니다. "그게 근거지, PR이라고 말하면 안 되지"라는 교정에서 나온 규칙입니다.

### 맥락 없는 외부인 기준으로 씁니다

약어·이슈 키·에러 코드만으로 설명하지 않습니다. 개발 용어는 처음 나올 때 풀어 씁니다.

### 할 일에는 왜와 완료 기준을 붙입니다

짧게 만들려고 둘을 빼지 않습니다. AI가 할 정리 작업은 팀원 할 일로 넘기지 않고 지금 초안으로 만듭니다.

### 작업 경과는 문서에 쓰지 않습니다

"오후에 고쳤어요" 같은 경과는 빼고 지금 상태만 씁니다. 구현 세부보다 해결한 문제를 앞에 둡니다.

| 지양 | 권장 |
|---|---|
| `## 주요 기능` 아래에 "예약 변경 기능", "알림 기능"을 나열한다 | `## 원칙 1. 예약 변경은 한 화면에서 끝낸다`처럼 소제목에 결정을 쓴다 |
| 출발점 없이 기능부터 쓴다 | "퇴근길에 예약 시간을 바꾸려는 사용자가 화면을 여러 번 오간다"처럼 문제에서 시작한다 |
| "자세한 내용은 PR #18 참고"로 근거를 대신한다 | PR 번호가 아니라 로그에서 확인한 내용을 근거로 쓴다 |
| 범위를 말하지 않는다 | "이번 범위에서 결제 수단 변경은 뺀다"처럼 하지 않는 것을 쓴다 |

표의 예는 가상의 예약 앱 기획서 한 절입니다.

## po-doc-writing vs decision-first-article

| | po-doc-writing | decision-first-article |
|---|---|---|
| 하는 일 | 팀이 다음 행동을 정하게 하는 문서를 쓴다 | 끝낸 작업을 결정이 먼저 나오는 아티클로 쓴다 |
| 시점 | 만들기 전·진행 중(기획서, 명세, 회의록) | 끝낸 뒤 |
| 독자 | 디자이너, 개발자, 맥락 없는 팀원 | 기술 블로그·포트폴리오 독자 |

진행 중인 결정은 po-doc-writing으로 남기고, 끝낸 작업을 글로 정리할 때는 decision-first-article로 넘깁니다.

## 명세

| 항목 | 내용 |
|---|---|
| 요청 예시 | "맥락 모르는 사람도 무슨 소린지 알게끔 문서화해서 md로"(쉬운 설명) · "노션 온보딩 가이드 문서 작성해 줄 수 있어? 비개발자들을 위해서"(G) · "더 디벨롭해서 기능 기획서로 작성해 봐, 구현 스펙이랑"(B·C) · "방금 한 테스트 사람들이 보기 쉽게 테스트 일지 작성해서 md로"(G) · "오늘 회의록 공유할 텍스트 전체 상세하게 정리"(F) · "내일 회의 준비 시트 만들어 줘"(F) · "나의 결정을 도와주기 위한 근거 좀 부탁할게"(D) |
| 입력 | 이슈(설명, 댓글), PR 내용, 회의 메모, 인계 요약 같은 원천 자료 |
| 출력 | md 파일 문서 초안. 점검 결과는 문서가 아니라 답변에 붙입니다 |
| 사전 준비 | 없음 |
| 외부에 쓰는가 | 기본은 md 파일입니다. 노션·리니어·위키는 초안을 보여 주고 승인을 받은 뒤에만 올립니다 |
| 근거 | 여러 팀의 기획서·회의록을 쓰며 반복된 교정, 저자가 직접 쓰고 고치지 않은 문서 |
| 검증 | 가상 예약 앱 팀 자료 시나리오 테스트(B, D, F) |

## 근거

아래 규칙은 여러 팀의 기획서·회의록·인계 문서를 쓰며 반복된 교정에서 나왔습니다. 가장 자주 반복된 것은 이미 쓴 문장을 다시 쉽게 풀어 달라는 요청이었고, "외부인 기준" 규칙은 이 되풀이를 줄이려는 것입니다.

뼈대는 저자가 직접 쓰고 이후 고치지 않은 문서에서 가져왔습니다. 검증형 PRD, MVP 실행형 PRD, 기능 기획서, 기능 명세, 결정 질문 문서, 팀 위키의 결정 기록 양식입니다. 규칙은 초안을 고친 방향에서 왔습니다.

| 고친 말 | 규칙 |
|---|---|
| "그냥 뻔하게 스펙을 나열하는 게 아니라… 근거 있게" | 문제 → 결정 → 근거 순서로 쓴다 |
| "그게 근거지, PR이라고 말하면 안 되지. 명시된 데이터 기준으로" | 근거는 PR 번호가 아니라 내용으로 쓴다 |
| "프로젝트 맥락 모르면 뭔 소리인지 모르게 말고, 진짜 외부인이 봤을 때 기준으로" | 약어·이슈 키·에러 코드만으로 설명하지 않는다 |
| "왜 해야 하는지 그리고 구체적인 완료 기준도… 길어져도 되니까" | 할 일에는 왜와 완료 기준을 붙인다 |
| "PR 18번은 오후에 반영해 고쳤어요, 이거 빼고" | 작업 경과를 문서에 쓰지 않는다 |
| "문서 최신화하라고는 하지 마, 너가 하면 되니까" | AI가 할 정리 작업을 팀원 할 일로 넘기지 않는다 |
| "준비물 부분은 빼고 어떤 문제를 해결했는지를… 프로덕트 단에서" | 구현 세부보다 해결한 문제를 앞에 둔다 |
| "등록하기 전에 초안 보여 주고" | 노션·리니어·위키에 올리기 전에 초안을 보여 준다 |

의사결정·회의 규칙은 2025년 5월에 만든 MAKER 프레임워크의 커뮤니케이션 모듈에서 가져왔습니다. 원본의 역할 모델(회의 쪽은 RACI)은 DACI 하나로 통일했습니다.

팀 위키의 기준 작성 원칙도 넣었습니다. 기준 하나에 규칙 하나, 제목만 읽어도 결정이 보이게, "적절히/필요시" 금지, 숫자는 단위까지, 지난 결정은 지우지 않고 폐기로 표시합니다.

## 검증

함정을 심은 가상의 예약 앱 팀 자료로 시나리오 테스트를 했습니다.

- **재료** — 이슈 6개, PR 요약 3개, 회의 메모, 인계 요약. 심은 함정은 다섯 가지입니다. 댓글에서 범위가 빠졌는데 설명에는 남아 있는 이슈, 인계 요약의 실패 건수(712)와 PR 원본 로그(612)의 차이, 원본 없이 댓글에만 있는 숫자, "409 conflict"·"idempotency key" 같은 개발 용어와 이슈 키, 회의 메모의 이미 끝난 항목과 팀원에게 넘겨진 위키 정리 작업입니다.
- **요청** — 실행형 기획서(B), 결정이 필요한 질문(D), 회의록(F) 세 가지를 쓰게 했습니다.
- **통과** — 심은 함정을 모두 걸렀습니다.
- **확인하지 못한 것** — 검증형 PRD(A), 기능 명세(C), 결정 기록(E), 가이드·테스트 일지(G)는 돌려 보지 않았습니다. 실제 팀이 이 문서를 받고 회의가 짧아졌는지도 확인하지 않았습니다.

## 설치

```bash
cp -r po-doc-writing ~/.claude/skills/
```

한 프로젝트에만 쓰려면 저장소 안의 `.claude/skills/po-doc-writing/`에 둡니다. 사전 준비는 없습니다.

문장 교정은 ko-tech-prose, 노션 업로드는 notion-ops, 이슈 등록은 linear-sync, 가설 세우기는 hypothesis-framework와 함께 씁니다.

## 범위와 한계

- 문서의 구조와 내용 규칙을 다룹니다. 문장 단위 교정과 비유적 어휘 정리는 [ko-tech-prose](../ko-tech-prose/)와 [plain-korean-doc](../plain-korean-doc/)이 맡습니다.
- 릴리즈 노트, 정책서, ADR(아키텍처 결정 기록), 원페이저는 뺐습니다. 실제로 쓸 일이 거의 없던 양식이라 근거 없이 싣지 않았습니다.
- 한 사람, 몇 개 팀의 요청에서 나왔습니다. 문서 문화가 다른 팀이면 뼈대의 소제목은 바꿔 쓰고 순서만 지키면 됩니다.
- 문서를 쓴 뒤 회의가 실제로 짧아졌는지는 재지 않았습니다.
