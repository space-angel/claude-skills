# plain-korean-doc

한국어 문서를 한 번 읽고 정확히 이해되게 다듬는 스킬입니다.

[SKILL.md](SKILL.md) · [설치](#설치) · 함께 쓰는 스킬: [ko-tech-prose](../ko-tech-prose/) · [po-doc-writing](../po-doc-writing/)

## 구성

plain-korean-doc은 기획서, PRD(제품 요구사항 문서), 레퍼런스, 설명 문서에 다섯 단계를 순서대로 적용합니다. 목표는 문장을 아름답게 만드는 것이 아니라 독자가 한 번에 이해하게 만드는 것입니다.

1. **구조와 서술 순서** — 문서가 놓일 곳에 맞춰 배치를 잡습니다.
2. **참조 문서 원칙** — 원문의 사실·수치·출처를 바꾸지 않습니다. 상관관계를 인과관계로 쓰지 않고, 원문에 없는 분류를 추가하지 않습니다.
3. **용어** — 한 개념에 한 단어를 씁니다. 업계 표현을 우선하고, 약어는 처음에 풀어 씁니다.
4. **비유 제거** — 비유적 어휘를 실제 일어나는 일을 직접 쓰는 단어로 바꿉니다. 대체어 표가 함께 들어 있습니다.
5. **문장** — 성분과 조사를 생략하지 않고, 한 문장에 한 내용만 씁니다. 엠대시와 메타 표현을 쓰지 않습니다.

마지막에 체크리스트로 점검하고 변경 사항을 짧게 정리합니다. 원문에 없던 내용을 넣었다면 그 위치를 알리고 확인을 요청합니다.

## 모드

### 팀 문서

목적 → 문서 정보 표(대상 독자, 알 수 있는 것, 다루지 않는 것, 관련 문서) → 한 문장 요약 → 용어 → 본문 순으로 배치합니다. 독자가 먼저 "이 문서를 지금 읽어야 하는가"를 판단하기 때문입니다.

### 아티클

장면으로 시작하고, 개념은 장면 뒤에 이름을 붙입니다. 기술 블로그 아티클의 서술 순서를 따릅니다.

## 상황별 사용

### 팀 문서 공간에 기획서를 올릴 때

컨플루언스 같은 팀 문서 공간에 올릴 기획서나 PRD를 정리하는 상황입니다.

사용할 모드: 팀 문서

### 비개발자가 읽을 설명 문서가 어렵다는 말을 들었을 때

용어와 비유 때문에 맥락이 없는 독자가 막히는 상황입니다. 문서가 놓일 곳을 모르면 팀 문서로 봅니다.

사용할 모드: 팀 문서

### 기술 블로그 아티클을 다듬을 때

독자가 겪어 봤을 장면으로 시작해 개념에 이름을 붙이는 글을 정리하는 상황입니다.

사용할 모드: 아티클

### 원천 자료에서 문서를 새로 써야 할 때

회의 메모나 이슈를 읽고 기획서나 회의록을 처음부터 쓰는 상황입니다. 내용은 po-doc-writing으로 쓰고, 이 스킬로 읽히는 방식을 다듬습니다.

함께 쓰는 스킬: [po-doc-writing](../po-doc-writing/)

### 문장을 규칙별로 세밀하게 점검할 때

구조는 정리됐고 번역체나 긴 문장 같은 문장 단위 문제만 남은 상황입니다.

함께 쓰는 스킬: [ko-tech-prose](../ko-tech-prose/)

## 가이드라인

### 비유는 일반 어휘로 바꿉니다

"결정이 다른 이슈로 번진다"를 읽으면 독자는 "번진다"가 실제로 무슨 일인지 한 번 더 해석해야 합니다. 비유는 쓰는 사람에게는 생생하지만, 그 해석은 읽는 사람 몫이 됩니다. 단어마다 "사전의 1번 뜻으로 읽어도 문장이 성립하는가"를 확인하고, 성립하지 않으면 바꿉니다.

### 비유 위에 비유를 얹지 않습니다

"병목", "파이프라인" 같은 업계 정착 비유는 무조건 지우지 않습니다. 직접 서술로 바꿀 수 없으면 용어 표에서 정의하고 남깁니다. 다만 같은 비유를 다른 의미로 넓혀 쓰지 않습니다.

### 주체와 성분을 생략하지 않습니다

누가, 무엇을, 언제 하는지 씁니다. 문장 성분을 빼면 독자가 빈자리를 추측해야 합니다.

### 수치를 지어내지 않습니다

모호한 표현은 구체적인 수치와 조건으로 바꿉니다. 원문에 수치가 없으면 만들어 내지 않고, 수치가 필요하다고 표시합니다.

| 지양 | 권장 | 규칙 |
|---|---|---|
| 결정이 다른 이슈로 번진다 | 결정이 다른 이슈에 영향을 준다 | 비유 제거 |
| 병목이 옮겨 간다 | 지연이 발생하는 단계가 바뀐다 | 비유 위에 비유 금지 |
| 그러면 경고가 붙습니다. | 그러면 이미 작업 중인 파일에도 경고 표시가 추가됩니다. | 성분 생략 금지 |
| 파일을 업로드하면 저장됩니다. | 사용자가 파일을 업로드하면 서버에 저장됩니다. | 주체 명시 |
| 데이터가 많으면 느려집니다. | (원문에 수치가 없으면) 수치가 필요하다고 표시 | 수치를 지어내지 않음 |

표의 문장은 가상의 예이며, 각 줄은 `SKILL.md`의 규칙 하나를 보여 줍니다.

## plain-korean-doc vs po-doc-writing

| | plain-korean-doc | po-doc-writing |
|---|---|---|
| 하는 일 | 이미 있는 내용을 한 번에 이해되게 다듬는다 | 원천 자료를 읽고 PM/PO 문서를 새로 쓴다 |
| 중심 | 구조, 용어, 비유 제거, 문장 규칙 | 문서 유형 선택, 문제 → 결정 → 근거 순서 |
| 원문에 없는 내용 | 넣지 않는다. 넣었다면 위치를 알린다 | 재료에서 근거를 찾아 쓴다 |

po-doc-writing이 무엇을 쓸지 정한다면, plain-korean-doc은 쓴 내용이 어떻게 읽히는지를 다룹니다.

## 명세

| 항목 | 내용 |
|---|---|
| 요청 예시 | "이 기획서 다듬어 줘" · "PRD 초안 써 줘" · "컨플루언스에 올릴 문서로 정리해 줘" · "이 설명 문서 읽기 쉽게 고쳐 줘" |
| 입력 | 한국어 문서 원문(기획서, PRD, 레퍼런스, 설명 문서) |
| 출력 | 다듬은 문서, 변경 사항 정리, 원문에 없던 내용의 위치 |
| 사전 준비 | 없음. `SKILL.md`만으로 동작 |
| 외부에 쓰는가 | 쓰지 않습니다 |
| 근거 | 네 가지 출처를 합친 규칙 |

## 근거

규칙은 네 가지 출처를 합쳐 만들었습니다. 각 출처가 맡는 단계는 아래와 같습니다.

| 규칙 | 근거 |
|---|---|
| 참조 문서 원칙 | [technical-writing.dev](https://technical-writing.dev/type/reference.html)의 참조 문서 원칙 |
| 문장 규칙(5단계 "문장") | fluent-korean 출력 스타일(MIT, snflkd)의 한국어 문장 규칙 |
| 아티클 서술 순서 | 기술 블로그 아티클의 서술 순서 |
| 비유 최소화, 팀 문서는 목적을 맨 앞에 | 작성자가 직접 정한 규칙 |

## 설치

```bash
cp -r plain-korean-doc ~/.claude/skills/
```

사전 준비는 없습니다. 스크립트 없이 `SKILL.md`만으로 동작합니다.

## 범위와 한계

- 비유 제거가 기본입니다. 비유가 문체의 일부인 에세이나 마케팅 문구에는 맞지 않습니다.
- 업계 정착 비유는 무조건 지우지 않습니다. 직접 서술로 바꿀 수 없으면 용어 표에서 정의하고 남깁니다.
- 문장 단위 진단을 규칙별로 세밀하게 하려면 [ko-tech-prose](../ko-tech-prose/)가 더 맞습니다. 이 스킬은 구조부터 문장까지 한 번에 다듬는 쪽입니다.
