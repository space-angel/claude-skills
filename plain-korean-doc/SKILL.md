# 한국어 문서 다듬기

이 스킬은 사용자가 한국어 문서를 새로 쓰거나 기존 문서를 정리해 달라고 요청할 때 사용합니다. 목표는 문장을 아름답게 만드는 것이 아니라, 독자가 한 번 읽고 의미를 정확히 이해하게 만드는 것입니다.

이 스킬은 네 가지 출처를 합친 것입니다.

- technical-writing.dev의 참조 문서(reference) 원칙: https://technical-writing.dev/type/reference.html
- fluent-korean 출력 스타일(MIT, snflkd): 명확한 한국어 문장 규칙
- 기술 블로그 아티클의 서술 순서: 장면으로 시작하고, 개념은 장면 뒤에 이름을 붙입니다.
- 사용자가 직접 요구한 사항: 비유적 어휘를 최대한 줄이고, 컨플루언스 문서는 목적을 맨 앞에 둡니다.

각 규칙에 붙은 예시는 규칙이 의도한 동작을 보여 줍니다. 규칙을 요약해서 적용하지 말고, 예시까지 확인한 뒤 적용합니다.

## 작업 순서

1. 원문을 끝까지 읽고, 문서의 목적과 독자를 한 문장으로 정리합니다.
2. 문서가 놓일 곳을 확인합니다. 컨플루언스 같은 팀 문서 공간이라면 0단계 "문서 구조"를 적용하고, 아티클이나 블로그라면 0단계의 "서술 순서"만 적용합니다. 확인할 수 없다면 팀 문서로 간주합니다.
3. 1단계 "참조 문서 원칙"을 적용합니다.
4. 2단계 "용어" 규칙을 적용합니다.
5. 3단계 "비유 제거" 규칙을 적용합니다. 이 단계는 생략하지 않습니다.
6. 4단계 "문장" 규칙을 적용합니다.
7. 5단계 "최종 점검"을 수행합니다. 점검에서 발견한 문제를 고친 뒤에 결과를 출력합니다.
8. 결과 아래에 변경 사항을 짧게 정리합니다. 원문에 없던 내용을 추가했다면, 추가한 위치를 명시하고 사용자에게 확인을 요청합니다.

## 0단계: 문서 구조와 서술 순서

### 팀 문서(컨플루언스 등)의 구조

팀 문서의 독자는 먼저 "이 문서를 지금 읽어야 하는가"를 판단합니다. 그래서 아래 순서로 배치합니다.

1. **제목**: 문서 번호가 있는 문서 묶음이라면 번호를 붙입니다. 번호를 추정했다면 사용자에게 알립니다. [01. 문제 정의: 바뀐 결정 사항을 팀 전체가 제때 알 수 있을까요]
2. **이 문서의 목적**: 이 문서가 무엇을 정의하거나 설명하는지, 그리고 다른 문서와 어떤 관계인지 두 문장 이내로 씁니다. [이 문서는 이 서비스가 어떤 문제를 왜 풀려고 하는지 정의해요. 이후 문서의 기능, 규칙, 가설은 모두 이 문서의 문제를 기준으로 해요.]
3. **문서 정보 표**: 아래 네 항목을 표로 정리합니다.

   | 항목 | 내용 |
   |---|---|
   | 대상 독자 | 이 문서를 읽어야 하는 사람 |
   | 읽고 나면 알 수 있는 것 | 번호를 붙여서 2~4개 |
   | 다루지 않는 것 | 독자가 이 문서에서 찾지 않아야 할 내용 |
   | 관련 문서 | 다루지 않는 내용이 있는 문서 |

   "다루지 않는 것"은 생략하지 않습니다. 이 항목이 있으면 독자가 엉뚱한 내용을 이 문서에서 찾지 않고 관련 문서로 이동합니다.
4. **한 문장 요약**: 본문의 결론을 한 문장으로 씁니다. 길어지면 두 문장까지 허용합니다.
5. **용어**: 문서에서 반복해서 쓰는 개념을 표로 정의합니다. 팀 문서는 중간부터 읽는 사람이 많으므로, 용어는 본문보다 먼저 둡니다.
6. **본문**: 장 제목에 번호를 붙이고, 아래 "서술 순서"를 따릅니다.

### 서술 순서 (아티클 방식)

1. **장면으로 시작합니다.** 본문의 첫 장은 독자가 겪어 봤을 구체적인 장면 하나로 시작합니다. 누가, 언제, 무엇을 했고, 그 결과 무슨 문제가 생겼는지 씁니다. [화요일에 백엔드 개발자가 `coupon` 필드를 비어 있어도 되는 값으로 바꿨어요. … 이 차이는 금요일 QA에서 발견됐어요.] 장면을 만들어 냈다면 "문제를 설명하기 위해 만든 예시예요"라고 표시하고, 실제 사례로 바꾸도록 사용자에게 제안합니다.
2. **원인이 사람이 아니라 구조에 있다면 그렇게 씁니다.** [누구도 실수하지 않았어요. 문제는 바뀐 내용이 영향을 받는 사람에게 전달되지 않았다는 점이에요.]
3. **개념은 장면을 보여 준 뒤에 이름을 붙입니다.** 현상을 먼저 설명하고, 그다음에 "이 작업을 ○○라고 불러요"라고 소개합니다. 단, 팀 문서에서는 용어 표에도 미리 정의합니다.
4. **문제에서 해결 방향 순서로 진행합니다.** 장면 → 현상 → 기존 방법의 한계 → 원인 → 해결 방향 → 범위 순서를 기본으로 합니다.
5. **장 제목은 결론 문장으로 씁니다.** 제목만 이어 읽어도 문서의 주장을 알 수 있어야 합니다. [원인 분석 → 에이전트가 늘수록 사람이 확인하는 단계에서 작업이 지연돼요]
6. **처음 읽을 내용은 문단으로, 다시 찾을 내용은 표로 씁니다.** 아티클에서는 문단을 우선하고, 팀 문서에서는 원인 목록, 역할별 정리, 근거처럼 나중에 다시 찾아볼 정보를 표로 정리합니다.
7. **문체는 문서가 놓일 곳에 맞춥니다.** 아티클과 사용자가 해요체를 원한 팀 문서는 해요체로, 그 외에는 합니다체로 씁니다. 한 문서 안에서는 문체를 섞지 않습니다.

## 1단계: 참조 문서 원칙

1. **정확하고 완전하게 씁니다.** 원문의 사실, 수치, 출처를 바꾸지 않습니다. 상관관계를 인과관계처럼 쓰지 않습니다. [441% 늘었어요. → 441% 늘었어요. 이 수치는 상관관계이고, 인과관계는 확인되지 않았어요.]
2. **근거의 수준을 표시합니다.** 문서 근거, 작성자 추론, 검증 필요를 구분해서 적습니다.
3. **구조를 일관되게 유지합니다.** 같은 수준의 항목은 같은 형식을 따릅니다. 예를 들어 표의 행이 여러 개라면 모든 행의 문장 끝을 같은 형태로 맞춥니다. [역할 표의 오른쪽 열을 모두 "~할 수 있어요"로 맞춥니다.]
4. **찾기 쉽게 만듭니다.** 문서가 길면 목차와 앵커 링크를 추가합니다. 제목은 30자 이내로 쓰고, 핵심 키워드를 포함합니다.
5. **한 문서에서는 한 주제만 다룹니다.** 다른 주제는 관련 문서로 연결합니다.
6. **예시를 제공합니다.** 규칙이나 개념을 설명했다면, 실제 상황 하나를 예시로 보여 줍니다. 원문에 예시가 없다면 예시 추가를 제안합니다.
7. **가치를 먼저 씁니다.** 독자가 이 문서나 기능으로 무엇을 할 수 있는지를 배경 설명보다 먼저 씁니다.
8. **원문에 근거가 없는 내용은 추가하지 않습니다.** 정리하다가 원문에 없는 분류나 대응 관계를 만들었다면, 빼거나 사용자에게 확인을 요청합니다.

## 2단계: 용어

1. **한 개념에는 한 단어만 씁니다.** ["결정", "기준", "스펙"이 섞여 있다면 하나로 통일합니다. "티켓"과 "이슈"를 섞어 쓴다면 "이슈"로 통일하고, 용어 표에 "티켓과 같은 의미"라고 적습니다.]
2. **업계에서 쓰는 표현을 우선합니다.** 문서가 직접 만든 표현보다 업계에서 이미 쓰는 표현을 고릅니다. [바뀐 결정이 어떤 이슈에 영향을 주는지 찾는 작업 → 변경 영향 분석(Change Impact Analysis)]
3. **추상적인 용어는 덜 추상적인 형태로 씁니다.** [결정 → 결정 사항] 단어만 보고 범위가 떠오르지 않는다면, 회의록이나 현업에서 더 자주 쓰는 형태를 고릅니다.
4. **넓은 범위의 용어는 예시로 범위를 보여 줍니다.** 정의 문장 아래에 역할이나 상황별 예시를 3~5개 붙입니다. [결정 사항: 기획 "비회원도 장바구니를 사용할 수 있다", 백엔드 "주문 API의 `coupon` 필드는 비어 있을 수 있다", QA "결제 실패 시 재시도는 3회까지 테스트한다"]
5. **약어는 처음 나올 때 풀어 씁니다.** [PR → PR(Pull Request)]
6. **프로젝트 고유 용어는 두 단계로 소개합니다.** 문제를 처음 접하는 독자가 읽는 부분에서는 통상 표현을 쓰고, 기능을 설명하는 부분에서 고유 용어를 정의한 뒤 사용합니다.

## 3단계: 비유 제거

비유적 어휘는 글쓴이에게는 생생하게 느껴지지만, 독자는 비유를 실제 의미로 다시 번역해야 합니다. 이 과정에서 의미가 달라지기 쉽습니다. 따라서 이 스킬에서는 일반 어휘로 바꿀 수 있는 비유는 모두 바꿉니다.

### 판단 기준

문장 안의 동사와 명사마다 다음 질문을 확인합니다.

- 이 단어를 사전의 1번 뜻(물리적이고 직접적인 뜻)으로 읽어도 문장이 성립하는가?
- 성립하지 않는다면 비유입니다. 그 자리에 실제로 일어나는 일을 직접 쓰는 단어로 바꿉니다.

["결정이 다른 이슈로 번진다": 결정은 불이나 물이 아니므로 "번지다"의 1번 뜻이 성립하지 않습니다. → "결정이 다른 이슈에 영향을 준다"]

### 자주 나오는 비유와 대체어

| 비유 표현 | 대체 표현 |
|---|---|
| 흘러가다, 흐름 | 진행되다, 순서, 진행 방향 |
| 쌓이다 (결과물, 알림이) | 늘어나다, 처리되지 않은 채 남다 |
| 번지다, 퍼지다 | 영향을 주다, 전달되다 |
| 묶다, 묶어서 보여 주다 | 하나의 단위로 정리하다, 함께 표시하다 |
| 붙이다 (이유를) | 함께 표시하다, 함께 기록하다 |
| 뒤지다 | 찾아보다, 직접 확인하다 |
| 칸 | 필드, 항목 |
| 기대다 (기준에) | 근거로 삼다, 따르다 |
| 갈리다 (추정이) | 다르게 나오다 |
| 박다, 얹다, 꽂다, 치우다 | 명시하다, 추가하다, 연결하다, 제거하다 |
| 흐름을 끊다, 막히다 | 작업이 중단되다, 진행되지 않다 |
| 자리 ("정책이 갈리는 자리") | 상황, 단계, 시점 |
| 대기열 (사람 일에 쓸 때) | 확인해야 할 항목 목록 |
| 자원 (주의력, 시간에 쓸 때) | 그대로 "주의력", "시간"이라고 씁니다 |
| 손을 타다, 손이 가다 | 사람이 직접 처리하다 |
| 놓치다 | 확인하지 못하다 |
| 녹아 있다, 담다 (의미를) | 포함하다, 기록하다 |
| 뼈대, 골격 | 구조, 목차 |
| 연쇄적으로 | 차례로 |
| 여지 ("추측할 여지") | 추측해야 하는 내용 |

### 업계 용어로 정착된 비유

"병목", "파이프라인", "대기열"처럼 업계에서 정착된 비유 용어는 다음 순서로 처리합니다.

1. 문서 전체에서 그 용어 없이 설명할 수 있는지 먼저 확인합니다. 가능하면 직접 서술로 바꿉니다. [병목 → 작업 전체를 지연시키는 단계, 입력 병목 → 불명확한 이슈]
2. 용어를 꼭 유지해야 한다면(원문의 핵심 키워드이거나 제목에 쓰인 경우), 용어 표에서 실제 의미로 정의하고, 본문에서는 정의한 의미로만 사용합니다.
3. 같은 비유를 다른 의미로 확장하지 않습니다. ["병목이 옮겨 간다", "병목을 키운다"처럼 비유 위에 다시 비유를 얹지 않습니다. → "지연이 발생하는 단계가 바뀐다", "확인할 항목이 늘어난다"]

## 4단계: 문장 (fluent-korean 규칙)

1. **의미가 있는 문장 성분을 생략하지 않습니다.** [그러면 경고가 붙습니다. → 그러면 이미 작업 중인 파일에도 경고 표시가 추가됩니다.] 관형격 조사 "~의"를 반복하면 성분이 빠지기 쉽습니다. [사본의 문구는 작업의 상황을 → 사본에 기재된 문구는 작업이 진행되는 상황을]
2. **문장을 완성된 형태로 끝맺습니다.** 명사구, 부사구, 연결어미로 문장을 끝내지 않습니다. 단, 제목과 목록, 표 안의 짧은 항목에는 이 규칙을 강제하지 않습니다.
3. **조사와 어미를 생략하지 않습니다.** 부사, 보조사, 선어말어미, 보조 용언을 활용해서 관계를 분명히 합니다. [이 결정은 이후 중요 정책이 갈리는 자리. → 이 결정은 이후 중요한 정책에 계속 영향을 주기 때문에 신중하게 반영합니다.]
4. **맥락에 맞는 한자어에 조사와 어미를 붙여서 씁니다.** 한자어만 나열하지 않습니다. [지출 비용 추론 용도의 토큰 카운트 함수의 오류 상황에서 → 지출한 비용을 추론하는 토큰 카운트 함수에 오류가 발생하면]
5. **잘 쓰이지 않는 어휘를 피합니다.** 사전에 있는 단어라도 실제로 잘 쓰이지 않으면, 의미가 같고 자주 쓰이는 단어로 바꿉니다.
6. **엠대시(—)를 쓰지 않습니다.** 앞뒤 관계에 따라 콜론이나 접속사로 바꿉니다.
7. **한 문장에는 하나의 내용만 씁니다.** 문장이 "~하며, ~하고, ~해서"로 길게 이어지면 나눕니다.
8. **주체를 분명히 씁니다.** 누가, 무엇을, 언제 하는지 씁니다. [파일을 업로드하면 저장됩니다. → 사용자가 파일을 업로드하면 서버에 저장됩니다.]
9. **모호한 표현 대신 구체적인 수치와 조건을 씁니다.** [데이터가 많으면 느려집니다. → 데이터가 10,000건을 넘으면 응답 시간이 1초 이상 걸립니다.] 원문에 수치가 없다면 수치를 만들어 내지 말고, 수치가 필요하다고 표시합니다.
10. **메타 표현을 지웁니다.** "앞에서 설명했듯이", "결론적으로", "아시다시피" 같은 표현을 제거합니다.
11. **고유 명사와 기술 용어는 정착된 표기를 따릅니다.** 정착된 번역어나 음차가 없으면 원어를 유지합니다. 코드, 변수명, 인용문에는 이 규칙들을 적용하지 않습니다.
