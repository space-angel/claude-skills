# 실험 설계 (MAKER 3. 가설 수립 및 실험)

가설을 "무엇으로, 누구에게, 얼마나 오래, 어떤 숫자가 나오면 맞다고 볼지"가 정해진 실험 계획으로 바꾼다. 판정 기준은 실험 전에 고정한다. 결과를 본 뒤에 기준을 정하면 어떤 결과든 성공으로 읽힌다.

## 전제

- **가설은 이 스킬이 세우지 않는다.** 가설이 없거나 근거가 흔들리면 `hypothesis-framework`로 먼저 세운다. 이 스킬은 받은 가설이 실험에 필요한 칸을 다 갖췄는지 확인하고 구조만 맞춘다.
- **통일된 가설 문장**: "만약 [대상]에게 [변화]를 주면, [지표]가 [기간] 안에 [크기]만큼 바뀔 것이다. 왜냐하면 [근거]." 유형은 문제 / 솔루션 / 성장 / 가치 네 가지다(지불 의사는 가치 가설).
- **지표 개수**: 북극성 지표 1개, 주요 지표 1~2개, 가드레일 지표 1~3개.
- **역할**: DACI(Driver / Approver / Contributors / Informed).
- **대화**: 빠진 정보는 한 번에 하나씩, 가능하면 선택지로 묻는다. 모르는 값은 추측으로 채우지 않고 `[확인 필요: …]`로 남긴다. 기준값, 트래픽, 목표치는 사용자에게서만 받는다.
- **저장**: 산출물은 `experiment-<주제>.md`로 저장하고 경로를 알린다. 노션 등록은 승인을 받은 뒤 `notion-ops`로 한다.
- **사례**: 아래 예시는 모두 가상의 예약 앱 "예약 시간 변경" 기능이다. 변경 기능이 없어 취소 후 재예약하는 사용자가 많고, 그중 일부가 재예약하지 않고 이탈한다. 숫자는 가상의 예다.

## 입력 계약

| 받는 것 | 보내는 곳 | 이 스킬이 하는 일 |
|---|---|---|
| 가설 문장(`hypothesis-framework` 출력) | 1. 가설 점검 | 칸 확인 후 바로 방식 고르기로 |
| HMW / 문제 진술문(`maker-problem-framing` 출력) | 캔버스 1번 칸 | 가설이 없으므로 `hypothesis-framework`로 넘긴 뒤 돌아온다 |
| MVP 범위, Must 목록(`maker-prioritization` 출력) | 4. MVP 실험 | 범위를 그대로 받고, 검증할 가설을 묻는다 |
| 이미 끝난 실험 결과 | 7. 결과 판정 | 사전 판정 기준이 있는지부터 본다 |

## 출력 계약

`실험 계획서(캔버스 1~8칸) + 지표 정의서 + 판정 기준` 세 가지를 한 파일로 낸다. 실험 후에는 캔버스 9칸과 판정 결과를 덧붙인다. `po-doc-writing`의 검증형 기획서는 이 파일을 그대로 받는다.

| 검증형 기획서 | 이 스킬의 산출물 |
|---|---|
| 문제 | 캔버스 1칸 |
| 가설 | 캔버스 2칸 |
| 검증 방법 | 캔버스 3·4칸 |
| 판정 기준 | 판정 기준 표 |
| 대안 가설 | 캔버스 7칸(가설이 틀렸을 때의 설명) |
| 리스크 → 다음 단계 | 캔버스 7칸, 판정별 다음 행동 |

## 모듈 고르기

| 상황 | 흐름 |
|---|---|
| 가설은 있고, 어떻게 검증할지 모름 | 1 → 2 → (3 또는 4) → 5 → 6 |
| UI·문구·흐름 변경의 효과를 보고 싶음, 트래픽 충분 | 1 → 3 → 5 → 6 |
| 새 기능·새 사업 모델, 만들기 전에 반응부터 | 1 → 2 → 4 → 5 → 6 |
| 사용자 행동을 바꾸려는 실험 | 1 → 3 → 5(행동 지표를 주요 지표로) → 6 |
| 여러 사람이 걸린 복잡한 실험, 한 장으로 공유 | 6에서 시작해 빈 칸마다 해당 모듈로 |
| 실험이 끝남 | 7 |
| 가설이 없음, 문제 진술문만 있음 | `hypothesis-framework` 먼저 |

## 1. 가설 점검

**목적**: 받은 가설이 실험에 필요한 칸을 다 가졌는지 본다. 코칭하지 않는다.
**언제**: 모든 흐름의 첫 단계.
**입력**: 가설 문장.

**절차**
1. 가설이 없으면 멈추고 `hypothesis-framework`를 제안한다. 여기서 대신 세우지 않는다.
2. 있으면 아래 표로 쪼갠다. 빈 칸은 `[확인 필요]`로 둔다. `hypothesis-framework`의 `[미확보]`도 같은 뜻으로 받는다. 그 출력에서 옮기는 곳: 변화(What) → 변화, 예상 결과(Result) → 지표, 영향(Impact) → 크기, 근거·반증 조건 → 그대로, 유형 → 게이트 0의 판정, 대상 → 변화·결과 문장이나 문제 정의서에서 분리. 그쪽의 "검증 기간"은 판정 기한이고, 여기의 [기간]은 지표가 바뀌는 관찰 창(예: 7일 뒤)이다. 섞지 않는다.
3. 빈 칸이 [변화]나 [근거]이면 `hypothesis-framework`로 돌려보낸다. [지표]·[기간]·[크기]만 비었으면 3·5 모듈에서 채운다.
4. 변화가 두 개 이상이면 "나눌지, 묶어서 패키지 효과만 볼지"를 묻는다. 묶으면 원인을 분리할 수 없다고 캔버스 7칸에 적는다.
5. "어떤 숫자가 나오면 틀렸다고 보는가"가 없으면 한 줄로 묻는다. 답은 판정 기준의 기각 조건이 된다.

```
| 칸 | 내용 |
|---|---|
| 유형 | 문제 / 솔루션 / 성장 / 가치 |
| 대상 | 예약 취소 화면에 들어온 사용자 |
| 변화 | 취소 대신 "시간 변경" 버튼을 보여 준다 |
| 지표 | 7일 뒤 예약 유지율 |
| 기간 | [확인 필요: 실험 기간] |
| 크기 | 60% → 66% (가상의 예) |
| 근거 | 취소 후 재예약 로그, CS 문의 분류 (출처 등급은 hypothesis-framework 결과를 그대로 옮긴다) |
| 반증 조건 | 유지율 차이가 +2%p 미만이면 기각 |
```

**유의**: 근거 등급을 다시 매기거나 대안 가설을 새로 짜지 않는다. 그건 `hypothesis-framework` 몫이다.
**다음**: 2. 실험 방식 고르기.

## 2. 실험 방식 고르기

**목적**: 가설을 가장 싸게, 되돌릴 수 있게 검증하는 방식을 고른다. A/B가 늘 답은 아니다.
**언제**: 방식이 정해지지 않았을 때.
**입력**: 점검한 가설, 하루 대상자 수, 구현 비용, 실패했을 때의 피해.

**절차**: 아래 세 가지를 하나씩 묻고 표에서 고른다.
1. "이 실험 대상이 되는 사용자가 하루에 몇 명인가?" (모르면 `[확인 필요]`, A/B는 보류)
2. "실패하면 사용자나 매출에 어떤 피해가 있나?" (없음 / 되돌릴 수 있음 / 되돌리기 어려움)
3. "지금 검증하려는 게 원인, 관심, 효과 중 무엇인가?"

| 방식 | 무엇을 검증하나 | 트래픽 | 리스크 | 되돌리기 | 비용 | 맞는 가설 |
|---|---|---|---|---|---|---|
| 인터뷰·관찰 | 문제가 있는지, 왜 그런지 | 5~10명이면 충분 | 낮음 | 쉬움 | 낮음 | 문제 |
| 페이퍼·클릭 프로토타입 테스트 | 흐름을 이해하고 끝까지 가는지 | 5~10명 | 낮음 | 쉬움 | 낮음 | 솔루션(사용성) |
| 페이크도어 | 기능에 관심이 있는지(클릭) | 중간 | 기대를 깨는 경험 | 쉬움 | 매우 낮음 | 가치·솔루션 수요 |
| 랜딩 페이지 | 가치 제안·가격에 반응하는지 | 유입 확보 필요 | 낮음 | 쉬움 | 낮음 | 가치 |
| 컨시어지 | 사람이 해 줘도 쓰는지, 니즈가 무엇인지 | 소수 | 운영 부담 | 쉬움 | 사람 시간 | 가치·문제 |
| 위저드 오브 오즈 | 완성품처럼 보일 때 쓰는지 | 소수~중간 | 운영 실수 | 쉬움 | 중간 | 솔루션·가치 |
| 단일 기능 MVP | 핵심 기능 하나로 행동이 바뀌는지 | 중간 | 중간 | 기능 플래그면 쉬움 | 중간~높음 | 솔루션·가치 |
| A/B 테스트 | 변화가 지표를 얼마나 움직이는지(인과) | 많음(3. 공식으로 확인) | 노출 범위만큼 | 기능 플래그면 쉬움 | 중간 | 솔루션·성장 |

**고르는 규칙**
- 원인을 아직 모르면(문제 가설) A/B로 가지 않는다. 인터뷰·관찰부터 한다.
- 3. 공식으로 계산한 기간이 6주를 넘으면 A/B 대신 MVP 방식이나 더 큰 변화(MDE를 키움)를 고른다.
- 되돌리기 어려운 변화(가격 인상, 데이터 삭제, 정책 변경)는 소수 대상 방식부터 하고 A/B는 노출 비율을 작게 시작한다.
- 페이크도어는 클릭 뒤에 "준비 중" 안내와 대안(예: 알림 신청)을 반드시 둔다.

**산출물**
```
## 실험 방식
- 선택: A/B 테스트
- 이유: 하루 대상자 약 150명(가상의 예), 기능 플래그로 즉시 끌 수 있음, 효과 크기를 알아야 출시 판단 가능
- 버린 대안: 페이크도어(관심은 CS 문의로 이미 확인됨)
```
**다음**: A/B면 3, 나머지는 4.

## 3. A/B 테스트 설계

**목적**: 대조군과 실험군을 무작위로 나눠 변화의 효과를 통계적으로 판정할 수 있게 설계한다.
**언제**: 2에서 A/B를 골랐을 때.
**입력**: 가설, 주요 지표의 현재값(p), 감지하려는 최소 차이(MDE, δ), 하루 대상자 수.

**절차**
1. **변형 정의**: 대조군(현행)과 실험군을 한 줄씩. 바꾸는 변수는 하나. 화면이나 명세를 링크한다.
2. **대상과 할당**: 포함·제외 조건, 무작위 단위(사용자 ID, 기기 간 오염 방지), 비율(기본 50:50).
3. **표본 크기**: 비율 지표 두 개를 비교할 때 그룹당 n.
   - 어림식(α=0.05 양측, 검정력 80%): **n ≈ 16 · p(1−p) / δ²**
   - 정식: n = [ z₁₋α/₂ · √(2p̄(1−p̄)) + z₁₋β · √(p₁(1−p₁) + p₂(1−p₂)) ]² / (p₂ − p₁)², p̄ = (p₁+p₂)/2, z₁₋α/₂ = 1.96, z₁₋β = 0.84
   - δ는 절대 차이(%p)다. 상대 변화(+10%)로 받으면 절대값으로 바꿔 계산한다.
   - 주요 지표가 2개이거나 실험군이 2개 이상이면 α를 비교 횟수로 나눈다(본페로니). n이 커진다.
   - 평균 지표(체류 시간, 객단가)는 n ≈ 16 · σ² / δ² 를 쓴다. σ는 현재 데이터의 표준편차다.
4. **기간**: 모집 기간 = 2n ÷ 하루 대상자 수, 올림해서 **주 단위로 맞추고 최소 1주(요일 주기 한 바퀴)**. 모집 기간이 6주를 넘으면 2로 돌아간다.
   - 하루 대상자는 변화를 실제로 겪는 사용자 수다. 가입 시 할당하고 특정 상황(트리거)에서만 변화가 보이면 트리거된 사용자 수로 나누고, 분석도 트리거된 사용자로 한다.
   - 비율이 50:50이 아니면 작은 그룹이 n을 채우는 날로 잡는다.
   - 지표에 관찰 창(7일 뒤 유지율의 7일 등)이 있으면 판정 시점은 마지막 진입자의 창이 닫힌 뒤다.
5. **멈춤 규칙**: 정한 기간과 n이 차기 전에는 결과를 보고 멈추지 않는다(peeking 금지). 일찍 멈추는 경우는 둘뿐이다. 가드레일이 미리 정한 선을 넘을 때, 그리고 할당 비율이 계획과 어긋날 때(SRM, 표본 비율 불일치 — 버그 신호).
6. **가드레일**: 5에서 1~3개를 받아 각각 "이 선을 넘으면 중단"을 적는다.
7. **사전 점검**: 가능하면 A/A 테스트로 할당과 수집이 맞는지 본다. 시즌·캠페인 기간은 피하거나 기록한다. 첫 며칠의 신기함 효과는 판정에서 따로 본다.

**산출물**
```
## A/B 설계
| 항목 | 내용 |
|---|---|
| 대조군 | 취소 화면 현행 (취소 → 재예약) |
| 실험군 | 취소 화면 상단에 "시간 변경" 버튼 |
| 대상 / 단위 | 취소 화면 진입 사용자 / 사용자 ID |
| 할당 | 50:50 |
| 주요 지표 기준값 p | 60% (가상의 예) |
| MDE δ | +6%p (60% → 66%) |
| 표본 | 어림식 16·0.6·0.4/0.06² ≈ 1,067명, 정식 ≈ 1,015명 → 그룹당 1,070명 |
| 하루 대상자 | 150명 (가상의 예) |
| 기간 | 2,140 ÷ 150 ≈ 15일 → 3주 모집(주 단위 올림), 판정은 마지막 진입자의 7일 뒤 |
| 가드레일 | 업장 측 변경 거절률 > 15%, 변경 관련 CS 문의 > 주 30건이면 중단 |
| 멈춤 규칙 | 3주·그룹당 1,070명 전에는 판정하지 않음 |
```
**유의**: 정식 공식과 어림식이 다르게 나오면 큰 쪽을 쓴다. 표본 계산기를 써도 되지만 입력값 네 개(p, δ, α, 검정력)를 계획서에 남긴다.
**다음**: 5. 측정 지표 설계.

## 4. MVP 실험 설계

**목적**: 다 만들기 전에 최소 구현으로 핵심 가설을 검증하고 확장 / 피봇 / 종료를 정한다.
**언제**: 2에서 A/B 외 방식을 골랐을 때.
**입력**: 가설, MVP 범위(`maker-prioritization`의 Must 목록). 범위가 없으면 `maker-prioritization`을 제안하거나, 사용자가 원하면 "이 실험에 꼭 필요한 것"만 함께 적고 `[확인 필요: 우선순위 합의]`를 단다.

**절차**
1. 검증할 가설을 한 개(최대 세 개, 번호를 붙인다) 고른다.
2. 방식(2의 표)과 구현 수단(직접 개발 / 프로토타입 / 수동 운영)을 정한다. Must가 아닌 기능은 넣지 않는다.
3. 대상과 모집 방법, 인원, 기간을 정한다.
4. 지표는 5에서 받는다. 인터뷰나 설문보다 실제 행동(클릭, 신청, 재사용)을 주요 지표로 둔다.
5. 판정 기준을 정한다. 표본이 작아 통계 검정을 하지 않는 방식은 "N명 중 M명" 같은 문턱값을 미리 쓴다.
6. 내부 파일럿(팀원 몇 명)으로 흐름이 끝까지 도는지 먼저 확인한다.

**산출물**
```
## MVP 실험
- 가설 1: 변경 버튼이 있으면 취소 대신 변경을 고른다
- 방식: 위저드 오브 오즈 (변경 요청을 받아 운영자가 업장과 수동 조율)
- 포함(Must): 변경 버튼, 희망 시간 선택, 완료 알림
- 제외: 자동 빈자리 조회, 업장용 승인 화면
- 대상 / 기간: 한 지역 업장 20곳의 취소 화면 진입자 / 2주
- 문턱값: 진입자 중 20% 이상이 변경 요청, 요청의 70% 이상이 48시간 안에 확정 (가상의 예)
```
**유의**: 완벽함보다 검증이다. 수동 운영은 감당할 수 있는 인원 상한을 미리 정한다.
**다음**: 5. 측정 지표 설계.

## 5. 측정 지표 설계

**목적**: 판정에 쓸 지표를 역할별로 고르고, 누가 봐도 같은 값이 나오게 정의한다.
**언제**: 3·4 다음, 또는 지표만 따로 정할 때.
**입력**: 가설, 실험 방식, 지금 수집 중인 이벤트.

| 역할 | 개수 | 뜻 | 예약 앱 예 |
|---|---|---|---|
| 북극성 지표 | 1 | 제품의 장기 가치. 실험 하나로 크게 안 움직여도 방향만 맞으면 된다 | 주간 방문 완료 예약 수 |
| 주요 지표 | 1~2 | 이 실험의 채택·기각을 정하는 지표. 가설의 [지표] | 취소 화면 진입자의 7일 뒤 예약 유지율 |
| 가드레일 지표 | 1~3 | 나빠지면 안 되는 것. 선을 넘으면 중단 | 업장 측 변경 거절률, 변경 관련 CS 문의 수, 앱 오류율 |
| 진단 지표 | 제한 없음 | 왜 움직였는지 설명용. 판정에 쓰지 않는다 | 변경 완료까지 걸린 시간, 버튼 클릭률 |

**절차**
1. 목표를 한 문장으로 묻는다. "이 실험이 성공하면 무엇이 달라지나?"
2. 주요 지표를 고른다. 기준: 변화와 직접 연결 / 노출이 아니라 행동 결과 / 비율이나 사용자당 값(누적 합계 대신) / 팀이 조작하기 어려움 / 실험 기간 안에 움직임.
3. 가드레일을 고른다. 품질(오류율, 로딩), 상대편(업장, 판매자), 비용(CS 문의)에서 하나씩 후보를 보고 1~3개.
4. 각 지표를 정의서로 쓴다. 계산식의 분자·분모를 빠짐없이 쓴다.
5. 필요한 이벤트가 없으면 이벤트 스펙을 쓰고 "개발 선행"으로 캔버스 5칸에 올린다.

**산출물 — 지표 정의서**
```
| 항목 | 주요 지표 |
|---|---|
| 지표명 | 7일 예약 유지율 |
| 역할 | 주요 (판정용) |
| 정의 | 취소 화면에 들어온 사용자 중 7일 뒤에도 같은 업장 예약이 있는 비율 |
| 계산식 | 분자: 진입 후 7일 시점 활성 예약 보유 사용자 수 / 분모: 취소 화면 진입 사용자 수 |
| 좋아지는 방향 | 높을수록 |
| 단위 / 집계 | % / 사용자 단위, 일별 |
| 데이터 소스 | cancel_view, booking_changed, booking_canceled 이벤트 |
| 세그먼트 | 신규·기존, 업종 |
| 기준값 | 60% (가상의 예, 최근 4주) |
| 목표값 / 기한 | 66% / 실험 종료 시 |
| 책임자 | [확인 필요] |
| 대시보드 | [확인 필요] |

| 이벤트명 | 설명 | 프로퍼티 |
|---|---|---|
| booking_changed | 예약 시간 변경 완료 | booking_id, from_time, to_time, variant |
```
**유의**: 지표가 늘면 판정이 흐려진다. 주요 지표가 둘이면 둘 다 좋아야 채택인지, 하나만이어도 되는지 미리 정한다. 누적 다운로드, 페이지뷰 같은 허영 지표는 주요 지표로 쓰지 않는다.
**다음**: 6. 실험 캔버스.

## 6. 실험 캔버스

**목적**: 실험의 모든 요소를 한 장 9칸에 모아 팀이 같은 그림을 보게 한다. 이 스킬의 최종 산출물이다.
**언제**: 1~5의 결과를 묶을 때, 또는 여러 사람이 걸린 실험을 처음부터 한 장으로 잡을 때.
**입력**: 1~5의 산출물. 비어 있는 칸은 해당 모듈로 돌아가 채운다.

**절차**: 1→8칸은 실험 전에 채우고, 9칸은 실험 후에 채운다. 진행 중 배운 것은 바로 반영하고 날짜를 단다.

```
# 실험 계획서: <주제>  (작성일 / 버전)

1. 문제 정의 — 관찰된 현상, 현재 지표, 영향. (문제 진술문을 그대로)
2. 가설 — 통일 문장 한 줄 + 유형 + 반증 조건
3. 대상 사용자 — 세그먼트, 포함·제외 조건, 최소 표본, 모집·할당 방법
4. 실험 설계 — 방식과 고른 이유, 대조군·실험군, 바꾸는 변수 / 고정하는 변수, 기간, 제한 사항
5. 구현 계획 — 할 일과 완료 기준(시간순), 의존성(이벤트 개발 등)
   DACI: Driver [ ] / Approver [ ] / Contributors [ ] / Informed [ ]
6. 성공 지표 — 북극성 1 / 주요 1~2 / 가드레일 1~3 (지표 정의서 첨부)
7. 리스크·가정 — 가정, 리스크(심각도×가능성, 완화책), 외부 변수(시즌·캠페인),
   가설이 틀렸을 때의 다른 설명
8. 분석 계획 — 분석 방법(비율 비교는 두 비율 z검정 또는 카이제곱), 유의수준,
   세그먼트 분석, 멈춤 규칙, 판정 기준 표
9. 결과·교훈 (실험 후) — 지표 결과, 판정, 예상 밖 발견, 다음 가설, 다음 행동
```

**판정 기준 표(8칸에 넣는다)**
```
| 판정 | 조건 (실험 전에 고정) | 다음 행동 |
|---|---|---|
| 채택 | 주요 지표가 좋아지는 방향으로 유의(p<0.05, 신뢰구간 전체가 개선 쪽)하고 점추정이 MDE 이상, 가드레일 모두 선 안 | 전체 출시 / MVP는 확장 |
| 기각 | 계획한 표본을 채웠고 1의 반증 조건에 해당(반증 조건이 없으면 신뢰구간 안에 MDE가 들지 않음), 또는 가드레일 위반 | 접고 다른 설명(7칸)으로 새 가설 |
| 보류 | 표본 미달, SRM, 외부 변수 발생, 또는 채택·기각 어디에도 들지 않음(유의하지만 MDE 미만 등) | 원인 수정 후 재실험, 효과 크기로 출시 가치 따로 판단, 또는 피봇 검토 |
```
**유의**: 한 장을 넘기지 않는다. 지표 정의서와 A/B 계산은 부록으로 붙인다. 비슷한 지난 캔버스가 있으면 먼저 찾아 본다.
**다음**: 저장 후 `po-doc-writing`(검증형 기획서)으로 넘길지 묻는다. 실험이 끝나면 7.

## 7. 결과 판정

**목적**: 미리 정한 기준대로 판정하고 9칸을 채운다.
**입력**: 실험 결과(지표별 대조군·실험군 값, 표본, 기간), 캔버스.

**절차**
1. 사전 판정 기준이 없으면 "이번 판정은 사후 기준이라 확증으로 쓸 수 없다"고 적고 진행한다.
2. 표본과 기간이 계획대로 찼는지, SRM이 없는지 먼저 본다.
3. 지표 표를 채운다. 계산한 p값·신뢰구간이 없으면 `[확인 필요]`로 두고 판정하지 않는다.
4. 판정 기준 표에 대어 채택 / 기각 / 보류 중 하나를 고른다. 세그먼트 결과는 진단으로만 쓴다.
5. 다음 가설과 다음 행동을 적는다.

```
| 지표 | 역할 | 대조군 | 실험군 | 차이 | 95% 신뢰구간 | p | 기준 충족 |
|---|---|---|---|---|---|---|---|
판정: 채택 / 기각 / 보류 — 근거 한 줄
예상 밖 발견:
다음 가설:
```
**유의**: 결과가 좋게 나와도 기준을 바꾸지 않는다. 실패한 실험도 9칸을 채워 남긴다.
**다음**: 회고는 `evidence-based-retro`, 팀 공유는 `slack-team-post`나 `team-status-report`, 결정 기록은 `po-doc-writing`.

## 하지 않는 것

- 가설을 대신 세우거나 근거 등급을 매기지 않는다(`hypothesis-framework`).
- 기준값, 트래픽, 목표치, p값을 지어내지 않는다. 예시 숫자를 사용자 실험에 옮겨 쓰지 않는다.
- 결과를 본 뒤 판정 기준이나 주요 지표를 바꾸지 않는다.
- 실험 도구 설정, 이벤트 코드 구현, 노션 등록을 승인 없이 하지 않는다.
- 실제 회사 사례나 출처 없는 성과 수치를 근거로 들지 않는다.
