# maker-experiment-design

세운 가설을 방식·표본·기간·지표·판정 기준이 정해진 실험 계획서로 바꾸는 스킬입니다.

[SKILL.md](SKILL.md) · [설치](#설치) · 함께 쓰는 스킬: [hypothesis-framework](../hypothesis-framework/), [po-doc-writing](../po-doc-writing/), [evidence-based-retro](../evidence-based-retro/)

## 구성

maker-experiment-design은 실험 하나를 일곱 단계로 설계하고 판정합니다.

1. **가설 점검** — 받은 가설을 대상·변화·지표·기간·크기·근거 칸으로 쪼개고 빈 곳을 표시합니다. 가설이 없으면 hypothesis-framework로 넘깁니다.
2. **실험 방식 고르기** — 트래픽, 실패 시 피해, 되돌리기 쉬운 정도로 A/B·페이크도어·컨시어지·인터뷰 등을 고릅니다.
3. **A/B 테스트 설계** — 그룹당 표본 크기, 주 단위 기간, 멈춤 규칙, 가드레일을 정합니다.
4. **MVP 실험 설계** — Must 범위만으로 최소 구현을 정하고 문턱값을 미리 씁니다.
5. **측정 지표 설계** — 북극성 1 / 주요 1~2 / 가드레일 1~3개를 고르고 지표 정의서를 씁니다.
6. **실험 캔버스** — 1~5를 9칸 한 장으로 묶고 판정 기준 표를 넣습니다.
7. **결과 판정** — 미리 정한 기준으로 채택·기각·보류를 정하고 9번 칸을 채웁니다.

## 모드

### 설계

가설은 있는데 어떻게 검증할지 모를 때 씁니다. 1부터 6까지 진행하고 실험 계획서, 지표 정의서, 판정 기준을 한 파일로 냅니다.

### 계산

"표본 몇 명 필요해?", "며칠 돌려야 해?"처럼 A/B 숫자만 필요할 때 씁니다. 기준값과 최소 감지 차이, 하루 대상자 수를 물어 3단계만 수행합니다.

### 지표

"성공 지표 뭘로 잡지", "지표 정의서 만들어 줘"처럼 지표만 정할 때 씁니다. 5단계만 수행합니다.

### 판정

실험이 끝났을 때 씁니다. 사전 판정 기준이 있는지부터 보고 7단계로 판정합니다.

## 상황별 사용

### 새 기능을 만들기 전에 반응부터 보고 싶을 때

다 만들 비용이 크고, 사용자가 정말 쓸지 모르는 상황입니다. MVP 범위가 이미 정해졌다면 maker-prioritization의 Must 목록을 받습니다.

사용할 모드: 설계(가설 점검 → 방식 고르기 → MVP 실험 → 지표 → 캔버스)

### 화면·문구·흐름을 바꾼 효과를 숫자로 알고 싶을 때

트래픽이 충분하고 기능 플래그로 되돌릴 수 있는 상황입니다.

사용할 모드: 설계(가설 점검 → A/B → 지표 → 캔버스)

### 문제 진술문만 있고 가설이 없을 때

maker-problem-framing에서 나온 HMW나 문제 진술문만 있는 상황입니다. 문제 진술문은 캔버스 1번 칸으로 받아 두고, 가설은 hypothesis-framework로 세운 뒤 돌아옵니다.

사용할 모드: 설계(hypothesis-framework를 거친 뒤)

### 실험 계획을 기획서로 내야 할 때

계획서를 팀에 공유할 문서로 바꾸는 상황입니다. 캔버스 1~8칸과 판정 기준을 po-doc-writing의 검증형 기획서로 넘깁니다.

사용할 모드: 설계 → po-doc-writing

### 실험이 끝났을 때

결과를 받아 채택할지 정하는 상황입니다.

사용할 모드: 판정 → evidence-based-retro(회고)

## 가이드라인

### 판정 기준은 실험 전에 고정합니다

결과를 본 뒤에 기준을 정하면 어떤 결과든 성공으로 읽힙니다. 캔버스 8번 칸에 채택·기각·보류 조건을 먼저 쓰고, 사전 기준 없이 판정할 때는 그 사실을 결과에 적습니다.

### A/B가 늘 답은 아닙니다

원인을 모르면 인터뷰부터, 관심만 확인하면 페이크도어부터 합니다. 계산한 기간이 6주를 넘으면 A/B 대신 MVP 방식이나 더 큰 변화를 고릅니다.

### 기간은 주 단위로 올림합니다

요일마다 사용 패턴이 다르기 때문에 최소 1주, 그 위로는 주 단위로 맞춥니다. 정한 기간 전에는 결과를 보고 멈추지 않습니다. 가드레일을 넘거나 할당 비율이 어긋날 때만 멈춥니다.

### 숫자는 사용자에게서만 받습니다

기준값, 트래픽, 목표치는 지어내지 않고 `[확인 필요]`로 남깁니다. 스킬 안의 숫자는 모두 가상의 예입니다.

| 지양 | 권장 |
|---|---|
| "변경 버튼 넣고 2주쯤 A/B 돌려 보죠" | 기준값 60%, MDE 6%p로 그룹당 표본을 계산하고, 하루 대상자 수로 기간을 정해 주 단위로 올림한다 |
| 3일째 실험군이 앞서서 실험을 끝낸다 | 정한 기간과 표본이 찰 때까지 판정하지 않는다 |
| 주요 지표를 다섯 개 둔다 | 주요 1~2개만 판정에 쓰고, 나머지는 진단 지표로 둔다 |
| 유지율만 보고 출시한다 | 업장 측 변경 거절률, CS 문의 수를 가드레일로 함께 본다 |
| 가설이 없는데 실험 캔버스부터 채운다 | hypothesis-framework로 가설을 세운 뒤 캔버스로 돌아온다 |

표의 예는 가상의 예약 앱 "예약 시간 변경" 기능입니다.

## maker-experiment-design vs hypothesis-framework

| | maker-experiment-design | hypothesis-framework |
|---|---|---|
| 하는 일 | 가설을 실험 계획으로 바꾸고 판정한다 | 가설을 세우도록 질문으로 코칭한다 |
| 가설을 다루는 방식 | 칸이 다 있는지 확인하고 구조만 맞춘다 | 관찰과 추측을 나누고 근거 등급을 따진다 |
| 결과물 | 실험 계획서, 지표 정의서, 판정 기준, 결과 판정 | 가설 문장과 취약점 리포트 |

가설이 없거나 근거가 흔들리면 hypothesis-framework가 먼저입니다. 가설이 나오면 이 스킬이 받아 실험으로 설계합니다.

| 입력 | 가설 문장(hypothesis-framework), HMW·문제 진술문(maker-problem-framing), MVP 범위(maker-prioritization), 실험 결과 |
| 출력 | 실험 계획서(9칸 캔버스), 지표 정의서, 판정 기준 표, 결과 판정. `experiment-<주제>.md`로 저장 |
| 다음 스킬 | po-doc-writing(검증형 기획서), evidence-based-retro(회고), notion-ops(승인 후 등록) |
| 외부에 쓰는가 | 쓰지 않습니다. 노션 등록은 승인 후 notion-ops로 |
| 근거 | MAKER 프레임워크 3. 가설 수립 및 실험 카테고리 |

## 근거

2025년 5월에 만든 MAKER 프레임워크의 가설 수립 및 실험 카테고리(가설 수립, A-B 테스트 설계, 실험 캔버스, 측정 지표 설계, MVP 실험 가이드)를 실행 가능한 스킬로 옮겼습니다. 원본은 읽는 문서였고, 다음을 고쳤습니다.

| 구분 | 원본 | 이 스킬 |
|---|---|---|
| 통일 | 가설 형식이 모듈마다 달랐고, MVP 실험 가이드는 가치·성장·수익 가설을 따로 썼습니다 | 문장 하나("만약 [대상]에게 [변화]를 주면, [지표]가 [기간] 안에 [크기]만큼…")와 네 유형(문제·솔루션·성장·가치)으로 맞췄습니다. 수익 가설은 가치 가설에 넣었습니다 |
| 통일 | 지표 개수가 "기본 지표 1~2개", "KPI 3개 이내, 보조 5~7개"로 엇갈렸습니다 | 북극성 1 / 주요 1~2 / 가드레일 1~3으로 정하고, 나머지는 판정에 쓰지 않는 진단 지표로 뒀습니다 |
| 통일 | 실험 결과의 결론이 "확장·피봇·종료"와 "검증·부분 검증·기각"으로 나뉘었습니다 | 채택·기각·보류 세 판정과 판정별 다음 행동으로 맞췄습니다 |
| 보완 | A/B 표본 크기는 입력값 네 개만 있고 공식이 없었습니다 | 두 비율 비교 공식, 어림식 n ≈ 16·p(1−p)/δ², 평균 지표 어림식, 다중 비교 보정을 넣었습니다 |
| 보완 | 기간 산정과 중간에 멈추는 기준이 없었습니다 | 최소 1주·주 단위 올림, 결과 보고 멈추지 않기, 가드레일·할당 비율 불일치일 때만 멈추기를 넣었습니다 |
| 보완 | 실험 방식을 고르는 기준이 없었습니다 | 트래픽·리스크·되돌리기·비용으로 여덟 방식을 비교하는 표를 넣었고, 페이크도어와 인터뷰를 추가했습니다 |
| 보완 | 판정 기준이 결과 표 안에만 있었습니다 | 캔버스 8번 칸에 실험 전에 고정하는 판정 기준 표를 넣었습니다 |
| 보완 | 모듈 간 입력·출력이 흩어져 있었습니다 | 앞 스킬의 산출물을 받는 입력 계약과 검증형 기획서로 넘기는 출력 계약을 뒀습니다 |
| 정리 | 가설 수립 모듈이 같은 일을 하는 hypothesis-framework와 겹쳤습니다 | 가설 코칭은 hypothesis-framework에 맡기고, 여기서는 칸 점검만 합니다 |
| 정리 | 없는 모듈(회고 및 학습)을 가리켰습니다 | evidence-based-retro로 연결했습니다 |
| 사례 교체 | 모듈마다 실제 회사 사례와 출처 없는 성과 수치가 있었습니다 | 모두 빼고, 가상의 예약 앱 "예약 시간 변경" 기능 하나로 모든 단계를 이었습니다 |

실험 캔버스의 9칸 구성은 원본 그대로 두었습니다.

## 검증

가상의 밀키트 구독 앱 문제 정의서와 가설을 받아 A/B 설계, 지표 정의서, 캔버스, 판정 기준까지 만들었습니다.

- **재료** — 문제 정의서(기준값 후보 하나는 누락, 하나는 출처끼리 어긋남), hypothesis-framework 형식의 솔루션 가설(반증 조건, 근거 등급, 대안 가설 포함), 가입 시 할당하지만 마감을 놓친 사용자에게만 변화가 보이는 실험 구조.
- **요청** — 해지 신청률 46%를 36%로 낮추는 기본값 변경을 검증할 실험 설계.
- **통과** — 가설 출력의 칸을 실험 칸으로 옮기면서 판정 기한과 지표 관찰 창을 구분했습니다. 기준값이 없는 지표는 주요 지표로 쓰지 않고 사용자에게 물었습니다. 표본은 어림식 398명, 정식 379명 중 큰 쪽을 썼고, 하루 대상자를 가입자 수가 아니라 변화를 실제로 겪는 사용자 수로 나눠 모집 6주, 4주 관찰 창을 더해 판정 약 8주를 냈습니다. 낮을수록 좋은 지표에서도 판정 표가 성립하고, 유의하지만 MDE에 못 미치는 결과도 보류로 분류됩니다. 스킬 안 예시의 표본 계산(1,067명, 1,015명)도 다시 계산해 맞았습니다.
- **확인하지 못한 것** — 실제 트래픽과 실험 도구에서의 할당, 실험 후 결과 판정(7절), 평균 지표 공식, 본페로니 보정이 들어가는 다중 비교.

```bash
mkdir -p ~/.claude/skills/maker-experiment-design && cp SKILL.md ~/.claude/skills/maker-experiment-design/
```

한 프로젝트에만 쓰려면 저장소 안의 `.claude/skills/maker-experiment-design/`에 둡니다. 다음 세션부터 Claude가 알아서 꺼내 씁니다.

가설을 함께 세우려면 [hypothesis-framework](../hypothesis-framework/)도 설치합니다.

## 범위와 한계

- 실험을 설계하고 판정합니다. 실험 도구 설정, 이벤트 구현, 실제 통계 계산 실행은 하지 않습니다. p값과 신뢰구간은 사용자가 가져온 값을 씁니다.
- 표본 크기 공식은 비율 지표 두 개를 비교하는 경우와 평균 지표의 어림식만 다룹니다. 순차 검정, 베이지안 방식, 다변량 테스트의 표본 계산은 다루지 않습니다.
- 효과를 수치로 재지는 않았습니다.
- 판정 문턱(p<0.05, 검정력 80%, 기간 상한 6주)은 흔히 쓰는 기본값입니다. 팀 기준이 있으면 `SKILL.md` 3단계와 6단계의 값을 팀 것으로 바꿉니다.
