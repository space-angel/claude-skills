# maker-navigator

막연한 제품 문제를 듣고 어떤 프레임워크를 어떤 순서로 쓸지 정한 뒤, 모듈을 이어서 실행하고 결과를 기록하는 스킬입니다.

[SKILL.md](SKILL.md) · [설치](#설치) · 함께 쓰는 스킬: [maker-problem-framing](../maker-problem-framing/), [maker-prioritization](../maker-prioritization/), [maker-experiment-design](../maker-experiment-design/)

## 구성

maker-navigator는 MAKER 프레임워크의 입구입니다. 네 단계로 동작합니다.

1. **진단** — 문제를 한 문장으로 다시 쓰고, 무엇이 비어 있는지(문제·우선순위·검증·결정) 하나만 묻습니다.
2. **프리셋 선택** — 상황에 맞는 모듈 조합을 추천하고, 왜 이 순서인지 한 줄로 붙입니다.
3. **이어서 실행** — 모듈마다 담당 스킬로 넘기고, 앞 모듈의 산출물을 다음 모듈의 입력으로 씁니다.
4. **기록** — 상황, 흐름, 모듈별 결과, 배운 것, 다음에 다시 쓸 방법을 남깁니다.

## MAKER 모듈 지도

| 카테고리 | 모듈 | 담당 스킬 |
|---|---|---|
| 문제 정의 | 피드백 수집, JTBD, 사용자 여정 맵, 5Why, 문제 진술문 | [maker-problem-framing](../maker-problem-framing/) |
| 우선순위 | RICE, MoSCoW, Kano, Impact-Effort, MVP 스코프 | [maker-prioritization](../maker-prioritization/) |
| 실험 | 가설, 실험 캔버스, A/B 테스트, 지표 정의, MVP 실험 | [maker-experiment-design](../maker-experiment-design/) |
| 커뮤니케이션 | 의사결정(DACI), 회의 | [po-doc-writing](../po-doc-writing/) |
| | 스프린트 공유 | [team-status-report](../team-status-report/) |

## 상황별 사용

### 신규 기능을 기획하는데 니즈가 불분명할 때

사용자가 무엇을 하려는지부터 정의해야 하는 상황입니다.

추천 흐름: JTBD → 문제 진술문 → RICE → MVP 범위

### 같은 CS가 반복될 때

증상은 보이는데 원인을 정리하지 못한 상황입니다.

추천 흐름: 피드백 수집 → 5Why → 문제 진술문

### 이탈이 늘었을 때

사용자가 어느 단계에서 왜 떠나는지 모르는 상황입니다.

추천 흐름: 사용자 여정 맵 → 5Why → 문제 진술문 → 가설 → 실험 캔버스

### 기능을 만들지 말지 정해야 할 때

가치와 비용을 함께 보고 근거를 남겨야 하는 상황입니다.

추천 흐름: Kano → RICE → MoSCoW·MVP 범위 → 결정 문서(질문 → 기록). 풀 문제가 아직 정의되지 않았다면 문제 진술문부터 만듭니다.

### MVP 범위를 정해야 할 때

추천 흐름: MoSCoW → MVP 스코프 → 가설

### 새 기능이 효과가 있는지 확인해야 할 때

추천 흐름: 가설 → 실험 캔버스 → 지표 정의. 화면·문구 개선이면 실험 캔버스 대신 A/B 테스트 설계를 씁니다.

### 실험 결과는 있는데 배운 게 남지 않을 때

추천 흐름: 실험 캔버스(배운 것 칸) → [evidence-based-retro](../evidence-based-retro/) → [decision-first-article](../decision-first-article/)

## 가이드라인

### 프레임워크보다 상황을 먼저 봅니다

모듈을 지정하지 않은 요청은 진단부터 합니다. "RICE 해 줘"처럼 모듈을 지정하면 바로 담당 스킬로 넘깁니다.

### 문제 정의를 건너뛰지 않습니다

진단에서 비어 있는 것이 여럿이면 문제 정의 → 우선순위 → 실험 → 커뮤니케이션 순서로 시작합니다. 정의되지 않은 문제로 우선순위를 매기면 점수가 근거를 잃습니다.

### 모듈은 2~4개만 씁니다

18개 모듈을 전부 돌리지 않습니다. 프리셋은 상황에 필요한 것만 담습니다.

### 결과는 다음 모듈로 그대로 넘깁니다

| 지양 | 권장 |
|---|---|
| JTBD를 끝내고 RICE에서 후보 기능을 처음부터 다시 묻는다 | JTBD의 Job과 문제 진술문을 RICE의 평가 기준으로 그대로 넘긴다 |
| 5Why 결과에 `[확인 필요]`가 남았는데 문제 진술문으로 넘어간다 | 빈칸을 먼저 묻고, 확인된 원인만 넘긴다 |
| "RICE, MoSCoW, Kano가 있습니다"라고 모듈 설명을 늘어놓는다 | 상황에 맞는 흐름 하나와 이유 한 줄, 대안 하나만 낸다 |
| 흐름을 끝내고 결과 파일만 남긴다 | 왜 이 흐름을 골랐고 무엇을 배웠는지 실행 기록으로 남긴다 |

표의 예는 가상의 상황입니다.

## maker-navigator vs 카테고리 스킬

| | maker-navigator | maker-problem-framing 등 카테고리 스킬 |
|---|---|---|
| 하는 일 | 어떤 모듈을 어떤 순서로 쓸지 정하고 기록 | 모듈 하나를 실제로 채움 |
| 쓰는 때 | 무엇부터 할지 모를 때 | 쓸 모듈을 이미 알 때 |
| 결과물 | 실행 기록 | 모듈별 산출물 |

## 명세

| 항목 | 내용 |
|---|---|
| 요청 예시 | "이 문제 어떻게 접근하지" · "뭐부터 해야 할지 모르겠어" · "CS가 계속 반복돼" · "이 기능 만들지 말지 정해야 해" · "MAKER로 풀어보자" |
| 입력 | 막연한 문제 한 문장 |
| 출력 | 프리셋 추천, 모듈별 산출물(담당 스킬이 생성), 실행 기록 md |
| 필요한 연결 | 없음. 노션 등록은 [notion-ops](../notion-ops/) |
| 외부에 쓰는가 | 아니요. 노션 등록은 승인 후 |

## 근거

2025년 5월에 만든 제품 문제 해결 프레임워크 MAKER의 "시작하기" 흐름을 실행 가능한 스킬로 옮겼습니다. 원본에서 다음을 고도화했습니다.

| 원본 | 스킬 |
|---|---|
| 프리셋마다 "왜 이 흐름인지" 설명이 있다고 했지만 비어 있었다 | 프리셋마다 이유를 한 줄로 붙였다 |
| 같은 상황(신규 기능, 반복 CS, 이탈)인데 페이지마다 흐름이 달랐다 | 상황당 흐름 하나로 통일했다 |
| 모듈 결과를 다음 모듈로 넘기는 방법이 없었다 | 모듈마다 넘기는 산출물을 정했다 |
| 없는 모듈(회고 및 학습 등)을 가리켰다 | 저장소의 기존 스킬로 연결했다 |
| 실제 회사 사례에 출처 없는 성과 수치가 있었다 | 모두 빼고 가상의 예로 바꿨다 |

## 검증

함정을 심은 가상의 밀키트 구독 앱 자료로 네비게이터부터 실험 설계까지 이어서 돌렸습니다. 스킬 안의 예약 앱 예시와 겹치지 않는 상황을 골랐습니다.

- **재료** — 피드백 15건(문제를 숨긴 기능 요청 4건, 서로 반대인 의견 한 쌍 포함), 신규 가입 코호트 퍼널, 퍼널과 어긋나는 보고서 수치 하나, 해결책이 들어간 기획 메모, 근거 없는 회의 메모.
- **요청** — "구독 해지가 늘었어, 어떻게 접근해야 할지 모르겠어."
- **통과** — 진단에서 문제 정의를 골랐고 "이탈이 늘었다" 프리셋을 추천했습니다. 피드백 원문이 있어 앞에 피드백 정리를 넣고 이유를 한 줄로 남겼습니다. 문제 진술문에서 실험으로 넘어가기 전에 가설 단계를 끼웠습니다. 문제 정의서 전체(영향 지표 현재값, 문제 가설 재료 포함)와 가설의 반증 조건·대안 가설을 다음 스킬로 그대로 넘겼습니다. `[확인 필요]`와 `[미확보]`가 남은 칸은 넘기기 전에 질문으로 올렸습니다.
- **확인하지 못한 것** — 실제 사용자와의 대화(선택지 응답은 시나리오로 대신함), 우선순위·커뮤니케이션 프리셋, 노션 등록.

## 설치

```bash
cp -r maker-navigator maker-problem-framing maker-prioritization maker-experiment-design ~/.claude/skills/
```

네비게이터는 카테고리 스킬을 불러 쓰므로 네 스킬을 함께 설치합니다. 결정 문서와 스프린트 공유까지 쓰려면 [po-doc-writing](../po-doc-writing/), [team-status-report](../team-status-report/)도 설치합니다.

## 범위와 한계

- 모듈 실행은 카테고리 스킬이 맡습니다. 이 스킬은 고르고, 잇고, 기록합니다.
- 프리셋은 자주 만나는 상황 위주입니다. 표에 없는 상황은 모듈 하나로 시작해 결과를 보고 다음을 정합니다.
- 프레임워크를 쓴 뒤 결정의 질이 얼마나 나아졌는지는 수치로 재지 않았습니다.
