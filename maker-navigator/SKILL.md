# MAKER 네비게이터

막연한 문제를 한 문장으로 받고, 맞는 모듈 조합(프리셋)을 골라, 앞 모듈의 결과를 다음 모듈에 넘기며 실행한다. 끝나면 어떤 상황에 무엇을 썼고 무엇을 배웠는지 남긴다.

## 이 스킬의 전제

**프레임워크는 읽는 것이 아니라 채우는 것이다.** 모듈 설명을 늘어놓지 않는다. 사용자와 함께 템플릿을 채우고, 채운 결과를 다음 모듈의 입력으로 쓴다.

**프레임워크를 먼저 고르지 않는다. 상황을 먼저 본다.** "RICE 해 줘"처럼 모듈을 지정하면 바로 해당 스킬로 넘긴다. 상황만 말하면 진단부터 한다.

## 1단계 — 상황을 진단한다

사용자가 말한 문제를 한 문장으로 다시 쓰고 확인받는다. 그다음 무엇이 비어 있는지 하나만 묻는다. 선택지를 준다.

| 선택지 | 비어 있는 것 | 시작 카테고리 |
|---|---|---|
| 무엇이 문제인지 모르겠다 | 문제 정의 | 문제 정의 |
| 할 일은 많은데 뭐부터 할지 모르겠다 | 우선순위 | 우선순위 |
| 이게 효과가 있을지 모르겠다 | 검증 | 실험 |
| 팀이 합의하지 못하고 있다 | 결정 | 커뮤니케이션 |

답이 둘 이상이면 앞쪽(문제 정의 → 우선순위 → 실험 → 커뮤니케이션) 순서로 시작한다. 문제가 정의되지 않은 채 우선순위나 실험으로 가지 않는다. 2단계 표의 우선순위·실험 프리셋은 풀 문제가 이미 한 문장으로 정의돼 있을 때 쓴다. 없으면 문제 진술문부터 만든다.

## 2단계 — 프리셋을 고른다

진단 결과에 맞는 흐름을 하나 추천한다. 추천마다 **왜 이 순서인지**를 한 줄로 붙이고, 대안이 있으면 하나만 함께 낸다.

| 상황 | 흐름 | 왜 이 순서인가 |
|---|---|---|
| 신규 기능을 기획하는데 니즈가 불분명하다 | JTBD → 문제 진술문 → RICE → MVP 범위 | 사용자가 하려는 일을 먼저 정의해야 후보 기능의 가치를 잴 수 있다 |
| 같은 CS가 반복된다 | 피드백 수집 → 5Why → 문제 진술문 | 흩어진 피드백을 모아야 반복 패턴이 보이고, 패턴이 있어야 근본 원인을 판다 |
| 이탈이 늘었다 | 사용자 여정 맵 → 5Why → 문제 진술문 → 가설 → 실험 캔버스 | 어느 단계에서 떠나는지 찾고, 왜 떠나는지 판 뒤, 고칠 방법을 가설로 고정하고 실험으로 설계한다 |
| 이 기능을 만들지 말지 정해야 한다 | Kano → RICE → MoSCoW·MVP 범위 → 결정 문서(질문 → 기록) | 사용자가 느끼는 가치 유형을 먼저 보고, 비용 대비 효과를 잰 뒤, 만든다면 어디까지인지 정하고 근거와 함께 결정을 남긴다. MoSCoW는 "만든다면"을 전제로 한 초안이며, 만들지 말지는 결정 문서에서 정한다 |
| 백로그가 너무 많다 | Impact-Effort → MoSCoW → 스프린트 공유 | 빠르게 큰 덩어리를 거른 뒤, 이번 릴리스에 꼭 필요한 것만 남기고 팀에 알린다 |
| MVP 범위를 정해야 한다 | MoSCoW → MVP 스코프 → 가설 | Must만 MVP에 넣고, MVP가 무엇을 검증하는지 가설로 고정한다 |
| 새 기능이 효과가 있는지 확인해야 한다 | 가설 → 실험 캔버스 → 지표 정의 | 가설 없는 실험은 끝나도 판정할 수 없다 |
| 화면이나 문구를 개선하려 한다 | 가설 → A/B 테스트 설계 → 지표 정의 | 트래픽이 충분한 화면은 A/B로 바로 비교할 수 있다 |
| 새 비즈니스 모델을 시도하려 한다 | 가설 → MVP 실험 → 실험 캔버스 | 만들기 전에 가장 싼 방법으로 수요부터 확인한다 |
| 실험 결과는 있는데 배운 게 남지 않는다 | 실험 캔버스(배운 것 칸) → 회고 → 아티클 | 결과를 결정으로 바꾸고, 팀과 바깥에 남긴다 |
| 여러 팀이 걸린 결정이 막혀 있다 | 결정이 필요한 질문(DACI) → 회의록 → 스프린트 공유 | 누가 정하는지부터 정해야 회의가 결정으로 끝난다 |

표에 없는 상황이면 1단계 진단 결과의 카테고리에서 모듈 하나로 시작하고, 결과를 보고 다음 모듈을 정한다.

## 3단계 — 모듈을 이어서 실행한다

모듈마다 담당 스킬로 넘긴다. 넘길 때 **앞 모듈의 산출물을 그대로 입력으로 준다.**

| 모듈 | 담당 스킬 | 다음 모듈에 넘기는 것 |
|---|---|---|
| 피드백 수집, JTBD, 사용자 여정 맵, 5Why, 문제 진술문 | `maker-problem-framing` | 문제 정의서 전체(문제 진술문, HMW, 영향 지표와 현재값, 문제 가설 재료, 후보 메모) |
| RICE, MoSCoW, Kano, Impact-Effort, MVP 스코프 | `maker-prioritization` | 순위 목록 + MVP 범위(Must) + 검증할 가정 + Won't 목록 |
| 가설, 실험 캔버스, A/B 테스트, 지표 정의, MVP 실험 | `maker-experiment-design` | 실험 계획 + 지표 정의서 + 판정 기준 |
| 가설이 아직 없을 때 | `hypothesis-framework` | 구조화된 가설(가설 문장, 반증 조건, 근거 등급) + 취약점 리포트(대안 가설) |
| 결정 문서(DACI), 회의록 | `po-doc-writing` | 결정 기록 |
| 스프린트 공유 | `team-status-report` | 공유 문서. 넘길 때 스프린트 목표 문장, 결정 기록 링크, 읽을 트래커·GitHub 위치를 함께 준다 |
| 회고 | `evidence-based-retro` | 배운 것 |
| 아티클 | `decision-first-article` | 공개 글 |

규칙:

- 모듈 하나가 끝날 때마다 산출물을 보여 주고, 다음 모듈로 넘어갈지 묻는다. 사용자가 멈추면 거기까지 기록한다.
- 산출물에 `[확인 필요]`나 `[미확보]`(hypothesis-framework의 표기)가 남아 있으면, 그 칸이 다음 모듈의 필수 입력인지 본다. 필수 입력이면 넘기기 전에 사용자에게 먼저 묻는다. 필수 입력이 아니면 표시한 채 넘기고 실행 기록의 "열린 질문"에 올린다. 어느 경우에도 빈칸을 추측으로 채우지 않는다.
- 프리셋이 문제 진술문에서 실험 모듈로 바로 가더라도, 가설이 없으면 그 사이에 `hypothesis-framework`를 넣는다(`maker-experiment-design`은 가설 없이 시작하지 않는다). 이 단계는 모듈 수에 세지 않고, 실행 기록의 흐름에는 적는다.
- 결과를 보고 흐름을 바꿀 수 있다. 예: 5Why에서 원인이 둘로 갈리면 문제 진술문을 둘로 쓰고, 우선순위 모듈을 하나 더 넣는다. 바꿀 때는 이유를 한 줄로 알린다.

## 4단계 — 기록한다

흐름이 끝나면(또는 사용자가 멈추면) 실행 기록을 md 파일로 남긴다.

```markdown
# <상황 한 줄>

> 날짜: YYYY-MM-DD · 흐름: <모듈 → 모듈 → 모듈>

## 상황
<1단계에서 확인한 문제 한 문장과, 비어 있던 것>

## 흐름과 이유
<고른 프리셋과 왜 이 순서였는지. 중간에 흐름을 바꿨다면 그 이유>

## 모듈별 결과
### <모듈 이름>
<산출물 요약 3~5줄. 전문은 별도 파일 링크>

## 배운 것
- <무엇을 실행했고 무엇을 알게 됐나>

## 다음에 비슷한 상황이 오면
- <이번 흐름에서 그대로 쓸 것 / 바꿀 것>

## 열린 질문
- <[확인 필요]로 남은 것>
```

노션에 올리려면 승인을 받은 뒤 `notion-ops`로 등록한다.

## 하지 않는 것

- 실제 회사 사례나 출처 없는 성과 수치를 근거로 들지 않는다. 예시가 필요하면 가상의 예라고 밝힌다.
- 모듈을 전부 돌리지 않는다. 상황에 필요한 2~4개만 쓴다.
- 사용자가 답하지 않은 칸을 추측으로 채우지 않는다.
- 팀에 보내거나 외부 도구에 쓰는 일은 승인 없이 하지 않는다.
