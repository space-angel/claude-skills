# 문제 정의 (MAKER 1단계)

표면 현상이 아니라 근본 원인을 잡아 "무엇을 풀 것인가"를 한 문장으로 고정한다. 그 문장을 HMW 질문으로 바꿔 다음 단계(우선순위, 가설, 실험)가 그대로 받을 수 있게 넘긴다.

## 전제

- **대화 방식**: 필요한 정보가 없으면 한 번에 하나씩 묻는다. 가능하면 선택지를 준다. 사용자가 주지 않은 수치·인용·원인을 추측으로 채우지 않고 `[확인 필요: …]`로 남긴다.
- **근거 표시**: 산출물의 모든 칸에 근거(데이터, 인용, 관찰)를 붙인다. 근거가 없는 칸은 "가정"으로 표시한다.
- **사례**: 이 문서의 예는 모두 가상의 예약 앱이다. 관찰: "예약 시간 변경" 기능이 없어 취소 후 재예약하는 사용자가 많고, 그중 일부가 재예약하지 않고 이탈한다. 숫자는 모두 가상의 예다.
- **저장**: 산출물은 `problem-framing-<주제>-<YYYYMMDD>.md`로 저장하고 경로를 알린다. 노션 등록은 사용자가 승인한 뒤 `notion-ops`로 한다.
- **출력 계약**: 이 스킬의 끝은 항상 7절의 "문제 정의서"다. 중간 모듈만 쓰고 끝내더라도 문제 진술문과 HMW 칸이 비었다는 것을 알린다.

## 모듈 고르기

첫 질문은 "지금 손에 있는 것이 무엇인가"다. 선택지: ① 피드백·CS·리뷰 원문 ② 이탈·전환 같은 행동 데이터 ③ 아이디어나 기능 요청만 ④ 원인은 이미 앎. 여러 개를 고를 수 있다. ①과 ②가 함께 있으면 1에서 시작해 행동 데이터는 1의 교차 확인과 3에 쓴다(1 → 3 → 4 → 5 → 6).

| 상황 | 시작 모듈 | 흐름 |
|---|---|---|
| VOC·CS·리뷰가 쌓였는데 무엇이 문제인지 모른다 | 1 피드백 정리 | 1 → 4 → 5 → 6 |
| 반복되는 CS, 고쳐도 다시 생긴다 | 1 피드백 정리(CS만) | 1 → 4 → 5 → 6 |
| 이탈·전환 하락이 어느 지점에서 생기는지 모른다 | 3 사용자 여정 맵 | 3 → 4 → 5 → 6 |
| 신규 기능 기획인데 사용자 니즈가 불분명하다 | 2 JTBD | 2 → (3) → 5 → 6 |
| 기능 요청은 많은데 "왜" 원하는지 모른다 | 1 → 2 | 1 → 2 → 5 → 6 |
| 근본 원인은 알고 문장만 필요하다 | 5 문제 진술문 | 5 → 6 |
| 진술문이 이미 있고 HMW만 필요하다 | 6 HMW 전환 | 6 → 7 |

모든 흐름은 5(문제 진술문)와 6(HMW)을 지나 7(문제 정의서)에서 끝난다.

## 1. 피드백 정리 (VOC → 문제 신호)

- **목적**: 여러 채널의 원시 피드백을 한곳에 모아 구조화하고, 빈도와 심각도로 "파고들 문제 신호" 하나를 고른다.
- **언제**: 피드백이 여러 채널에 흩어져 있을 때, 기능 요청을 문제로 번역해야 할 때, 반복 CS의 원인을 찾기 전.
- **입력**: 채널별 원문(인앱 의견, CS 티켓, 앱 리뷰, 인터뷰 메모, 설문 응답), 가능하면 행동 데이터(퍼널, 이탈 지점).

**절차와 질문**

1. 채널 확인: "어떤 채널의 피드백이 있나요?" 아래 표를 보여 주고 고르게 한다. 채널마다 편향을 함께 적는다.

   | 채널 | 잘 보이는 것 | 편향 |
   |---|---|---|
   | 인앱 의견 | 사용 맥락이 붙은 즉시 반응 | 자기 선택, 극단 의견 |
   | 인터뷰 | 동기와 맥락 | 표본이 적다 |
   | 설문 | 규모 있는 정량 | 깊이 부족, 응답률 |
   | 행동 데이터 | 실제로 한 일 | 의도를 모른다 |
   | CS | 실제 고통점, 꾸준히 들어온다 | 부정 편향, 형식이 제각각 |
   | 앱 리뷰·소셜 | 비공식 감성 | 대표성 부족, 노이즈 |
   | 베타 그룹 | 신기능 심층 반응 | 일반 사용자와 다르다 |

2. 원문 받기: 붙여 넣기나 파일로 받는다. 요약본만 있으면 원문을 요청한다. 요약은 맥락을 잃는다.
3. 구조화: 한 건마다 `날짜 / 출처 / 사용자 유형 / 제품 영역 / 유형(버그·요청·칭찬·불만·제안) / 태그 / 원문 인용`을 붙인다.
4. 요청을 문제로 번역: "변경 버튼 만들어 주세요" 같은 요청은 "무엇을 하려다 막혔는가"로 다시 적는다. 번역이 불가능하면 `[확인 필요: 요청 배경]`.
5. 테마 묶기: 같은 막힘끼리 묶고, 테마별 빈도와 심각도를 매긴다. 서로 반대인 의견("메뉴가 적다"/"많다")은 한 테마로 합산하지 않고 양쪽을 따로 적는다. 세그먼트 차이일 수 있다. 심각도는 1 불편 / 2 과업 지연 / 3 과업 실패·이탈.
6. 교차 확인: 상위 테마를 행동 데이터로 확인한다. "피드백 수가 많다"와 "실제로 많은 사용자가 겪는다"는 다르다.
7. 신호 고르기: "빈도×심각도가 가장 높은 테마는 ○○입니다. 이걸로 진행할까요?" 사용자가 고른 테마 하나만 다음 모듈로 넘긴다.

**산출물 템플릿**

```markdown
## 피드백 정리 — <주제>
- 기간·채널: <예: 최근 4주, CS 120건 + 앱 리뷰 40건>(가상의 예)
| 테마 | 빈도 | 심각도(1~3) | 대표 인용 | 행동 데이터 교차 | 비고 |
|---|---|---|---|---|---|
| 예약 시간을 바꾸려면 취소 후 재예약해야 함 | 48 | 3 | "시간만 바꾸고 싶은데 취소하니까 그 자리가 없어졌어요" | 취소 후 24시간 내 재예약 없음 31% | 가상의 예 |
- 선택한 문제 신호: <테마 1개>
- 확인 필요: <목록>
```

- **유의 사항**: 소수의 큰 목소리에 끌려가지 않는다(대표성 확인). 원문 인용을 지우지 않는다. 체계를 복잡하게 만들지 않는다. 피드백 제공자에게 결과를 알리는 "루프 닫기"는 이 스킬 범위 밖이며, 상태 칸(접수→검토→계획→해결→알림 완료)만 남겨 둔다.
- **다음 모듈**: 반복 CS·원인 불명 → 4(5Why). 이탈 지점 불명 → 3(여정 맵). 원인이 명확 → 5.

## 2. JTBD (사용자가 제품을 "고용"하는 일)

- **목적**: 기능 요구가 아니라 "어떤 상황에서 무엇을 이루려고 이 제품을 쓰는가"를 정의한다.
- **언제**: 신규 기능 기획, 니즈가 불분명할 때, 기능 요청의 동기를 알아야 할 때.
- **입력**: 인터뷰·관찰 기록, 1의 피드백 테마.

**절차와 질문**

1. 인터뷰 기록이 없으면 다음 질문으로 인터뷰 가이드를 만들어 준다: 이 기능을 쓰기 전 어떤 문제가 있었나요? / 왜 이 방법을 골랐나요? / 쓴 뒤 무엇이 달라졌나요? / 이게 없었다면 어떻게 해결했을까요?
2. Job을 세 관점으로 적는다: 기능적(실제 과업) / 감정적(느끼고 싶은 상태) / 사회적(남에게 보이고 싶은 모습). 근거가 없는 관점은 비워 둔다.
3. Job 진술문: `[상황]에서 [사용자]는 [목표]를 이루기 위해 [제품/방법]을 쓴다.`
4. Job 수행 중 어려움을 나열한다. 이것이 5의 "문제/장애물" 후보다.
5. 전환을 막고 미는 네 힘을 적는다: 추진(지금 방법의 불만) / 끌림(새 방법의 매력) / 습관(지금 방법에 익숙함) / 불안(새 방법에 대한 걱정).

**산출물 템플릿**

```markdown
## JTBD — <주제>
| 관점 | 내용 | 근거 |
|---|---|---|
| 기능적 | 이미 잡은 예약을 새 시간으로 옮긴다 | 인터뷰 [확인 필요] |
| 감정적 | 자리를 잃을까 불안하지 않고 싶다 | CS 인용 |
| 사회적 | 상대(매장·동행)에게 번거로움을 주지 않고 싶다 | 가정 |
- Job 진술문: 갑자기 일정이 바뀐 상황에서 예약 고객은 원래 받으려던 서비스를 놓치지 않기 위해 예약 앱을 쓴다.
- 어려움: 변경이 취소+재예약이라 자리를 잃을 위험 / 재예약에 시간이 든다
| 힘 | 내용 | 중요도 |
|---|---|---|
| 추진 / 끌림 / 습관 / 불안 | … | 높음·중간·낮음 |
```

- **유의 사항**: JTBD는 사용자 특성(누구인가)이 아니라 상황과 목적(왜 쓰는가)을 본다. 기능 이름이 Job에 들어가면 다시 쓴다.
- **다음 모듈**: 어려움이 어느 단계에서 생기는지 모르면 3, 알면 5.

## 3. 사용자 여정 맵 (Pain Point 찾기)

- **목적**: 한 사용자가 목표를 이루기까지 거치는 단계를 행동·접점·생각·감정으로 펼쳐, 문제가 몰린 지점을 찾는다.
- **언제**: 이탈·전환 하락 지점을 모를 때, 팀이 같은 흐름을 보고 있는지 맞출 때.
- **입력**: 1의 테마 또는 2의 Job, 퍼널·이탈 데이터, 인터뷰.

**절차와 질문**

1. 범위 정하기: "누구의, 어떤 목표의, 어디서 어디까지 여정인가요?" 사용자 유형 하나, 시나리오 하나, 시작점과 끝점을 정한다. 지금 상태(as-is)를 그린다. 바라는 상태는 그리지 않는다.
2. 단계 나누기: 사용자 관점의 동사로 5~7단계를 잡는다. 화면 이름이 아니라 사용자가 하는 일로 적는다.
3. 단계별로 채우기: 행동 / 접점(화면·채널·사람) / 생각(가능하면 실제 인용) / 감정(-2~+2) / 문제점 / 근거. 근거가 없는 칸은 "가정"으로 표시한다. 가정이 절반을 넘으면 "가정 지도"라고 제목에 밝힌다.
4. 감정 곡선과 데이터 겹치기: 감정이 가장 낮은 단계와 이탈 데이터가 큰 단계를 표시한다. 둘이 어긋나면 그 자체가 확인할 질문이다.
5. Pain Point 고르기: 단계별 문제점에 빈도와 심각도(1의 척도)를 매기고, 상위 1~2개를 고른다.
6. 기회 영역 적기: 해결책이 아니라 "~하지 못한다 → ~할 수 있다면" 형태로 적는다. 이것이 6(HMW)의 재료가 된다.
7. 인사이트 3줄: 무엇이 어디서 왜 막히는지.

**산출물 템플릿**

```markdown
## 사용자 여정 맵 — <사용자 유형> / <시나리오> (as-is)
| 단계 | 행동 | 접점 | 생각 | 감정(-2~+2) | 문제점 | 근거 |
|---|---|---|---|---|---|---|
| 일정 변경 인지 | 예약 시간에 못 간다는 걸 안다 | 캘린더 | "시간만 미루면 되는데" | -1 | — | 인터뷰 |
| 변경 방법 찾기 | 예약 상세에서 변경 버튼을 찾는다 | 예약 상세 | "변경이 어디 있지?" | -1 | 변경 메뉴가 없다 | CS 48건(가상의 예) |
| 취소 | 어쩔 수 없이 취소한다 | 취소 화면 | "자리 없어지면 어쩌지" | -2 | 기존 자리가 바로 풀린다 | 취소 로그 |
| 재예약 시도 | 새 시간을 고른다 | 예약 화면 | "원하는 시간이 다 찼네" | -2 | 원하는 슬롯이 이미 없다 | 재예약 실패율 [확인 필요] |
| 재예약 완료/이탈 | 다른 시간에 잡거나 포기한다 | — | — | -2 | 31%가 24시간 내 재예약 없음 | 퍼널(가상의 예) |
- Pain Point(상위): 취소 순간 기존 자리가 풀린다 / 재예약 시 원하는 슬롯이 없다
- 기회 영역: 자리를 잃지 못한다 → 기존 자리를 지킨 채 새 시간을 확보할 수 있다면
- 인사이트(3줄): …
```

- **유의 사항**: 한 맵에 사용자 유형 하나. 단계를 내부 조직 순서로 나누지 않는다. 기회 영역에 해결책("변경 버튼 추가")을 쓰지 않는다.
- **다음 모듈**: 고른 Pain Point의 원인을 모르면 4, 알면 5.

## 4. 5Why (근본 원인)

- **목적**: "왜?"를 반복해 증상 뒤의 시스템 원인을 찾는다. 사람이 아니라 구조를 고칠 수 있는 수준까지 내려간다.
- **언제**: 같은 문제가 반복될 때, 겉으로 보이는 해결책이 효과가 없었을 때, 원인에 대한 의견이 갈릴 때.
- **입력**: 1의 문제 신호 또는 3의 Pain Point 한 문장, 관련 데이터.

**절차와 질문**

1. 문제를 구체적인 한 문장으로 적는다. 현상과 수치가 들어가야 한다.
2. "왜 그런가요?"를 묻고 답마다 "우리가 이걸 사실로 아는 근거는?"을 붙인다. 근거가 없으면 `[확인 필요]`로 두고 다음 왜로 넘어가지 않는다. 사용자에게 확인 방법(로그, 인터뷰, 정책 문서)을 제안한다.
3. 앞 답을 원인으로 삼아 반복한다. 5회는 기준이지 규칙이 아니다. 더 물어도 의미가 없거나, 팀이 바꿀 수 있는 구조에 닿으면 멈춘다.
4. 원인이 여러 갈래면 갈래마다 따로 돌린 뒤 공통 원인으로 묶는다.
5. 근본 원인을 한 문장으로 정한다. 해결 방향은 메모만 하고 평가하지 않는다.

**산출물 템플릿**

```markdown
## 5Why — <문제 한 문장>
| 단계 | 질문 | 답 | 근거 |
|---|---|---|---|
| 문제 | — | 취소한 사용자의 31%가 24시간 안에 재예약하지 않는다 | 퍼널(가상의 예) |
| Why 1 | 왜 재예약하지 않는가? | 원하는 시간대가 이미 찼다 | 인터뷰 5건 중 4건(가상의 예) |
| Why 2 | 왜 찼는가? | 취소하는 순간 기존 자리가 다른 사람에게 풀렸다 | 슬롯 로그 |
| Why 3 | 왜 취소해야 했는가? | 시간을 바꾸는 방법이 취소 후 재예약뿐이다 | 화면 구조 |
| Why 4 | 왜 그 방법뿐인가? | 예약 모델이 생성·취소만 있고 변경 상태가 없다 | 기획 문서 [확인 필요] |
| 근본 원인 | — | 시간 변경이 "취소+신규 예약"으로만 처리되어 변경 도중 기존 자리를 잃는 구조 | Why 1~3, Why 4는 확인 전 [확인 필요] |
- 해결 방향 메모(평가하지 않음): …
```

- **유의 사항**: 개인을 탓하는 답("담당자가 놓쳐서")이 나오면 "그 실수가 가능했던 구조는?"으로 다시 묻는다. 근거 없는 사슬은 그럴듯한 이야기일 뿐이다.
- **다음 모듈**: 5.

## 5. 문제 진술문

- **목적**: 사용자·상황·문제·영향·원인을 한 문장으로 이어 팀이 같은 문제를 보게 한다. 이후 모든 판단의 기준 문장이 된다.
- **언제**: 원인을 찾은 뒤, 팀원 간 문제 인식이 다를 때, 아이디어를 평가할 기준이 필요할 때.
- **입력**: 4의 근본 원인, 3의 Pain Point, 2의 Job과 어려움, 1의 근거.

**절차와 질문** (칸 하나씩 묻고, 앞 모듈 산출물이 있으면 채운 안을 보여 주고 확인받는다)

1. 사용자: 문제를 겪는 주체. "모든 사용자"는 받지 않는다.
2. 상황: 언제, 어느 단계에서.
3. 문제: 무엇이 막히는가. 해결책 단어(버튼, 기능명)를 넣지 않는다.
4. 영향: 그래서 사용자와 사업에 생기는 결과. 가능하면 지표와 현재값.
5. 원인: 4의 근본 원인. 없으면 `[확인 필요]`.
6. 근거: 칸마다 출처.
7. 한 문장으로 잇는다: `[사용자]는 [상황]에서 [문제]를 겪고 있으며, 이로 인해 [영향]이 생긴다. 이는 [원인] 때문이다.`

**점검** (하나라도 걸리면 고친다)

- 중립성: 해결책이 들어 있지 않은가?
- 단일 초점: 문제가 하나인가? "그리고"로 두 문제가 이어지면 나눈다.
- 범위: 한 분기 안에 손댈 수 있는 크기인가? 너무 넓으면 사용자나 상황을 좁힌다.
- 근거: 모든 칸에 출처가 있는가?
- JTBD 일치: 2를 했다면 Job의 어려움과 같은 이야기인가?

**산출물 템플릿**

```markdown
## 문제 진술문
| 칸 | 내용 | 근거 |
|---|---|---|
| 사용자 | 기존 예약의 시간을 바꿔야 하는 고객 | CS 테마 |
| 상황 | 예약 후 일정이 바뀌어 시간을 옮기려 할 때 | 여정 맵 2~4단계 |
| 문제 | 시간을 옮기는 도중 기존 자리를 잃고 원하는 시간을 다시 잡지 못한다 | 인터뷰, 슬롯 로그 |
| 영향 | 예약 건이 사라지고 사용자가 이탈한다(취소 후 24시간 내 미재예약 31%, 가상의 예) | 퍼널 |
| 원인 | 시간 변경이 취소+신규 예약으로만 처리되어 변경 도중 자리가 풀리는 구조 | 5Why |
> 기존 예약의 시간을 바꿔야 하는 고객은 일정이 바뀌어 시간을 옮기려 할 때 기존 자리를 잃고 원하는 시간을 다시 잡지 못하고 있으며, 이로 인해 예약이 사라지고 이탈이 생긴다. 이는 시간 변경이 취소와 신규 예약으로만 처리되어 변경 도중 기존 자리가 풀리기 때문이다.
```

- **유의 사항**: 팀 합의가 필요한 문장이다. 사용자 혼자 정했다면 "팀 검토 전"이라고 표시한다.
- **다음 모듈**: 6.

## 6. HMW 전환 (문제 진술문 → "어떻게 하면 ~할 수 있을까?")

- **목적**: 문제 문장을 해결을 여는 질문으로 바꾼다. 질문은 해결책을 정하지 않으면서, 해결책이 나올 방향은 정한다.
- **언제**: 5를 마친 직후. 우선순위·가설·실험 단계로 넘기기 직전.
- **입력**: 5의 문제 진술문.

**절차와 질문**

1. 기본형을 만든다: `어떻게 하면 [사용자]가 [상황]에서 [문제가 풀린 상태]를 이룰 수 있을까?` 진술문의 "문제"를 뒤집어 "원하는 상태"로 쓴다.
2. 변형 2~3개를 만든다(아래 중 맞는 것만).
   - 원인 겨냥: 근본 원인을 직접 겨냥한다
   - 부정 제거: 가장 나쁜 순간을 없앤다
   - 긍정 강화: 이미 잘 되는 부분을 키운다
   - 가정 뒤집기: 당연하게 여긴 전제를 의심한다
   - 대상 좁히기: 가장 심하게 겪는 세그먼트로 좁힌다
3. 범위 점검: 각 질문이 너무 넓은지(어떤 해결책이든 다 들어감), 너무 좁은지(해결책이 이미 들어 있음) 표시한다.
4. 사용자에게 주 HMW 1개를 고르게 한다. 나머지는 보조로 남긴다.
5. 후보 메모: 사용자가 이미 떠올린 해결책이 있으면 HMW 아래에 "후보"로 받아 적기만 한다. 평가와 순위는 maker-prioritization에서 한다.

**산출물 템플릿**

```markdown
## HMW
| 구분 | 질문 | 범위 판정 |
|---|---|---|
| 너무 넓음(예시) | 어떻게 하면 이탈을 줄일 수 있을까? | 넓음: 문제와 무관한 해결책도 다 들어간다 |
| 너무 좁음(예시) | 어떻게 하면 예약 상세에 변경 버튼을 넣을 수 있을까? | 좁음: 해결책이 정해져 있다 |
| 주 HMW(원인 겨냥) | 어떻게 하면 시간을 바꾸려는 고객이 기존 자리를 잃지 않고 새 시간을 확보할 수 있을까? | 적정 |
| 보조(부정 제거) | 어떻게 하면 취소 후 원하는 시간을 못 잡는 순간을 없앨 수 있을까? | 적정 |
| 보조(대상 좁히기) | 어떻게 하면 당일 일정이 바뀐 고객이 같은 날 다른 시간으로 옮길 수 있을까? | 적정 |
- 후보 메모(평가 전): 사용자가 말한 아이디어만
```

- **유의 사항**: HMW는 하나의 문제 진술문에서만 나온다. 다른 문제가 섞이면 5로 돌아가 진술문을 나눈다.
- **다음 모듈**: 7.

## 7. 문제 정의서 (최종 산출물과 넘기기)

모든 흐름은 이 문서로 끝난다. 다음 스킬이 이 문서를 그대로 입력으로 받는다.

```markdown
# 문제 정의서 — <주제> (<YYYY-MM-DD>, 상태: 팀 검토 전/합의됨)
## 문제 진술문
> <5의 한 문장>
## HMW
- 주: <질문>
- 보조: <질문>, <질문>
## 근거 요약
- 대상 사용자·세그먼트: …
- 영향 지표와 현재값: <지표> = <값> (<출처>) — 실험 기준선 후보. 출처마다 값이 다르면 둘 다 적고 `[확인 필요: 정의·분모]`를 단다. 다른 지표에서 역산해 채우지 않는다
- 근본 원인: <4의 결론 또는 [확인 필요]>
- 빈도·심각도: <1·3의 판정>
## 문제 가설 재료 (hypothesis-framework 입력)
- 대상: … / 상황: … / 문제: … / 근거: …
## 후보 메모 (평가 전)
- …
## 확인 필요
- [확인 필요: …]
## 사용한 모듈
- 1 피드백 정리 → 4 5Why → 5 → 6 (산출물 파일: …)
```

**넘기는 곳**

| 다음 스킬 | 받아 가는 칸 | 쓰는 방식 |
|---|---|---|
| maker-prioritization | HMW, 후보 메모, 영향 지표 | HMW에 답하는 후보를 모아 순위를 매긴다. 영향 지표가 평가 기준이 된다 |
| hypothesis-framework | 문제 가설 재료, 근본 원인 | 문제 가설부터 세운다. 원인이 `[확인 필요]`면 문제 가설로, 특정되면 솔루션 가설로 간다 |
| maker-experiment-design | 문제 진술문, 영향 지표 현재값 | 실험의 "문제 정의" 칸과 기준선으로 쓴다 |

넘기기 전에 묻는다: "다음은 ① 후보 우선순위 ② 가설 세우기 ③ 여기서 마치고 저장 중 무엇으로 갈까요?"

## 하지 않는 것

- 해결책을 고르거나 순위를 매기지 않는다(maker-prioritization).
- 가설 문장을 대신 완성하지 않는다(hypothesis-framework). 재료만 넘긴다.
- 실험·지표를 설계하지 않는다(maker-experiment-design).
- 사용자가 주지 않은 수치, 인용, 원인을 만들지 않는다.
- 피드백 제공자에게 결과를 알리거나 피드백 수집 체계를 운영하지 않는다.
- 페르소나 정의, 아이디어 발산, 가치 제안 매핑 같은 별도 단계를 만들지 않는다. 필요하면 사용자에게 알리고 문제 정의서의 `확인 필요`에 적는다.
- 노션에 승인 없이 쓰지 않는다.
