# maker-problem-framing

피드백과 행동 데이터에서 출발해 풀 문제를 한 문장(문제 진술문)으로 정의하고, 그 문장을 "어떻게 하면 ~할 수 있을까(HMW)" 질문으로 바꿔 다음 단계에 넘기는 스킬입니다.

[SKILL.md](SKILL.md) · [설치](#설치) · 함께 쓰는 스킬: [hypothesis-framework](../hypothesis-framework/), [maker-prioritization](../maker-prioritization/), [maker-experiment-design](../maker-experiment-design/)

## 구성

maker-problem-framing은 문제 정의를 일곱 단계로 나눕니다. 상황에 따라 시작하는 곳은 다르지만, 끝은 언제나 5 → 6 → 7입니다.

1. **피드백 정리** — 여러 채널의 VOC를 모아 구조화하고, 빈도와 심각도로 파고들 문제 신호 하나를 고릅니다.
2. **JTBD** — 사용자가 어떤 상황에서 무엇을 이루려고 제품을 쓰는지 정의합니다.
3. **사용자 여정 맵** — 단계별 행동·접점·생각·감정을 펼쳐 문제가 몰린 지점을 찾습니다.
4. **5Why** — 근거를 붙여 "왜?"를 반복하고 구조 수준의 근본 원인을 정합니다.
5. **문제 진술문** — 사용자·상황·문제·영향·원인을 한 문장으로 잇습니다.
6. **HMW 전환** — 진술문을 해결을 여는 질문으로 바꾸고, 범위가 맞는 주 질문 하나를 고릅니다.
7. **문제 정의서** — 진술문, HMW, 근거, 가설 재료, 확인 필요 목록을 한 문서로 묶어 넘깁니다.

## 모드

### 피드백에서 시작

CS·리뷰·인앱 의견 원문을 받아 테마로 묶습니다. 기능 요청은 "무엇을 하려다 막혔는가"로 다시 적고, 상위 테마를 행동 데이터로 교차 확인한 뒤 하나만 다음 단계로 넘깁니다.

### 이탈 지점에서 시작

사용자 유형 하나와 시나리오 하나로 지금 상태의 여정 맵을 그립니다. 감정이 가장 낮은 단계와 이탈 데이터가 큰 단계를 겹쳐 보고, Pain Point를 해결책이 아닌 "기회 영역" 형태로 적습니다.

### 니즈에서 시작

인터뷰 기록이나 가이드로 Job을 기능적·감정적·사회적 관점으로 정의하고, 전환을 밀고 막는 네 힘(추진·끌림·습관·불안)을 정리합니다.

### 문장만 필요할 때

원인을 이미 알면 문제 진술문과 HMW만 만듭니다. 칸마다 근거를 묻고, 해결책 단어가 섞였는지, 문제가 둘 이상인지, 범위가 맞는지 점검합니다.

## 상황별 사용

### VOC나 CS가 쌓였는데 무엇이 문제인지 모를 때

채널마다 흩어진 원문을 하나의 문제 신호로 좁히는 상황입니다.

사용할 단계: 피드백 정리 → 5Why → 문제 진술문 → HMW

### 고쳐도 같은 CS가 다시 들어올 때

증상만 고쳐 온 상황입니다. CS만 따로 정리한 뒤 구조 원인까지 내려갑니다.

사용할 단계: 피드백 정리(CS) → 5Why → 문제 진술문 → HMW

### 이탈이나 전환 하락이 어디서 생기는지 모를 때

지표는 떨어졌는데 지점을 모르는 상황입니다.

사용할 단계: 사용자 여정 맵 → 5Why → 문제 진술문 → HMW

### 신규 기능 기획인데 사용자 니즈가 불분명할 때

만들 것보다 "왜 쓰는가"를 먼저 정해야 하는 상황입니다. 다음은 [maker-prioritization](../maker-prioritization/)으로 넘깁니다.

사용할 단계: JTBD → (여정 맵) → 문제 진술문 → HMW

## 가이드라인

### 추측으로 빈칸을 채우지 않습니다

사용자가 주지 않은 수치, 인용, 원인은 `[확인 필요: …]`로 남기고 어디서 확인할 수 있는지 제안합니다. 근거 없는 5Why 사슬은 그럴듯한 이야기일 뿐입니다.

### 한 번에 하나씩 묻습니다

필요한 정보를 한 질문에 하나씩, 가능하면 선택지로 묻습니다. 앞 단계 산출물이 있으면 채운 안을 먼저 보여 주고 확인받습니다.

### 진술문에는 해결책을 넣지 않습니다

"변경 버튼이 없다"가 아니라 "시간을 옮기는 도중 자리를 잃는다"로 씁니다. 해결책이 들어가면 HMW가 좁아져 다른 해법을 검토할 수 없습니다.

| 지양 | 권장 |
|---|---|
| 요청 원문 "변경 버튼 만들어 주세요"를 그대로 문제로 쓴다 | "무엇을 하려다 막혔는가"로 번역한다 |
| 피드백 건수가 많으니 많은 사용자가 겪는다고 본다 | 상위 테마를 행동 데이터로 교차 확인한다 |
| 여정 맵의 기회 영역에 "변경 기능 추가"를 쓴다 | "자리를 잃지 못한다 → 지킨 채 옮길 수 있다면"으로 쓴다 |
| 5Why 답에 근거 없이 다음 왜로 넘어간다 | 답마다 근거를 붙이고, 없으면 멈추고 확인 방법을 제안한다 |
| "어떻게 하면 이탈을 줄일까?"로 HMW를 끝낸다 | 근본 원인을 겨냥하도록 사용자와 상황을 좁힌다 |

표의 예는 "예약 시간 변경" 기능이 없는 가상의 예약 앱입니다.

### 끝은 항상 문제 정의서입니다

중간 단계만 쓰더라도 진술문과 HMW 칸이 비었다는 것을 알립니다. 다음 스킬은 이 문서를 그대로 입력으로 받습니다.

## maker-problem-framing vs hypothesis-framework

| | maker-problem-framing | hypothesis-framework |
|---|---|---|
| 하는 일 | 풀 문제를 정하고 질문으로 연다 | 검증할 가설 문장을 세운다 |
| 결과물 | 문제 진술문 + HMW가 담긴 문제 정의서 | 가설 한 문장 |
| 가설을 쓰는가 | 쓰지 않습니다. 대상·상황·문제·근거 재료만 넘깁니다 | 재료를 받아 사용자가 스스로 세우게 합니다 |

문제가 아직 흐리면 이 스킬로 시작하고, 문제 정의서가 나오면 hypothesis-framework로 넘깁니다. 후보 해결책의 순위는 [maker-prioritization](../maker-prioritization/), 실험 설계는 [maker-experiment-design](../maker-experiment-design/)이 맡습니다.

| 다음 단계 | maker-prioritization, hypothesis-framework, maker-experiment-design |
| 외부에 쓰는가 | 쓰지 않습니다. 노션 등록은 승인 후 notion-ops로 |
| 근거 | 2025년 5월에 만든 MAKER 프레임워크의 문제 정의 카테고리와 피드백 수집 및 활용 모듈 |

## 근거

2025년 5월에 만든 MAKER 프레임워크의 문제 정의 카테고리(5Why, 문제 진술문, 사용자 여정 맵, JTBD)를 실행 가능한 스킬로 옮겼습니다. 커뮤니케이션 카테고리의 피드백 수집 및 활용 모듈 중 수집·구조화·분석 부분을 입력 단계로 가져왔습니다. 원본은 읽는 문서였고, 옮기면서 다음을 고도화했습니다.

| 구분 | 내용 |
|---|---|
| 통일 | 문제 진술문 형식을 "사용자·상황·문제·영향 + 원인" 한 가지로 맞췄습니다. 원본은 카테고리 안내와 사례의 형식이 달랐습니다 |
| 통일 | 페이지마다 달랐던 모듈 흐름을 "시작점은 상황별, 끝은 진술문 → HMW → 문제 정의서"로 정리했습니다 |
| 통일 | 피드백 정리와 여정 맵의 Pain Point 판정에 같은 심각도 척도(불편·지연·실패)를 씁니다 |
| 보완 | 원본에 절차가 없던 사용자 여정 맵에 범위 정하기부터 인사이트까지 일곱 단계와 산출물 표를 채웠습니다 |
| 보완 | 선택 사항이던 HMW 전환을 독립 단계로 세우고, 변형 방법과 범위 점검(너무 넓음·좁음)을 붙였습니다 |
| 보완 | 모든 단계에 입력 → 출력 계약을 두고, 다음 스킬이 받는 칸을 문제 정의서에 고정했습니다 |
| 보완 | 진술문 점검 항목(중립성, 단일 초점, 범위, 근거, JTBD 일치)과 5Why의 "근거 없으면 멈춤" 규칙을 넣었습니다 |
| 사례 교체 | 원본의 실제 회사 사례와 출처 없는 성과 수치를 모두 빼고, 가상의 예약 앱 하나로 전 단계를 이었습니다 |
| 정리 | 원본이 가리키지만 존재하지 않는 모듈(페르소나 정의, 아이디어 발산, 가치 제안 매핑, 루트 코즈 분석)은 연결하지 않았습니다 |

## 검증

함정을 심은 가상의 밀키트 구독 앱 자료로 피드백 정리부터 문제 정의서까지 돌렸습니다.

- **재료** — 피드백 15건(문제를 숨긴 기능 요청 4건, "메뉴가 적다"와 "많다"처럼 서로 반대인 의견 한 쌍), 신규 가입 코호트 퍼널(4주차 유지 값 누락), 퍼널과 어긋나는 보고서 해지율, "해지 화면에 건너뛰기 옵션이 없다"는 기획 메모, 근거 없는 "푸시를 꺼 둬서" 회의 메모.
- **요청** — "구독 해지가 늘었어, 어떻게 접근해야 할지 모르겠어."
- **통과** — 기능 요청을 "무엇을 하려다 막혔는가"로 번역했습니다. 반대 의견은 합산하지 않고 양쪽을 따로 적었습니다. 5Why에서 근거 없는 답에 `[확인 필요]`를 달고 그 갈래를 멈췄으며, 팀이 바꿀 수 있는 정책에서 근본 원인을 잡았습니다. 해결책이 든 기획 메모는 중립성 점검에서 걸러 후보 메모로 옮겼습니다. 어긋난 두 해지율은 둘 다 적고 정의를 물었고, 누락된 유지율은 다른 지표에서 역산하지 않았습니다.
- **확인하지 못한 것** — 실제 VOC 규모(수백 건)에서의 테마 묶기, JTBD 경로, 팀 합의 과정, 노션 등록.

## 설치

```bash
mkdir -p ~/.claude/skills/maker-problem-framing && cp SKILL.md ~/.claude/skills/maker-problem-framing/
```

한 프로젝트에만 쓰려면 저장소 안의 `.claude/skills/maker-problem-framing/`에 둡니다. 다음 세션부터 Claude가 알아서 꺼내 씁니다.

가설 단계까지 이어 쓰려면 [hypothesis-framework](../hypothesis-framework/)도 함께 설치합니다.

## 범위와 한계

- 문제를 정의하는 데까지만 다룹니다. 해결책 평가, 가설 문장 완성, 실험 설계는 다른 스킬로 넘깁니다.
- 피드백 수집 체계를 설계·운영하거나 피드백 제공자에게 결과를 알리는 일은 다루지 않습니다.
- 인터뷰와 데이터 분석을 대신하지 않습니다. 받은 자료를 구조화하고, 빈 곳을 확인할 질문으로 바꿉니다.
- 심각도 척도와 HMW 변형 방법은 일반적으로 쓰이는 방식을 단순화한 것이라 팀 기준이 있으면 그쪽이 우선입니다.
- 효과를 수치로 재지는 않았습니다.
