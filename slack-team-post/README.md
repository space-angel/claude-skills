# slack-team-post

첫 줄만 읽어도 할 일이 보이는 팀 슬랙 메시지를 쓰는 스킬입니다.

[SKILL.md](SKILL.md) · [설치](#설치) · 함께 쓰는 스킬: [team-status-report](../team-status-report/) · [decision-first-article](../decision-first-article/) · [ko-tech-prose](../ko-tech-prose/)

## 구성

slack-team-post는 메시지를 네 단계로 씁니다.

1. **유형 정하기** — 여덟 유형 중 하나를 고릅니다. 애매하면 가장 가까운 것을 고르고 따로 묻지 않습니다.
2. **결론을 첫 줄에** — 그 유형의 템플릿을 따라 씁니다.
3. **코드블록에 담기** — 바로 붙여넣을 수 있게 코드블록으로 줍니다.
4. **모르는 건 비워 두기** — 링크나 담당자처럼 확인되지 않은 것은 `<링크>`, `OO님` 같은 자리표시로 남기고 알립니다.

## 모드

유형마다 첫 줄에 올 것을 정해 둡니다. 나머지는 그 아래 한 줄에 한 가지씩 붙입니다.

### 결정 사항 공지

첫 줄에 무엇을 어떻게 하기로 했는지 씁니다. 그 아래에 이유, 바뀌는 것, 위키·이슈 기록 링크를 붙입니다.

### 배포 공유

첫 줄에 무엇을 배포했는지와 사용자가 체감하는 변화를 씁니다. 바뀐 점은 1~3개로 줄이고, 커밋 목록을 그대로 옮기지 않습니다. 배포 범위를 모르면 바뀐 점을 비워 두고 묻습니다.

### 팀원에게 묻는 질문

첫 줄에 질문 하나를 씁니다. 그 아래에 내가 확인한 현재 상태와 이걸 알아야 하는 이유를 붙입니다. 예/아니오나 짧은 답으로 끝날 수 있게 묻습니다.

### PO에게 결정 요청

첫 줄에 무엇을 정해야 하는지와 무엇이 막혀 있는지 씁니다. 결정마다 현재 상태, 선택지, 정해지면 무엇이 진행되는지를 고정합니다. 선택지는 코드를 몰라도 고를 수 있게 결과로 씁니다.

### 위키·이슈 변경 공지

첫 줄에 무엇을 어디에 반영했는지 씁니다. 그 아래에 "이전 → 지금", 확인해야 할 사람, 링크를 붙입니다.

### 데일리 리포트

끝낸 것, 진행 중, 막힌 것을 개조식으로 컴팩트하게 씁니다. 비개발자도 읽는 채널이면 작업 이름 대신 결과를 씁니다.

### 설문

첫 줄에 무엇에 대해 언제까지 이모지로 답해 달라는지 씁니다. 선택지는 서로 겹치지 않게 4개 이하로 둡니다.

### 동료 의견에 다는 답글

이 유형만 형식이 다릅니다. 이름을 부르지 않고, 불릿으로 나누지 않고 줄글로 씁니다. 칭찬으로 감싸지 않고 내 입장을 첫 문장에 씁니다.

## 상황별 사용

### 회의에서 결정이 난 직후

정해진 내용을 회의에 없던 팀원에게도 알려야 하는 상황입니다.

사용할 모드: 결정 사항 공지

### 배포를 마쳤을 때

무엇이 나갔고 사용자에게 무엇이 달라지는지 팀에 공유하는 상황입니다.

사용할 모드: 배포 공유

### 결정이 없어 작업이 막혔을 때

PO가 코드를 몰라도 고를 수 있게 현재 상태와 선택지를 올리는 상황입니다.

사용할 모드: PO에게 결정 요청

### 팀원에게 하나만 확인하면 될 때

구현 여부처럼 짧은 답으로 끝날 질문을 던지는 상황입니다.

사용할 모드: 팀원에게 묻는 질문

### 현황 문서를 팀 채널에 알릴 때

긴 현황 정리를 채널에 올릴 짧은 메시지로 옮기는 상황입니다. 현황 문서는 team-status-report가 쓰고, 첫 줄과 줄 나눔은 이 스킬이 잡습니다.

함께 쓰는 스킬: [team-status-report](../team-status-report/)

## 가이드라인

### 결론이 첫 줄입니다

무엇이 정해졌나, 무엇이 나갔나, 무엇을 묻나를 먼저 씁니다. 배경부터 쓰면 슬랙에서는 아무도 끝까지 읽지 않습니다.

### 짧게는 줄 수를 줄이라는 뜻이 아닙니다

한 줄에 한 가지만 씁니다. 줄이 하나 늘어도 읽기 쉬운 쪽을 고릅니다. "두 줄 말고 세 줄로, 가독성 좋게"라는 교정에서 나온 규칙입니다. 답글 유형은 예외로 줄글로 씁니다.

### 결정 요청에는 세 칸을 고정합니다

현재 상태, 선택지, 무엇이 결정되는지가 다 있어야 합니다. 결정이 여러 개면 번호를 붙여 하나씩 나눕니다.

| 지양 | 권장 |
|---|---|
| "## 배경"부터 시작해 지난주 논의를 정리한다 | "예약 변경 알림을 어떻게 보낼지 정해야 해요. 이게 정해져야 알림 작업을 시작해요"를 첫 줄에 둔다 |
| 현재 상태를 빼고 의견만 묻는다 | "지금: 예약 시간이 바뀌어도 알림이 안 가요"를 붙인다 |
| 선택지를 구현 방식으로 쓴다 | "A. 시간이 바뀔 때만 알림 — 알림 수가 적어요 / B. 모든 변경에 알림 — 놓치는 변경은 없지만 알림이 많아요"처럼 결과로 쓴다 |
| 결정 뒤에 무엇이 진행되는지 뺀다 | "정해지면: 알림 문구와 화면 작업을 바로 시작해요"를 붙인다 |

표의 예는 가상의 예약 앱 팀에서 PO에게 알림 방식 결정을 요청하는 메시지입니다.

### 어조는 담백한 평서문입니다

"~해요", "~입니다"로 씁니다. "혹시… 괜찮으시다면… 부탁드려도 될까요?" 같은 과하게 조심스러운 말투는 지양합니다.

### 바꾼 것에는 링크를 붙이고, 모르는 것은 지어내지 않습니다

위키·이슈·PR·문서를 바꿨으면 링크를 넣습니다. 확인되지 않은 링크, 일정, 수치, 담당자는 자리표시로 남깁니다.

### 슬랙 서식을 따르고, 보내지 않습니다

굵게는 `*별표 하나*`이고, 제목(`#`)과 표는 쓰지 않습니다. 슬랙 커넥터가 연결돼 있어도 사용자가 보내 달라고 명시하기 전에는 보내지 않습니다. 명시했더라도 채널과 최종 문구를 한 번 확인받습니다. 팀에 나가는 말은 되돌리기 어렵고, 사용자 이름으로 남기 때문입니다.

## slack-team-post vs team-status-report

| | slack-team-post | team-status-report |
|---|---|---|
| 하는 일 | 짧은 메시지의 형식과 순서를 잡는다 | 트래커·GitHub·위키를 읽고 현황 문서를 쓴다 |
| 출처를 읽는가 | 읽지 않는다. 대화에서 확인된 사실만 쓴다 | 세 출처를 직접 읽고 대조한다 |
| 결과물 | 코드블록에 담긴 붙여넣기용 메시지 | `.md` 현황 문서, 요청 시 슬랙용 짧은 버전 |

긴 현황 정리는 team-status-report가 맡고, 팀 채널에 올릴 짧은 메시지의 첫 줄과 줄 나눔은 slack-team-post가 맡습니다.

## 명세

| 항목 | 내용 |
|---|---|
| 요청 예시 | "슬랙에 이거 배포한 거 공유하는 메시지 좀" · "해당 결정 사항 답변을 슬랙 메시지용으로 작성 좀" · "OO님한테 reflected 함수가 구현되어 있는지 물어보는 슬랙 메시지 좀" · "해당 두 가지를 PO 입장에서 결정 도움을 위해 슬랙에서 물어보는 코멘트 좀" · "슬랙 공지 글도 작성 부탁" |
| 입력 | 대화에서 확인된 사실(결정, 배포 내용, 링크, 받는 사람) |
| 출력 | 코드블록에 담긴 메시지. 길이 차이가 큰 두 안이 다 그럴듯하면 짧은 안과 긴 안 |
| 필요한 연결 | 없습니다. 슬랙 커넥터 없이 동작합니다 |
| 외부에 쓰는가 | 쓰지 않습니다. 명시적으로 부탁받으면 채널과 문구를 확인받은 뒤에만 보냅니다 |
| 근거 | 여러 프로젝트에서 슬랙 메시지 초안을 고친 교정 |
| 검증 | 가상 팀 시나리오 테스트 |

## 근거

아래 규칙은 여러 프로젝트에서 팀 슬랙 메시지를 쓰며 초안을 고쳐 달라고 한 방향에서 나왔습니다.

| 규칙 | 근거 |
|---|---|
| 결론이 첫 줄 | 쉽고 컴팩트하게, 결론 먼저 |
| 한 줄에 한 가지. 짧게가 곧 줄 수를 줄이라는 뜻은 아니다 | "두 줄 말고 세 줄로 가독성 좋게" |
| 결정 요청 템플릿에 세 칸을 고정 | 질문에 현재 상태, 선택지, 무엇이 결정되는지가 빠짐 |
| 변경 공지에는 링크를 붙인다 | 위키나 이슈를 바꿨는데 공지에 링크가 없음 |
| 답글은 이름 없이 줄글로 | "이름 언급해서 답변하지 말고 내가 하고 싶은 말 솔직하게 의견 다는 식으로", "나누지 말고 줄글로" |
| 담백한 평서문 어조 | 지나치게 조심스러운 말투 |

## 검증

가상의 팀에서 세 가지를 차례로 요청하는 시나리오 테스트를 했습니다.

- **재료** — 가상의 팀과 세 가지 상황. 알림 설정 페이지 배포, 안 읽은 알림 뱃지(숫자/점) 결정, 팀원의 온보딩 알림 제안.
- **요청** — 배포 공유 메시지, PO에게 뱃지 방식 결정 요청, 온보딩 알림 제안에 대한 답글.
- **통과** — 세 메시지 모두 결론이 첫 줄에 왔습니다. 확인되지 않은 PR 링크·PO 이름·기한은 자리표시로 남겼습니다. 답글은 이름 없이 줄글로 나왔습니다. 아무것도 보내지 않았습니다.
- **확인하지 못한 것** — 실제 슬랙에 붙여넣었을 때 들여쓰기와 `•`가 그대로 보이는지, 실제 팀원과 PO의 반응. 테스트는 한 번뿐이라 다른 모델이나 다른 요청에서 같은 결과가 나오는지도 확인하지 못했습니다.

## 설치

```bash
cp -r slack-team-post ~/.claude/skills/
```

한 프로젝트에만 쓰려면 레포 안의 `.claude/skills/slack-team-post/`에 둡니다. 사전 준비는 없고, 슬랙 커넥터 없이 동작합니다. "슬랙 공지 글도 작성 부탁"처럼 한국어로 부탁하는 요청에 걸리도록 `SKILL.md`와 템플릿도 한국어로 썼습니다.

긴 글이나 작업 회고는 [decision-first-article](../decision-first-article/), 문장 단위 교정은 [ko-tech-prose](../ko-tech-prose/)가 맡습니다.

## 범위와 한계

- 짧은 메시지의 형식과 순서만 다룹니다. 슬랙 캔버스나 긴 공지 문서는 대상이 아닙니다.
- 측정이 아닙니다. 실제 업무 요청과 교정 기록에서 패턴을 뽑았습니다.
- 이 템플릿을 쓴 메시지가 더 많이 읽히거나 답이 빨리 온다는 것을 따로 잰 적은 없습니다.
- 팀마다 슬랙 문화가 다릅니다. 존댓말 수위나 이모지 쓰임은 팀에 맞게 고쳐 씁니다.
