# decision-first-article

끝낸 작업을 "왜 그렇게 정했나"가 남는 엔지니어링 아티클로 정리하는 스킬입니다.

[SKILL.md](SKILL.md) · [설치](#설치) · 함께 쓰는 스킬: [ko-tech-prose](../ko-tech-prose/)

## 구성

decision-first-article은 결정 목록부터 뽑고, 결정 하나를 섹션 하나로 씁니다.

1. **결정 뽑기** — 대화·커밋·문서에서 결정과 "틀렸다가 고친 지점"을 찾습니다.
2. **숫자 다시 세기** — 인용할 숫자를 원본 산출물에서 확인합니다. 못 찾으면 쓰지 않고 묻습니다.
3. **금지 주장 목록** — 이 작업에 맞는 "하면 안 되는 주장" 목록을 쓰기 전에 만듭니다.
4. **결정 우선 구조로 쓰기** — 섹션은 결정으로 시작해 근거로 이어집니다. 도입은 구체적인 장면 하나로 엽니다.
5. **구조 점검** — 소제목만, 섹션 첫 두 문장만 뽑아 읽고 체크리스트에 대조합니다.

결과물은 넷입니다. 아티클 본문, 이미지 제안 목록, 체크리스트 대조 결과, 다시 세지 못한 숫자 목록입니다.

## 상황별 사용

### 스프린트나 프로젝트가 끝났을 때

끝낸 작업에서 무엇을 고르고 무엇을 버렸는지 글로 남기는 상황입니다. 사람과 팀의 행동을 돌아보는 회고는 [evidence-based-retro](../evidence-based-retro/)가 맡습니다.

함께 쓰는 스킬: [evidence-based-retro](../evidence-based-retro/)

### 다른 대화나 인계 메모를 받아 글을 쓸 때

요약을 거친 숫자가 원본과 어긋날 수 있는 상황입니다. 인용할 숫자를 원본 산출물에서 다시 세고, 못 찾은 숫자는 묻습니다.

중점 단계: 2. 숫자 다시 세기

### 포트폴리오나 공개 블로그에 올릴 때

"그래서 왜 그렇게 했나"에 답해야 하고, 내부 이름이나 실명이 남으면 안 되는 상황입니다.

중점 단계: 3. 금지 주장 목록

### 아티클 초안을 다 쓰고 문장까지 다듬을 때

서사 구조는 잡혔고 번역체나 긴 문장을 고칠 상황입니다.

함께 쓰는 스킬: [ko-tech-prose](../ko-tech-prose/)

## 가이드라인

### 결과 보고서가 아니라 결정의 기록으로 씁니다

"지표 → 결과 → 특징" 순서로 쓰지 않습니다. 무엇을 고민했고 어떻게 결정했는지가 드러나야 합니다. 포트폴리오로 쓰는 글은 "그래서 왜 그렇게 했나"에서 방어가 되어야 하기 때문입니다.

### 소제목은 문장이나 질문으로 씁니다

소제목만 이어 읽어도 줄거리가 보이게 씁니다. 숫자는 결정을 뒷받침할 때만 넣습니다. 표는 2~3개까지이고, 나머지는 산문입니다.

| 지양 | 권장 |
|---|---|
| 평가 지표 | 점수를 하나로 합치지 않기로 했습니다 |
| 결과 | 그래서, 지난번 결과는요? |
| 트러블슈팅 | 원인을 잘못 짚을 뻔했습니다 |
| 한계 | 아직 모르는 것 |
| "F1은 정밀도와 재현율의 조화평균으로… (세 문단 뒤) …그래서 합치지 않았습니다." | "점수를 하나로 합치지 않았습니다. 저희에게 두 실패의 무게가 다르기 때문입니다." |

표의 예는 같은 작업을 정리한 두 초안의 소제목과 첫 문장입니다(가상의 예).

### 넘겨받은 숫자는 원본에서 다시 센 뒤 인용합니다

아티클은 앞선 대화나 요약된 인계 메모를 바탕으로 쓰는 경우가 많습니다. 요약을 거친 숫자는 원본과 어긋날 수 있고, 숫자 하나가 틀리면 글 전체의 신뢰가 무너집니다. 넘겨받은 값과 원본이 다르면 원본 값을 쓰고, 두 값을 확인 목록에 남깁니다.

### "하면 안 되는 주장"을 쓰기 전에 정합니다

쓰기 전에 목록을 만들고, 다 쓴 뒤 대조합니다. 한 번 잰 결과를 일반화하거나 조건부 결과를 무조건처럼 쓰는 실수를 막습니다. 작은 차이를 "이겼다"로 쓰지 않습니다.

### 장면은 재료에 있는 것만 씁니다

도입은 구체적인 장면 하나로 엽니다. 재료에 없는 장면이나 일화를 지어내지 않고, 없으면 묻습니다.

### "실패"가 아니라 "씨름하고 배운 것"으로 씁니다

틀렸다가 고친 일은 숨기지 않고, 알아챈 과정과 바로잡은 과정을 씁니다. 한계는 "아직 모르는 것"에 모으고 앞세우지 않습니다. 어미는 ~요/~습니다를 쓰고, 비개발자가 읽을 수 있는 어휘를 씁니다.

## decision-first-article vs evidence-based-retro

| | decision-first-article | evidence-based-retro |
|---|---|---|
| 하는 일 | 끝낸 작업의 결정과 근거를 이야기로 쓴다 | 회고와 팀원 피드백을 산출물 근거로 쓴다 |
| 중심 | 무엇을 골랐고 무엇을 버렸나 | 누가 무엇을 했고 다음엔 무엇을 바꿀까 |
| 결과물 | 아티클 본문, 이미지 제안, 체크리스트 대조 결과 | KPT, 팀원별 피드백, 내 역할 회고 |

작업의 결정을 글로 남길 때는 decision-first-article을, 사람과 팀의 행동을 돌아볼 때는 evidence-based-retro를 씁니다.

## 근거

아래 규칙은 끝낸 작업을 아티클로 정리하며 초안을 받은 뒤 고쳐 달라고 한 방향에서 나왔습니다.

| 규칙 | 근거 |
|---|---|
| 결과 보고 구조로 쓰지 않기 | "지표 → 결과 → 특징" 초안을 무엇을 고민했고 어떻게 결정했는지 드러나게 바꿔 달라는 교정이 반복됐습니다 |
| 문장·질문형 소제목 | 소제목을 문장이나 질문으로 바꿔 달라는 교정 |
| 표 2~3개, 나머지 산문 | 표가 많은 초안을 산문으로 줄여 달라는 교정 |
| ~요/~습니다, 비개발자 어휘 | 어미와 어휘를 바꿔 달라는 교정 |
| "씨름하고 배운 것" 프레이밍 | 한계만 앞세우지 말라는 교정 |
| 숫자 대신 접근 방식 | 숫자를 늘어놓지 말고 접근 방식을 보여 달라는 교정 |
| 이미지는 필요한 곳에만, 제안으로 | 이미지 자리를 제안으로 남겨 달라는 교정 |
| 숫자 다시 세기, 금지 주장 체크리스트 | 요약을 거친 맥락에서 쓰는 작업 방식에서 나온 규칙입니다 |

측정이 아니라 교정에서 나온 규칙입니다. 이 규칙을 적용한 글이 더 잘 읽힌다는 것은 따로 재지 않았습니다.

## 검증

가상의 작업 기록으로 시나리오 테스트를 했습니다. 작은 팀이 상품 추천 방식(규칙 기반과 임베딩 유사도)을 고른 작업입니다.

- **재료** — 작업 로그, 인수인계 메모, 원본 결과 CSV. 메모에는 원본과 어긋나는 숫자 하나를 심었습니다. 임베딩 클릭률이 메모에는 4.8%, 원본에는 2,176/51,800 = 4.2%입니다.
- **요청** — "아티클 형식으로 정리해 줘, 포트폴리오에도 쓸 거야."
- **통과** — 숫자 다시 세기 단계에서 어긋난 값을 잡았습니다. 결정 목록 3개 추출, 문장형 소제목, 결정이 먼저 오는 문단, 표 0개, 근거 자료 절, 이미지 제안 형식이 규칙대로 나왔습니다.
- **확인하지 못한 것** — 실제 작업 기록에 쓴 결과(가상 재료 한 건만 돌렸습니다), 사용자에게 묻는 단계의 실제 응답, 실제 독자나 채용 담당자의 반응, 트리거 문구가 실제로 이 스킬을 부르는지, `ko-tech-prose`로 넘기는 흐름.

## 설치

```bash
cp -r decision-first-article ~/.claude/skills/
```

한 프로젝트에만 쓰려면 저장소 안의 `.claude/skills/decision-first-article/`에 둡니다. 사전 준비는 없습니다.

아티클은 이 스킬로 쓰고, 문장은 [ko-tech-prose](../ko-tech-prose/)로 다듬는 순서를 권장합니다.

## 범위와 한계

- 서사 구조만 다룹니다. 문장 단위 교정은 `ko-tech-prose`가 맡습니다.
- "끝낸 작업을 이야기로 정리하는" 한 가지 용도입니다. 문서 유형 선택이나 API 문서·가이드 같은 다른 기술 문서에는 일반 테크니컬 라이팅 스킬이나 쉬운 한국어 문서 스킬이 더 맞습니다.
- 공개용 글이면 내부 이름·실명·이슈 키가 남지 않았는지 체크리스트에서 한 번 더 봅니다. 공개 여부는 스킬이 정하지 않고 사용자에게 묻습니다.
- 한 사람의 기록에서 나온 규칙이라 다른 독자층이나 다른 팀 블로그 문체에는 그대로 맞지 않을 수 있습니다.
