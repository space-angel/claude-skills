# 결정이 먼저 오는 엔지니어링 아티클

## 이 스킬의 전제

**아티클은 결과 보고서가 아니다. 결정의 기록이다.**

수치만 늘어놓은 글은 "그래서 왜 그렇게 했나"에 답하지 못한다. 읽는 사람이 남는 건 결정과, 기각한 대안과, 그 사이의 근거다. 이 글이 포트폴리오로 쓰일 때 방어선이 되는 것도 그 부분이다.

사용자가 실제로 고쳐 달라고 한 방향은 하나로 모인다. "지표 설명 → 결과 → 특징" 순서로 쓴 초안을 "내가 무엇을 고민했고 어떻게 결정했는지 논리적 근거가 드러나게"로 바꿔 달라는 것이다. 이 스킬은 처음부터 그쪽으로 쓴다.

## 쓰기 전에 — 재료를 모은다

1. **결정 목록을 뽑는다.** 대화, 커밋, 문서, 결정 기록에서 "A 대신 B로 했다"를 찾는다. 결정마다 한 줄로 적는다: 무엇을 골랐나 / 무엇을 버렸나 / 왜.
2. **틀렸다가 고친 지점을 찾는다.** 원인을 잘못 짚었다가 바로잡은 일, 조용히 틀릴 뻔한 일. 글에서 가장 반응이 좋은 부분이 대개 여기다.
3. **숫자를 다시 센다.** 대화나 다른 에이전트가 넘겨준 숫자는 인용하기 전에 원본 산출물(리포트, 로그, 데이터 파일, 스크립트 출력)에서 직접 다시 확인한다. 못 찾은 숫자는 쓰지 않거나 "확인 필요"로 표시해 사용자에게 묻는다. 넘겨받은 값과 원본이 다르면 본문에는 원본 값을 쓰고, 두 값과 계산식을 출력의 확인 목록에 남겨 사용자에게 묻는다.
4. **"하면 안 되는 주장" 목록을 만든다.** 아래 체크리스트 절 참고. 쓰기 전에 만들고, 다 쓴 뒤 대조한다.
5. **독자를 정한다.** 기본값은 "비개발자도 읽을 수 있는 동료"다. 사용자가 다르게 말하면 따른다.

결정이 3개 미만이면 아티클 감이 아닐 수 있다. 그때는 사용자에게 짧은 회고나 결정 기록으로 갈지 묻는다.

## 구조

### 뼈대

```markdown
# <질문형 또는 이야기형 제목> — <한 줄 부제>

**날짜 · 무슨 작업 · 이 글의 수치는 <근거 위치>에 있습니다**

---

<도입: 구체적인 장면 하나로 시작한다. 무엇을 만들고 있었고, 왜 이 결정을 해야 했나.>

## <결정 1을 문장으로>
## <결정 2를 문장으로>
## <틀릴 뻔한 것 / 잘못 짚었던 것>
## 그래서 무엇을 골랐나
## 아직 모르는 것
## 정리하면

**근거 자료** — 수치와 결정의 출처 목록
```

공개용 글이면 `<근거 위치>`에 내부 파일 경로 대신 자료 이름("A/B 결과 집계표, 9/17~9/23")을 쓴다.

섹션 수와 순서는 작업에 맞춘다. 고정된 건 "결정 섹션이 본문의 대부분"이라는 점뿐이다.

### 소제목은 문장이나 질문이다

| 피한다 | 쓴다 |
|---|---|
| 평가 지표 | 점수를 하나로 합치지 않기로 했습니다 |
| 결과 | 그래서, 지난번 결과는요? |
| 트러블슈팅 | 원인을 잘못 짚을 뻔했습니다 |
| 한계 | 아직 모르는 것 |

소제목만 이어 읽어도 글의 줄거리가 나와야 한다. 다 쓴 뒤 소제목만 뽑아서 확인한다.

### 문단은 결정이 먼저다

각 섹션의 첫 한두 문장에 결정을 쓴다. 근거는 그 뒤에 온다.

- 나쁨: "F1은 정밀도와 재현율의 조화평균으로… (세 문단 뒤) …그래서 합치지 않았습니다."
- 좋음: "점수를 하나로 합치지 않았습니다. 저희에게 두 실패의 무게가 다르기 때문입니다. (그 뒤에 각 지표 설명)"

기각한 대안을 함께 적는다. "B를 골랐다"보다 "A가 자연스러워 보였지만 B를 골랐다, 왜냐하면"이 근거가 된다.

### 도입은 장면으로 연다

배경 설명("최근 LLM의 발전으로…")으로 시작하지 않는다. 사용자가 실제로 보게 될 화면, 실제 입력 한 건, 실제로 막혔던 순간 하나로 시작한다. 장면은 재료(로그, 대화, 문서)에 있는 것만 쓴다. 재료에 없는 상품명, 날짜, 대사, 감정을 덧붙여 장면을 만들지 않는다. 쓸 만한 장면이 없으면 사용자에게 하나 묻는다.

## 문체

- **어미는 ~요/~습니다.** 두 어미를 섞어도 된다. 평서문 "~다"는 쓰지 않는다.
- **비개발자가 읽을 수 있는 어휘.** 전문 용어는 처음 나올 때 한 문장으로 풀어 쓴다. 지표 이름보다 "낮으면 무슨 일이 생기나"를 먼저 쓴다.
- **산문 위주.** 표는 정말 나란히 비교해야 하는 것 2~3개까지. 표로 갈 내용이 문장 세 개로 설명되면 문장으로 쓴다.
- **숫자를 늘어놓지 않는다.** 숫자는 결정을 뒷받침할 때만 넣는다. 한 문단에 숫자가 셋을 넘으면 그중 하나만 남기고 나머지는 근거 자료로 보낸다. 독자에게 보여줄 건 숫자보다 접근 방식이다.
- **굵게는 문단당 한 곳 정도.** 결정이나 핵심 결과에만.

## 프레이밍 — "실패"가 아니라 "씨름하고 배운 것"

포트폴리오로 쓰이는 글이다. 한계만 앞세우면 글 전체가 사과문이 된다.

- 틀렸다가 고친 일은 **숨기지 않는다.** 대신 "제가 실패했습니다"가 아니라 "원인을 잘못 짚을 뻔했습니다 → 이렇게 알아챘고 → 이렇게 바로잡았습니다" 순서로 쓴다. 알아챈 과정이 실력이다.
- 한계는 "아직 모르는 것" 섹션에 모은다. 본문 곳곳에 "다만…", "아쉽게도…"를 흩뿌리지 않는다.
- 반대로 과장하지도 않는다. 프레이밍은 순서와 강조의 문제지 사실을 바꾸는 게 아니다.

## 이미지와 다이어그램

필요한 곳에만 넣는다. 글로 세 문장이 넘게 걸리는 흐름, 구조, 전후 비교일 때만이다.

직접 만들 수 없으면 자리를 제안한다. 본문에 이렇게 남긴다.

```markdown
> [이미지 제안] <무엇을 보여줄지> — <왜 여기서 필요한지>
```

마지막에 제안 목록을 따로 정리해 사용자에게 준다. 넣을지 말지는 사용자가 정한다.

## 하면 안 되는 주장 — 체크리스트

쓰기 전에 이 작업에 맞게 목록을 만든다. 기본 항목은 이렇다.

- [ ] 한 번 잰 결과를 일반적인 사실처럼 쓰지 않았나 ("항상", "확실히")
- [ ] 측정하지 않은 개선 폭을 쓰지 않았나 ("훨씬 빨라졌다" — 몇 배인가, 쟀나)
- [ ] 조건부로 성립하는 걸 무조건처럼 쓰지 않았나 (데이터 규모, 설정, 버전)
- [ ] 다른 사람이 한 일을 내가 한 것처럼 쓰지 않았나
- [ ] 인과를 확인 안 했는데 "때문에"라고 쓰지 않았나
- [ ] 차이가 작은데 "이겼다", "더 낫다"고 쓰지 않았나 (유의성을 확인 안 했으면 "차이가 작았다"로)
- [ ] 재료에 없는 장면, 대사, 일화를 살붙이기로 지어내지 않았나
- [ ] 넘겨받은 숫자를 원본에서 다시 세지 않고 썼나
- [ ] 내부 이름, 동료 실명, 고객사, 이슈 키, 내부 경로가 공개용 글에 남았나 (공개 여부는 사용자에게 확인)

작업 고유 항목을 더한다. 예: "이 모델이 다른 데이터에서도 이긴다고 말하지 않는다", "정답지가 사람이 만든 것이라고 말하지 않는다".

다 쓴 뒤 본문 전체를 이 목록에 대조한다. 걸린 문장은 고치거나 조건을 붙인다.

## 마무리 점검

1. 소제목만 뽑아 읽는다 — 줄거리가 되나
2. 각 섹션 첫 두 문장만 읽는다 — 결정이 보이나
3. 표 개수 — 3개 이하인가
4. 체크리스트 대조 — 걸린 게 없나
5. 숫자마다 출처가 있나 — 근거 자료 절에 위치가 있나

## 출력

- 아티클 본문 (마크다운). 파일로 달라고 하면 파일로 쓴다.
- 이미지 제안 목록 (있으면)
- 체크리스트 대조 결과 한 줄 — "걸린 것 없음" 또는 고친 항목
- 다시 세지 못한 숫자 목록 (있으면) — 사용자에게 확인을 요청한다

## 다른 스킬과의 분담

이 스킬은 **서사 구조**를 맡는다. 문장 단위 교정(번역체, 이중피동, 긴 문장)은 `ko-tech-prose`에 맡긴다. 아티클을 다 쓴 뒤 사용자가 문장까지 봐 달라고 하면 그쪽으로 넘긴다.
