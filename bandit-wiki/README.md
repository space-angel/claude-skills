# bandit-wiki

팀이 정한 결정 사항을 git 저장소 안의 `.wiki/` 하나에 버전과 함께 남기고, 바뀔 때마다 목차·CHANGELOG·에이전트 규칙 파일을 다시 만드는 스킬입니다.

[SKILL.md](SKILL.md) · [설치](#설치) · [hooks](hooks/README.md) · 함께 쓰는 스킬: [bandit-issue-link](../bandit-issue-link/)

## 구성

bandit-wiki는 결정 하나가 남고 바뀌는 과정을 다섯 부품으로 나눕니다.

1. **원본 자료** — 회의 메모, 대화 발췌, PR 요약을 `.wiki/sources/`에 그대로 둡니다. 결정 후보의 근거가 됩니다.
2. **결정 파일** — `.wiki/decisions/<영역>.md`. 사람이 읽고 PR로 고칠 수 있는 결정의 현재 상태입니다.
3. **버전 기록** — `.wiki/history.jsonl`. 버전마다 한 줄씩 붙기만 하는(append-only) 기록입니다.
4. **생성물** — 목차(INDEX), CHANGELOG, `CLAUDE.md`·`AGENTS.md`의 관리 블록, `.claude/rules/`·`.cursor/rules/` 규칙 파일. 모두 기록에서 다시 만듭니다.
5. **스크립트** — `scripts/wiki.py`. 검사, 버전, 생성, 영향 계산, 지표를 맡습니다. Python 3.9 이상 표준 라이브러리만 씁니다.

## 설계

### 세 층

구조는 Andrej Karpathy의 [LLM Wiki 패턴](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)에서 출발했습니다. 원본 자료는 고치지 않고, 에이전트가 원본을 읽어 위키를 쌓고, 목차를 먼저 읽은 뒤 필요한 페이지만 엽니다. 이 패턴을 팀 결정 사항에 맞게 세 층으로 나눴습니다.

| 층 | 위치 | 누가 쓰는가 | 성격 |
|---|---|---|---|
| 원본 | `.wiki/sources/` | 사람이 넣습니다 | 고치지 않습니다. 결정 후보의 근거입니다 |
| 결정과 기록 | `.wiki/decisions/`, `history.jsonl`, `links.jsonl`, `acks.jsonl` | 스크립트가 씁니다. 결정 파일은 사람도 PR로 고칩니다 | 유일한 원본입니다 |
| 생성물 | `INDEX.md`, `CHANGELOG.md`, `CLAUDE.md` 블록, 규칙 파일 | 스크립트만 씁니다 | 맨 위에 "생성됨" 표시가 붙습니다. 손으로 고치면 검사가 알립니다 |

LLM Wiki의 스키마 층(위키를 어떻게 다룰지 적은 지시문)은 이 스킬의 `SKILL.md`와 `.wiki/config.json`이 맡습니다.

### 결정적인 일은 스크립트, 판단은 Claude

같은 입력에 같은 결과가 나와야 하는 일은 스크립트가 하고, 문장을 읽고 사람에게 물어야 하는 일은 Claude가 합니다. 반딧에서는 같은 검사 규칙이 세 곳에 따로 구현돼 있어 하나를 고치면 셋을 맞춰야 했습니다. 이 스킬에서는 규칙이 `wiki.py` 한 곳에만 있습니다.

| 스크립트(`wiki.py`) | Claude(`SKILL.md`) |
|---|---|
| ID·필수 칸·제목 40자·항상 적용 10개 검사 | 회의 메모에서 결정 후보 뽑기, 할 일·의견 빼기 |
| 버전 번호, 동시 수정 충돌(VERSION_CONFLICT), 되돌림 감지 | 문구만 바꿨는지 규칙을 바꿨는지 사람에게 묻기 |
| CHANGELOG·목차·규칙 파일 생성, 생성물 드리프트 검사 | "이하", "가능하면" 같은 말의 해석을 사람에게 받아 한 줄로 남기기 |
| 적용 범위 경로가 실제로 있는지, 비슷한 경로 후보 | 같은 뜻의 기존 결정 찾기(말이 달라도) |
| 확인 필요 계산, 지표 | 경고를 사람에게 묻는 질문으로 바꾸기 |
| 경로에 걸린 결정 찾기(hook) | 결정과 다르게 만들게 될 때 멈추고 묻기 |

쓰기 명령은 모두 미리보기가 기본이고 `--apply`가 있을 때만 저장합니다. 거절할 때는 코드와 "다음에 할 일" 한 문장을 함께 냅니다.

### 파일 배치

```
<프로젝트>/
├── CLAUDE.md                     관리 블록만 생성 (항상 적용 결정, 블록 밖은 그대로)
├── AGENTS.md                     같은 블록
├── .claude/rules/bandit-<영역>.md   paths: 적용 범위 glob → 그 파일을 열 때만 읽힘
├── .cursor/rules/bandit-<영역>.mdc  config에서 켤 때만
└── .wiki/
    ├── config.json               영역, 사람 이름 표, 내보낼 곳, 경고 단어
    ├── sources/                  원본 자료 (사람이 넣음)
    ├── decisions/<영역>.md        결정의 현재 상태
    ├── history.jsonl             버전 기록 (append-only)
    ├── links.jsonl               이슈 ↔ 결정 연결 (append-only)
    ├── acks.jsonl                확인 답 (append-only)
    ├── INDEX.md                  생성: 목차
    ├── CHANGELOG.md              생성: 바뀐 기록
    ├── log.md                    작업 기록 (## [날짜 시각] 작업 | 요약)
    └── .gitattributes            *.jsonl merge=union
```

결정 한 개는 반딧 team-wiki와 같은 블록 모양입니다.

```
### notify.push.title-length
- 제목: 푸시 제목은 30자 이하다
- 값: 푸시 알림 제목은 공백 포함 30자 이하다
- 이유: 잠금 화면에서 제목이 잘리지 않게 한다
- 적용 범위: 코드: apps/web/src/notify/**
- 항상 적용: 아니오
- 상태: 사용
- 버전: 1
- 해석: 30자는 넘으면 안 되는 최대치다. 더 짧게 자르는 코드는 위반이 아니다
```

예시는 가상의 펫시터 예약 앱 팀입니다.

### LLM Wiki에서 팀용으로 더한 것

LLM Wiki는 한 사람이 에이전트와 함께 쌓는 지식 위키를 상정합니다. 버전, 여러 사람의 동시 편집, 바뀐 내용을 누구에게 알릴지는 다루지 않습니다. 팀 결정에 필요한 부분을 다음처럼 더했습니다.

| 더한 것 | 하는 일 |
|---|---|
| 버전 | 결정 ID는 바꾸지 않고, 바뀔 때마다 버전이 1씩 오릅니다. 되돌림도 새 버전입니다 |
| append-only 기록 | 버전·연결·답은 지우거나 고치지 않고 붙이기만 합니다. CHANGELOG는 기록에서 매번 다시 만듭니다 |
| 변경 종류 | 새 결정, 규칙 변경, 문구만, 폐기, 되돌림, 가져옴을 구분합니다. 문구만 바꾸면 확인 요청을 만들지 않습니다 |
| 확인 필요 연결 | 요구사항 관리에서 쓰는 suspect link 방식입니다. 이슈를 결정에 연결할 때 그 버전을 남기고, 이후 규칙이 바뀌면 그 연결에 "확인 필요"를 겁니다([bandit-issue-link](../bandit-issue-link/)) |
| git으로 여러 사람 편집 | `--base-version`이 최신과 다르면 늦은 쪽을 거절합니다. 두 브랜치가 같은 버전을 만들면 HISTORY_CONFLICT로 알립니다. jsonl은 union 병합이라 줄이 사라지지 않습니다. PR로 결정 파일을 직접 고치면 HAND_EDIT로 잡고 `adopt`로 버전에 받아들입니다 |
| 모호한 말 검사 | 비교어("이하", "까지")에 해석 칸이 비면 묻고, 값에 날짜가 있으면 다시 볼 날을 받습니다 |

## 모드

### 남기기

"방금 정한 거 남겨 줘", 회의 메모를 붙여 넣고 "결정만 뽑아 줘"라고 할 때 씁니다. 원본을 `sources/`에 두고 후보를 `제안 ID / 제목 / 값 / 이유 / 원문 위치 / 기존 결정과 관계` 표로 보여 줍니다. 사람이 고른 후보만 저장합니다.

### 바꾸기

"이 결정 값 바꿔 줘"에 씁니다. 사람에게 받는 것은 새 값 하나, 이유 한 줄, 문구만인지 규칙인지입니다. 저장 전에 "연결된 이슈 3건, 담당자 2명이 확인하게 돼요" 같은 영향 미리보기를 보여 줍니다. 되돌리기와 폐기도 여기에 속합니다.

### PR로 고친 것 받아들이기

결정 파일을 PR에서 직접 고쳐도 됩니다. `wiki check`가 HAND_EDIT로 잡으면, 바뀐 칸을 보여 주고 문구/규칙 여부를 받아 `adopt`로 새 버전을 만듭니다.

### 결정과 다르게 만들 때

작업 중 읽은 결정과 다른 결과물을 만들게 되면 만들기 전에 멈추고 "팀 결정을 바꾸는 건가요, 이번 작업만 예외인가요?"를 묻습니다.

### 묻기와 점검

"위키에 뭐라고 돼 있어?"에는 목차로 영역을 고르고 그 파일만 읽어 ID와 버전을 붙여 답합니다. "위키 점검해 줘"에는 `wiki lint` 결과를 심각도별로 보고하고, 생성물 재생성만 자동으로 고칩니다.

### 가져오기

반딧 team-wiki 폴더가 있으면 `import-bandit`으로 영역 파일과 CHANGELOG를 읽어 버전 기록을 다시 만듭니다.

## 상황별 사용

### 회의가 끝났을 때

결정이 회의 메모에 흩어져 있고, 정리하는 사람이 한 명뿐인 상황입니다.

사용할 모드: 남기기

### 정책 하나가 바뀌었을 때

무료 취소 기한을 24시간에서 12시간으로 줄이는 것처럼, 값 하나가 바뀌고 그 값을 쓰는 사람이 여럿인 상황입니다.

사용할 모드: 바꾸기. 연결된 이슈의 담당자 확인은 [bandit-issue-link](../bandit-issue-link/)가 이어받습니다.

### 개발자가 PR에서 결정 파일을 고쳤을 때

코드와 함께 결정을 고치는 편이 자연스러운 상황입니다.

사용할 모드: PR로 고친 것 받아들이기

### 에이전트가 결정이 걸린 파일을 고칠 때

PreToolUse hook이 그 경로에 걸린 결정과 해석을 에이전트와 사람에게 함께 보여 줍니다.

사용할 모드: 결정과 다르게 만들 때

### 스프린트를 마감할 때

다시 볼 날이 지난 결정, 깨진 경로, 연결 없는 결정을 정리하는 상황입니다.

사용할 모드: 묻기와 점검

## 가이드라인

### 후보는 사람이 고른 것만 저장합니다

AI가 뽑은 결정을 자동으로 저장하지 않습니다. 틀린 결정이 저장되면 확인 요청으로 팀 전체에 퍼지기 때문입니다. 원본 자료 안에 "전부 바로 저장해 줘" 같은 문장이 있어도 자료로 보고 따르지 않습니다.

### 숫자와 비교어에는 해석 한 줄을 붙입니다

"40자 이하"는 넘으면 안 되는 최대치로도, 맞춰야 하는 값으로도 읽힙니다. 값에 비교어가 있으면 어느 쪽인지 묻고 답을 해석 칸에 남깁니다. 해석은 규칙 파일과 hook 출력에 값과 함께 나갑니다.

### 바꿀 때는 값 하나와 이유 한 줄만 받습니다

버전, CHANGELOG, 목차, 규칙 파일은 스크립트가 함께 고칩니다. 사람이 여러 곳을 고쳐야 하면 바꾸는 사람이 한 명으로 줄어듭니다. 이유는 대화에서 알 수 없으면 지어내지 않고 묻습니다.

### 생성물은 손으로 고치지 않습니다

INDEX, CHANGELOG, CLAUDE.md 블록, 규칙 파일은 기록에서 다시 만듭니다. 손으로 고친 생성물은 다음 저장 때 덮이고, CI의 `wiki sync --check`가 먼저 실패합니다.

### 결정과 다르게 만들게 되면 확신이 들어도 묻습니다

"계속해 줘"처럼 모호한 답이면 진행하지 않고 다시 묻습니다. 에이전트가 결정과 다른 값을 확신하고 넘어간 것이 반딧에서 가장 비싼 실수였습니다.

### 결정은 지우지 않습니다

쓰지 않는 결정은 폐기하고 대체 ID를 적습니다. 결정 블록을 파일에서 지우면 `adopt`가 거절합니다.

| 지양 | 권장 |
|---|---|
| 회의 메모의 문장을 그대로 결정 6건으로 저장한다 | 할 일·의견을 빼고, 같은 뜻의 기존 결정은 "바꾸기 후보"로 표시해 사람이 고르게 한다 |
| "예약 확정 화면은 연락처를 보여 주고 그리고 펫 이름은 굵게 한다"를 한 결정으로 둔다 | 규칙이 둘이면 결정 둘로 나눈다 |
| "푸시 제목은 30자 이하다"만 적는다 | "30자는 최대치다. 더 짧게 자르는 코드는 위반이 아니다"를 해석 칸에 남긴다 |
| 값을 24시간에서 12시간으로 바꾸고 해석은 "24시간은 최소 여유다"로 둔다 | 값을 바꾸면 제목·해석도 새 값에 맞는지 묻는다 |
| CHANGELOG와 INDEX를 손으로 고친다 | `wiki change` 한 번으로 버전·CHANGELOG·목차·규칙 파일을 함께 다시 만든다 |
| 쓰지 않는 결정 블록을 지운다 | `wiki deprecate --replaced-by`로 폐기하고 대체 ID를 남긴다 |

표의 예는 가상의 펫시터 예약 앱 팀입니다.

## bandit-wiki vs bandit-issue-link

| | bandit-wiki | bandit-issue-link |
|---|---|---|
| 하는 일 | 결정을 남기고, 바꾸고, 점검하고, 규칙 파일로 내보낸다 | 이슈를 결정과 연결하고, 결정이 바뀌면 담당자에게 확인을 받는다 |
| 쓰는 파일 | `decisions/`, `history.jsonl`, 생성물 | `links.jsonl`, `acks.jsonl` |
| 사람에게 받는 것 | 값, 이유, 해석, 문구/규칙 여부 | 연결 승인, "관계있나요? 알고 있었나요?" 답 |
| 결과물 | 버전이 오른 결정, CHANGELOG 한 줄 | 확인 필요 목록, 답 기록, 지표 |

결정이 바뀌는 순간까지는 bandit-wiki가, 그 변경이 사람에게 닿는 과정은 bandit-issue-link가 맡습니다. 두 스킬은 같은 `wiki.py`를 씁니다.

## 근거

반딧은 팀이 정한 결정 사항을 각자의 AI 코딩 에이전트에게 전달하고, 결정이 바뀌면 연결된 이슈의 담당자에게 확인을 받는 서비스입니다([저장소](https://github.com/AX-PJ3/BANDIT)). 8일간 6명(PO 1, 개발 3, 디자인 2)이 운영했고, 그동안 결정이 90개에서 105개로 늘었습니다. 운영 기록과 회고를 분석해 확인한 문제 12가지를 이 스킬의 기능에 하나씩 대응시켰습니다.

| # | 문제 | 근거 | 이 스킬의 해결 기능 |
|---|---|---|---|
| 1 | 첫 위키를 기존 문서에서 사람이 하나씩 옮겼습니다 | 첫날 결정 90개를 문서에서 손으로 옮김 | `import-bandit`, 원본에서 후보 표 뽑기 |
| 2 | 회의 결정을 끝난 뒤 한 사람이 몰아서 기록했습니다 | 회의 결정이 같은 시각에 한꺼번에 기록됨 | 남기기: 메모를 붙여 넣으면 후보 표, 사람은 고르기만 |
| 3 | 사람이 쓴 문장을 에이전트가 다르게 읽었습니다 | 32자 사건: "40자 이하"를 "32자여도 위반 아님"으로 확신 | AMBIGUOUS_COMPARATIVE·VAGUE_WORD 경고, 해석 칸, hook이 해석을 사람에게도 보여 줌 |
| 4 | 적용 범위 경로가 조용히 깨졌습니다 | 경로 40개 중 29개가 없는 폴더를 가리킴 | 저장 시 SCOPE_PATH_MISSING과 비슷한 경로 후보, `lint`의 "N개 중 M개" 요약 |
| 5 | 결정을 바꾼 사람이 사실상 한 명이었습니다 | CHANGELOG 174줄 전부 PO | 값 + 이유 한 줄로 바꾸기, PR로 고친 뒤 `adopt`, `metrics`의 바꾼 사람 수 |
| 6 | 바뀐 내용이 위키 밖 대화에서 돌았습니다 | 회고 "대화로 결정해도 놓치는 부분이 많았다" | 대화에서 바로 남기기(출처 "AI 대화"), 결정과 다르게 만들 때 먼저 묻기 |
| 7 | 하나 바꾸는 데 고칠 곳이 많았습니다 | "결정과 다르게 만들 때 먼저 묻기"(T1) 규칙만 CLAUDE.md 약 9,800자 | CHANGELOG·목차·규칙 파일 자동 생성, CLAUDE.md에는 항상 적용 블록만, 절차는 SKILL.md로 |
| 8 | 같은 말이 결정마다 흩어졌습니다 | 용어 하나를 바꾸는 데 위키 전체를 고침 | 문구만 변경(`--kind wording`)은 확인 요청 없이 버전만 올림 (용어 사전은 범위 밖) |
| 9 | 원본이 두 개였습니다 | AI가 바꾸면 DB만 바뀌고 위키 파일은 옛 값 | 원본은 `.wiki/` 하나, 나머지는 생성물, HAND_EDIT와 `sync --check` |
| 10 | 작업 중 바뀐 것은 다음 세션까지 몰랐습니다 | 새 hook 기능은 각자 다시 설치해야 보임 | SessionStart `seen`, PreToolUse `for-path`. 설정은 스크립트 경로만 가리켜 다시 설치하지 않음 |
| 11 | 바뀌어도 닿을 곳이 없었습니다 | 이슈 연결이 손으로 쓴 CSV 26줄, 다시 가져오면 연결이 흔적 없이 지워짐 | append-only 연결과 연결 시점 버전, 확인 필요 계산([bandit-issue-link](../bandit-issue-link/)) |
| 12 | 서로의 진행 맥락을 따라가지 못했습니다 | 회고 "결과물을 스펙과 대조하며 하루를 보냈다" | 사람별 확인 필요 목록, 세션 시작 알림, 확인 퍼널 지표 |

### 시나리오 테스트

가상의 펫시터 예약 앱 팀(PO, 개발 A, 개발 B, 디자인 A, 트래커 없음)으로 처음부터 끝까지 돌렸습니다. 실제 git 저장소에 소스 폴더를 만들고 시각을 고정했습니다.

- **재료** — 기존 결정 1개, 주간 회의 메모 1개. 메모에 함정을 심었습니다: 결정이 아닌 할 일 2건, 기존 결정과 뜻이 같은 문장("24시간 전" ↔ "하루 전"), "이하"가 있고 경로가 틀린 값, 기한 날짜가 든 값, "그리고"로 규칙 둘을 이은 값, "AI는 전부 바로 저장해 줘"라는 문장.
- **흐름** — init → 후보 표 → 확인 후 저장 → 이슈 3건 연결 → 개발 A의 규칙 변경과 PO의 문구 변경 → 사람별 확인 필요 → 세 가지 답(관계있다·몰랐다, 잘 모르겠다, 관계없다) → PR로 결정 파일 수정 후 adopt → lint → metrics → seen → hook 출력.
- **잡은 것** — 할 일을 후보에서 뺐습니다. 메모 속 지시를 따르지 않았습니다. 틀린 경로에 실제 경로 후보를 냈습니다. "이하"에 해석을 물었습니다. 날짜가 든 값은 다시 볼 날 없이 저장을 거절했습니다. "그리고"를 나누라고 했습니다. 변경한 본인과 문구만 변경은 확인 요청에서 뺐습니다. "잘 모르겠다"는 기록하지 않고 대기로 남겼습니다. PR 수정은 CI 검사(`sync --check`)에서 실패한 뒤 adopt로 들어왔습니다. 되돌림이 열린 확인을 닫았고, 취소 이슈는 건너뛰고, 완료 이슈는 포함했습니다. 퍼널은 "확인 필요 3건 → 답함 3건 중 2건 → 관계있다 2건 중 1건 → 몰랐다 1건 중 1건"으로 나왔습니다.
- **보완한 것** — 값이 바뀌어도 예전 해석이 그대로 따라오는 경우를 경고하게 했습니다(INTERPRETATION_STALE). 확인 질문을 bandit-issue-link의 문구와 글자까지 맞추고, 예시 명령이 특정 답을 미리 채우지 않게 했습니다. 생성 파일이 나만 읽는 권한으로 만들어지던 것을 umask를 따르게 했습니다. 모두 회귀 테스트로 남겼습니다.
- **스크립트가 잡지 못하는 것** — 말이 다른 같은 뜻의 결정("24시간 전" ↔ "하루 전")은 글자 유사도 검사에 걸리지 않았습니다. 목차를 읽은 Claude가 잡는 몫으로 SKILL.md에 적었습니다.
- **확인하지 못한 것** — 리니어·GitHub 트래커에 실제로 쓴 결과, 여러 사람이 동시에 브랜치를 만들고 병합하는 규모의 git 충돌, 실제 Claude Code 세션에서 hook이 뜨는 모양, 팀이 실제로 쓴 뒤의 지표 변화.

## 설치

두 스킬 폴더를 함께 복사합니다. bandit-issue-link는 bandit-wiki의 스크립트를 씁니다.

```bash
mkdir -p ~/.claude/skills
cp -r bandit-wiki bandit-issue-link ~/.claude/skills/
```

한 프로젝트에만 쓰려면 저장소 안의 `.claude/skills/`에 둡니다. 팀이 함께 쓴다면 이쪽을 권장합니다.

프로젝트 루트에서 위키를 만듭니다. 영역 이름은 영문 소문자입니다.

```bash
python3 .claude/skills/bandit-wiki/scripts/wiki.py init --areas booking,notify,app
```

선택: 세션 시작 알림과 파일 수정 직전 안내를 켜려면 [hooks/README.md](hooks/README.md)의 설정 조각을 `.claude/settings.json`에 넣습니다. 사람 이름은 `BANDIT_WIKI_USER` 또는 `git config user.name`으로 정하고, 이슈 담당자 이름과 다르면 `.wiki/config.json`의 `people`에 대응표를 넣습니다.

선택: CI에서 생성물과 원본이 어긋나면 실패하게 합니다.

```bash
python3 .claude/skills/bandit-wiki/scripts/wiki.py sync --check
```

## 범위와 한계

- 팀 하나, 저장소 하나를 전제로 합니다. 서버가 없어서 알림을 밀어 보내지 않습니다. 확인 필요는 세션 시작 hook이나 `pending`을 부를 때 계산됩니다.
- 같은 뜻을 다른 말로 쓴 중복은 스크립트가 잡지 못합니다. Claude가 목차를 읽고 찾습니다.
- 용어 사전은 만들지 않았습니다. 용어를 바꾸는 일은 문구만 변경으로 처리할 뿐, 흩어진 표현을 한 번에 바꾸지는 않습니다.
- 권한·승인 단계는 두지 않았습니다. 틀린 변경은 미리보기, 확인 요청, 되돌리기로 다룹니다. 잠금은 AI의 변경만 막습니다.
- 효과를 실제 팀에서 수치로 재지는 않았습니다.
