# evidence-based-retro

회고와 팀원 피드백을 기억 대신 이슈·PR·위키·프로토타입 같은 산출물에 근거해 쓰는 스킬입니다.

[SKILL.md](SKILL.md) · [설치](#설치) · 함께 쓰는 스킬: [linear-sync](../linear-sync/), [team-status-report](../team-status-report/)

## 구성

evidence-based-retro는 피드백 한 줄을 "한 행동 → 그 영향 → 다음 행동"으로 쓰기 위해 네 단계를 거칩니다.

1. **근거 모으기** — 트래커, GitHub, 위키, 프로토타입, 대화 기록을 읽습니다. 읽지 못한 출처와 근거가 부족한 사람은 그렇다고 밝힙니다.
2. **행동 단위로 자르기** — 산출물 하나에서 행동 하나를 뽑습니다.
3. **모드에 맞게 쓰기** — 아래 다섯 모드 중 하나로 씁니다.
4. **문장 틀 비교** — 사람별 첫·끝 문장을 나란히 놓고, 겹치면 바꿉니다.

## 모드

### KPT

"회고 KPT로", "회고록 써 줘"에 씁니다. KPT(Keep·Problem·Try 회고) 항목마다 근거를 달고, Problem과 Try는 짝을 맞춥니다.

### 회고 진행 설계

"회고 어떻게 진행하면 좋을까"에 씁니다. 결과물이 아니라 진행 순서, 섹션 구성, 질문을 줍니다.

### 팀원 피드백

"팀원별로 잘한 점, 더 잘할 점"에 씁니다. 분량은 묻고, "각각 3줄" 옵션은 사람당 3줄로 읽습니다. 근거 표기는 줄 수에 세지 않습니다.

### 내 역할 회고

"PO 관점에서 내가 한 역할"에 씁니다. 산출물에서 역할을 추론하고 그 안에서 KPT를 씁니다. 추론이라 본인의 의도와 다를 수 있다고 결과에 적습니다.

### 외부 공개용 재구성

포트폴리오·블로그·발표로 돌릴 때 씁니다. 전달할 메시지를 먼저 정하고, 그 메시지를 받치는 항목만 고릅니다.

## 상황별 사용

### 스프린트나 프로젝트가 끝났을 때

무엇을 계속하고 무엇을 바꿀지 근거와 함께 돌아보는 상황입니다. 나온 Try를 이슈로 만들 때는 확인을 받은 뒤 [linear-sync](../linear-sync/)로 넘깁니다.

사용할 모드: KPT

### 회고 회의를 앞두고 진행 방식을 정할 때

결과물보다 진행 순서와 질문이 필요한 상황입니다.

사용할 모드: 회고 진행 설계

### 팀원에게 피드백을 줘야 할 때

사람마다 잘한 점과 더 잘할 점을 행동 단위로 전하는 상황입니다.

사용할 모드: 팀원 피드백

### 내가 이 프로젝트에서 무슨 역할을 했는지 정리할 때

이슈·PR·위키에 남은 기록에서 내 역할을 읽어 내는 상황입니다.

사용할 모드: 내 역할 회고

### 회고를 포트폴리오나 발표로 옮길 때

사실을 다 늘어놓지 않고 전할 메시지에 맞는 항목만 고르는 상황입니다. 끝낸 작업의 결정을 글로 남기려면 [decision-first-article](../decision-first-article/)을 씁니다.

사용할 모드: 외부 공개용 재구성

## 가이드라인

### 성격이 아니라 관찰한 행동을 씁니다

"꼼꼼하다"는 받는 사람에게 다음에 무엇을 바꿀지 알려 주지 않습니다. 관찰한 행동, 그 행동이 팀이나 결과에 준 영향, 다음에 할 수 있는 행동 하나를 씁니다.

| 지양 | 권장 |
|---|---|
| OO님은 꼼꼼하고 책임감 있는 분이에요. | 화면 시안을 올리면서 데이터에 없는 칸을 따로 표시해 주셨어요. 덕분에 개발 전에 어느 쪽을 맞출지 정할 수 있었어요. (근거: 시안 공유 이슈) |
| 다만 조금 더 적극적이면 좋겠어요. | 리뷰 요청이 늦게 와서 마지막 날 수정이 몰렸어요. 다음엔 절반쯤 됐을 때 한 번 보여 주시면 어떨까요? (근거: PR 리뷰 기록) |

표의 예는 가상의 팀원 OO님에게 줄 "잘한 점 / 더 잘할 점"입니다. 왼쪽은 근거도 다음 행동도 없고, 오른쪽은 줄마다 행동·영향·제안과 근거가 붙습니다.

### 받는 사람 혼자 못 바꾸는 문제는 팀 Try로 옮깁니다

구조 문제는 개인 피드백이 아닙니다. 팀원 피드백만 요청받았으면 결과 끝에 "팀 Try 후보"로 둡니다.

### 사람마다 문장 틀을 바꿉니다

다섯 명에게 같은 틀의 문장이 나가면 받는 사람이 금방 알아챕니다. 첫 문장이든 마지막 문장이든 두 사람 이상이 같은 틀이면 바꿉니다. "너무 구성이 똑같아서 조금 바꿔서"라는 교정에서 나온 규칙입니다.

### 근거가 없으면 지어내지 않습니다

근거가 없는 줄은 "근거가 부족해요"로 둡니다. 읽은 출처에 기록이 없다는 것만으로 "하지 않았다"고 쓰지 않습니다. 읽지 못한 채널에서 했을 수 있기 때문입니다.

### 공개용은 고르되 지어내지 않습니다

사실을 다 나열하면 포트폴리오가 아니라 사실 목록이 됩니다. 팀의 약점 사례는 사용자가 원할 때만 넣습니다. 고르는 것과 지어내는 것은 다릅니다.

## evidence-based-retro vs team-status-report

| | evidence-based-retro | team-status-report |
|---|---|---|
| 하는 일 | 지난 기간을 돌아보고 회고·피드백을 쓴다 | 지금 진행 상황을 읽고 리포트·안건·태스크 지시를 쓴다 |
| 읽는 곳 | 트래커, GitHub, 위키, 프로토타입, 대화 기록 | 트래커, GitHub, 위키 |
| 결과물 | KPT, 팀원별 피드백, 내 역할 회고 | 데일리 리포트, 회의 안건, 태스크 지시, 메트릭 리뷰 |
| 트래커에 쓰는가 | 쓰지 않는다. Try는 확인 후 linear-sync로 넘긴다 | 쓰지 않는다. 이슈 초안만 linear-sync로 넘긴다 |

같은 출처를 읽지만, 지금 할 일은 team-status-report가, 끝난 기간의 회고와 피드백은 evidence-based-retro가 맡습니다.

| 입력 | 이슈 트래커, GitHub(PR·리뷰·커밋), 위키, 프로토타입, 대화 기록 |
| 출력 | KPT, 회고 진행안, 팀원별 피드백, 내 역할 회고, 공개용 회고 |
| 필요한 연결 | 출처마다 연결: 리니어 MCP(외부 도구 연결 방식) 커넥터나 CLI, `gh` CLI, 위키에 맞는 MCP나 CLI. 없으면 붙여 넣은 자료만 씁니다 |
| 외부에 쓰는가 | 쓰지 않습니다. 피드백 전송, 회고 보드 생성, 이슈 등록은 하지 않습니다 |
| 근거 | 팀 회고와 팀원 피드백을 쓰며 받은 교정 |
| 검증 | 가상 2주 프로젝트 시나리오 테스트 |

## 근거

아래 규칙은 팀 회고와 팀원 피드백을 쓰며 결과물을 받은 뒤 고쳐 달라고 한 내용에서 나왔습니다. 측정한 수치는 없습니다.

| 고쳐 달라고 한 것 | 규칙 |
|---|---|
| "구체적인 프로젝트 내용보다는 행동 중심 피드백 원칙 지켜서" | 기술 세부를 줄이고 행동·영향·제안만 남긴다 |
| 두 사람의 피드백이 "너무 구성이 똑같아서 … 조금 바꿔서" | 사람별 첫·끝 문장을 비교하고 틀을 바꾼다 |
| "컴팩트하게 줄여서 각각 3줄로" | 분량 옵션으로 둔다 |
| 역할을 내 말로 다시 쓰고 싶으니 초안 말고 판단 근거를 달라 | 내 역할 회고는 근거를 따로 준다 |
| 포트폴리오로 돌릴 때 "팩트 기반이지만 너무 솔직한 건 그냥 팩트 나열" | 공개용은 메시지를 먼저 정하고 그에 맞는 항목만 고른다 |
| 외부 발표 자료에서 팀의 약점이 드러나면 안 된다 | 공개용에서 약점 사례는 사용자가 원할 때만 넣는다 |

## 검증

가상의 2주 프로젝트로 시나리오 테스트를 했습니다.

- **재료** — 트래커 JSON(이슈 6건), PR 4건과 리뷰 코멘트, 위키 변경 기록. 팀원 A/B/C와 PO인 사용자가 있습니다.
- **요청** — "팀원별로 잘한 점, 더 잘할 점 각각 3줄로, 그리고 PO로서 내 역할 KPT도."
- **통과** — 읽지 못한 출처를 맨 위에 밝혔습니다. 줄마다 행동·영향·제안과 근거 번호를 달았습니다. 성격 평가 없이 썼습니다. 내 역할을 근거와 함께 4개로 묶고 추론이라고 밝혔습니다. Problem과 Try의 짝을 맞췄고, 사람별 첫·끝 문장을 비교했습니다.
- **확인하지 못한 것** — 실제 리니어·GitHub·위키 연결에서 데이터를 읽는 동작, 실제 팀원이 이 문장을 받았을 때의 반응, 다섯 명 이상 팀에서 문장 틀이 계속 갈리는지. 회고 진행 설계와 외부 공개용 재구성 모드는 돌려 보지 않았습니다.

## 설치

```bash
cp -r evidence-based-retro ~/.claude/skills/
```

한 프로젝트에만 쓰려면 저장소 안의 `.claude/skills/evidence-based-retro/`에 둡니다.

근거를 읽으려면 출처마다 연결이 필요합니다. 리니어 MCP 커넥터나 CLI, `gh` CLI, 위키에 맞는 MCP나 CLI입니다. 연결이 없으면 사용자가 붙여 넣은 자료와 대화 기록만으로 쓰고, 그렇다고 밝힙니다.

회고에서 나온 Try를 이슈로 만들 때는 초안을 확인받은 뒤 [linear-sync](../linear-sync/)로 넘깁니다. 팀 현황 리포트와 태스크 지시는 [team-status-report](../team-status-report/)가 맡습니다.

## 범위와 한계

- 글을 쓰는 데까지입니다. 피드백을 팀원에게 보내거나, 회고 보드 페이지를 만들거나, 이슈를 등록하지 않습니다.
- 내 역할 회고는 산출물에서 추론한 것이라 본인의 의도와 다를 수 있습니다.
- 한 사람이 한두 팀에서 쓴 기록에서 나온 규칙입니다. 피드백 문화가 다른 팀에서는 "더 잘할 점"의 수위가 맞지 않을 수 있습니다.
