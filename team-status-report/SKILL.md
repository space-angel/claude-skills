# 팀 현황 리포트

트래커·GitHub·위키를 직접 읽고, 회의에서 바로 쓸 수 있는 현황 문서를 만든다.

## 이 스킬의 전제

**요약이 아니라 "누가 지금 무엇을 챙겨야 하나"를 쓴다.**

결론만 담은 리포트("가설을 확인할 숫자는 아직 없어요" + 핵심 숫자 표)는 사용자가 실제로 거절했다. 대신 요청한 것은 이것이다. "현재 진행 상황이랑 지금 이야기해야 할 것 우선순위와 각 작업 간에 잘 체크해야 하는 상황들, 인원별로."

## 모드

요청 문장을 보고 고른다. 애매하면 무엇을 만들지 한 줄로 묻는다. "안건이랑 태스크 지시"처럼 두 모드를 같이 요청하면 둘 다 만들고, 7단계대로 따로 저장한다.

| 사용자가 한 말 | 모드 | 산출물 |
|---|---|---|
| "데일리 리포트", "오늘 정리", "일일 리포트" | **데일리** | 오늘 바뀐 것 + 인원별 진행 상황 + 막힌 곳 |
| "위클리 회의", "회의 안건", "이번 주 뭐 이야기할지" | **위클리 안건** | 우선순위 순 논의 주제 + 각 주제에서 정할 것 |
| "테스크 지시", "각자 할 일", "누가 뭐 해야 해" | **태스크 지시** | 인원별 태스크 + 왜 + 완료 기준 |
| "메트릭 리뷰", "지표 봐줘", "가설 검증되나" | **메트릭 리뷰** | 지표별 현재 값 + 출처 + 아직 못 잰 것 |
| "발표/마감 전까지 뭐 해야 해", "빠진 이슈 있어?" | **갭 점검** | 남은 작업 + 트래커에 없는 작업 제안 |
| "스프린트 공유", "스프린트 결과 정리", "스프린트 리뷰 자료" | **스프린트 공유** | 목표 대비 결과 + 완료/이월 + 지표 변화 + 다음 목표 + 도움 필요 |

전달 형태는 따로 묻는다. **"슬랙용"이면 개조식으로 짧게**, 문서용이면 풀어서 쓴다. 같은 내용을 두 형태로 달라고 하는 일이 많다.

## 실행 절차

### 1단계 — 세 곳을 다 읽는다

한 곳만 보고 쓰지 않는다. 출처마다 보는 것이 다르다.

| 출처 | 무엇을 본다 |
|---|---|
| 이슈 트래커 | 상태, 담당자, 최근 변경, 설명 안 체크박스, 댓글, 하위 이슈 |
| GitHub | 열린 PR, 최근 머지, 브랜치, 커밋 메시지, PR 리뷰 코멘트 |
| 팀 위키 | 정해진 결정 사항, 최근 바뀐 기준, 변경 기록(CHANGELOG 등) |

"최근"의 기본 범위는 데일리면 직전 영업일 이후, 위클리면 지난 회의 이후(모르면 7일)다. 문서 맨 위에 범위와 기준 시각을 적는다.

연결된 도구(MCP, CLI)가 없는 출처가 있으면 **어느 출처를 못 읽었는지 문서 맨 위에 적는다**. 못 읽은 출처를 읽은 척하지 않는다.

### 2단계 — 출처끼리 대조한다

이 스킬의 가치는 대부분 여기서 나온다.

- **GitHub에는 있는데 트래커에 없는 작업** — PR·브랜치·커밋이 가리키는 이슈가 없거나, 이슈 범위 밖의 일이 섞여 있다. "등록 제안"으로 따로 모은다.
- **트래커 상태가 실제보다 늦은 것** — PR은 머지됐는데 이슈가 진행 중이다. 설명의 체크박스가 비어 있다.
- **위키 결정과 어긋난 작업** — 위키에서 기준이 바뀌었는데 그 기준을 쓰는 이슈·PR이 옛 값으로 진행 중이다. 어느 쪽이 맞는지 단정하지 않는다. "작업을 고친다 / 기준을 다시 본다"를 선택지로 둔 논의 주제로 올린다.
- **이미 합의된 것** — 대화나 댓글에서 끝난 건은 논의 주제에서 뺀다.

대조 결과는 판단이 섞이므로 근거를 같이 쓴다. 제목과 설명만 보고 분류했다면 "제목과 설명으로 읽은 분류예요"라고 밝힌다.

### 3단계 — 사람별로 쓴다

각 사람 아래에 같은 틀을 둔다.

```markdown
### 팀원 A — (맡은 영역)
- 지금 상태: (진행 중 이슈, 열린 PR, 마지막 변경 시점)
- 지금 이야기할 것: (우선순위 순)
- 챙길 점: (다른 사람 작업과 겹치거나 기다리는 지점)
```

담당자가 없는 이슈는 "담당자 없음" 칸에 따로 모은다. 위클리 안건의 논의 주제마다는 "왜 지금 / 정할 것(선택지가 있으면 A/B) / 의견 줄 사람"을 쓴다.

**챙길 점**이 핵심이다. "A의 PR이 머지돼야 B가 DB 연결을 시작할 수 있다"처럼 작업 사이의 의존과 순서를 쓴다.

### 4단계 — 태스크는 왜와 완료 기준을 붙인다

태스크 지시 모드에서 사용자가 덧붙인 요구다. "왜 해야 하는지, 그리고 구체적인 완료 기준도 같이 명시해서. 길어져도 되니까 풀어서."

```markdown
**태스크: (동사로 끝나는 한 줄)**
- 왜: (이게 안 되면 무엇이 막히나, 어떤 결정·지표와 이어지나)
- 다 됐다고 볼 조건:
  - [ ] (확인 가능한 상태. "검토한다"가 아니라 "PR이 머지됐다", "위키 v2로 저장됐다")
- 기다리는 것: (선행 작업, 없으면 생략)
```

- AI가 직접 할 수 있는 일(문서 최신화, 위키 정리, 표 만들기)을 팀원에게 시키지 않는다. 사용자가 "그건 너가 하면 되니까"라며 실제로 뺐다. 이슈 상태 맞추기(머지됐는데 진행 중인 이슈)도 팀원 태스크로 넘기지 않고 이슈 초안에 넣는다.
- 사용자가 범위 밖이라고 한 항목은 지운다. 담당자·상태는 지금 기준으로 고친다.

### 5단계 — 비개발자도 읽게 쓴다

팀에 비개발자가 있으면(모르면 있다고 보고) 개발 용어를 처음 쓸 때 괄호로 푼다. "PR(코드 변경 요청)", "머지(본 코드에 합치기)". 메트릭 리뷰에는 "메트릭 리뷰가 무엇인지"를 두세 문장으로 먼저 설명한다.

### 6단계 — 숫자는 출처와 함께, 못 잰 것은 못 쟀다고

메트릭 리뷰와 데일리에 숫자를 쓸 때 지킨다.

- 숫자마다 어디서 셌는지 쓴다. "기록률 80% (위키 변경 기록 20건 중 16건)".
- 확인하지 않은 인과는 단정하지 않는다. "이 상태 때문에 재작업이 생겼는지는 아직 확인하지 않았어요."
- 데이터가 아직 안 쌓였으면 언제부터 쌓이는지, 무엇이 먼저 끝나야 하는지 쓴다.
- 추정치를 요청받으면 추정이라고 표시하고 근거가 된 사례를 나열한다.

### 7단계 — 저장하고 넘긴다

- 결과는 `.md` 파일로 저장한다. 저장 위치는 사용자에게 묻는다. 말이 없으면 `~/Downloads`를 제안한다. 파일 이름에 날짜와 모드를 넣는다(`2026-10-12-daily.md`). 회의 자료는 만든 날이 아니라 회의 날짜를 쓴다.
- 자료가 둘이면 "두 개 따로 저장"을 기본으로 한다. 하나로 합칠지는 사용자가 정한다.
- 슬랙 공지문을 요청받으면 문서 링크·이슈 링크를 넣은 짧은 버전을 따로 준다.

## 스프린트 공유 모드

스프린트가 끝난 뒤 팀과 이해관계자에게 "목표 대비 무엇이 됐나"를 같은 틀로 알린다. 범위는 스프린트 시작일부터 종료일까지다. 목표는 스프린트 시작 때 적어 둔 문장(이슈 트래커의 사이클·마일스톤 설명, 계획 문서)에서 그대로 가져온다. 찾지 못하면 지어내지 않고 사용자에게 묻는다.

앞 단계 규칙을 그대로 쓴다.

- **근거(6단계)** — 지표마다 출처를 붙이고, 아직 못 잰 지표는 못 쟀다고 쓴다. 지표가 오른 이유를 이번 스프린트 작업 덕분이라고 단정하지 않는다.
- **사람별(3단계)** — 완료·이월 항목에 담당자를 붙이고, 도움이 필요한 것은 누가 누구에게 받아야 하는지로 쓴다.
- **완료 기준(4단계)** — "완료"는 트래커 상태가 아니라 완료 기준을 채웠는지로 판단한다. 머지됐는데 이슈가 열려 있거나, 이슈는 닫혔는데 PR이 열려 있으면 2단계 대조 결과로 따로 적는다.

```markdown
# 스프린트 <번호> 공유 (YYYY-MM-DD ~ YYYY-MM-DD)

> 기준 시각: <…> · 읽은 출처: <트래커/GitHub/위키> · 못 읽은 출처: <없으면 생략>

## 목표 대비 결과
| 스프린트 목표 | 결과 | 근거 |
|---|---|---|
| <시작 때 적은 목표 문장 그대로> | 달성 / 일부 / 미달 | <확인한 상태·숫자와 출처> |

## 완료
- <항목> — 담당 <이름> · 완료 기준: <채운 조건> · <PR·이슈 링크>

## 이월
- <항목> — 담당 <이름> · 이월 이유: <막힌 곳·범위 변경> · 다음 스프린트에서 할 것: <…>

## 지표 변화
| 지표 | 시작 값 | 목표 | 지금 값 | 출처 |
|---|---|---|---|---|
| <지표> | <…> | <…> | <…> 또는 "아직 못 잼(언제부터 잼)" | <…> |

## 정한 것 (결정 기록이 있으면)
- <결정 한 문장> — Approver <이름 또는 역할> · 상태 초안/확정 · <결정 기록 링크>

## 다음 스프린트 목표 (초안)
- <목표 한 문장> — 이번 결과와의 연결: <…>

## 도움이 필요한 것
- <누가> → <누구에게>: <무엇을, 언제까지> (선택지가 있으면 A/B)
```

달성률은 (지금 값 − 시작 값) ÷ (목표 − 시작 값)으로 계산하고, 계산에 쓴 값을 표에 남긴다. 다음 스프린트 목표는 초안이다. 확정은 팀이 한다. 회고(잘된 점·개선할 점)는 이 문서에 섞지 않고 `evidence-based-retro`로 넘긴다.

## 논의 주제를 이슈로 만들 때

위클리 안건과 갭 점검에서 나온 항목은 이슈 초안으로 바꿀 수 있다. **이 스킬은 등록하지 않는다.**

1. 항목마다 이슈 초안을 쓴다. 제목, 왜, 정할 것(선택지가 있으면 선택지), 의견을 달아 줄 사람.
2. 상위 이슈 하나에 하위 이슈로 묶을지, 따로 둘지 표로 보여준다.
3. 사용자가 확인하면 `linear-sync` 스킬로 넘겨 등록한다. 확인 전에는 아무것도 만들지 않는다.

결정이 필요한 질문을 팀원에게 물을 때는 선택지 A/B, 사용자의 의견, 상대에게 구체적으로 묻는 것 하나를 담는다.

## 하지 않는 것

- 결론 한 단락 + 숫자 표로 끝내기
- 출처를 읽지 않고 이전 대화 기억으로 쓰기
- 이슈를 사용자 확인 없이 만들거나 상태를 바꾸기
- 확인하지 않은 원인을 결론처럼 쓰기
- AI가 할 수 있는 정리 작업을 팀원 태스크로 넘기기
