# team-status-report

이슈 트래커, GitHub, 팀 위키를 직접 읽고 회의에서 바로 쓰는 팀 현황 문서를 사람별로 만드는 스킬입니다.

[SKILL.md](SKILL.md) · [설치](#설치) · 함께 쓰는 스킬: [linear-sync](../linear-sync/)

## 구성

team-status-report는 현황 문서를 다섯 단계로 만듭니다.

1. **세 출처 읽기** — 트래커(상태·담당·체크박스·댓글), GitHub(PR·커밋·리뷰), 위키(결정 사항·변경 기록)를 모두 읽습니다. 못 읽은 출처는 문서 맨 위에 밝힙니다.
2. **출처 대조** — 트래커에 없는 GitHub 작업, 실제보다 늦은 이슈 상태, 위키 기준과 어긋난 작업, 이미 합의된 논의 주제를 찾습니다.
3. **문서 쓰기** — 모드에 맞는 문서를 사람별로 씁니다.
4. **숫자에 출처 붙이기** — 숫자마다 어디서 셌는지 쓰고, 확인하지 않은 인과는 단정하지 않습니다.
5. **저장** — `.md`로 저장합니다. 요청하면 슬랙 공지용 짧은 버전을 따로 줍니다.

## 모드

### 데일리

"데일리 리포트", "오늘 정리"처럼 하루 현황을 볼 때 씁니다. 오늘 바뀐 것, 인원별 진행 상황, 막힌 곳을 씁니다.

### 위클리 안건

"위클리 회의", "이번 주 뭐 이야기할지"처럼 회의를 준비할 때 씁니다. 논의 주제를 우선순위 순으로 놓고, 주제마다 "왜 지금 / 정할 것 / 의견 줄 사람"을 씁니다.

### 태스크 지시

"각자 할 일", "누가 뭐 해야 해"처럼 인원별 지시가 필요할 때 씁니다. 태스크마다 왜 하는지와 체크박스로 된 완료 조건을 붙입니다.

### 메트릭 리뷰

"지표 봐줘", "가설 검증되나"처럼 숫자를 볼 때 씁니다. 지표별 현재 값과 출처, 아직 못 잰 것을 씁니다. 메트릭 리뷰가 무엇인지 두세 문장으로 먼저 설명합니다.

### 갭 점검

"발표 전까지 뭐 해야 해", "빠진 이슈 있어?"처럼 마감 전에 남은 일을 볼 때 씁니다. 남은 작업과 트래커에 없는 작업의 등록 제안을 모읍니다.

### 스프린트 공유

"스프린트 결과 정리"처럼 스프린트가 끝난 뒤 팀과 이해관계자에게 알릴 때 씁니다. 목표 대비 결과, 완료와 이월(담당자별), 지표 변화(출처 포함), 다음 스프린트 목표 초안, 도움이 필요한 것을 씁니다. 완료는 트래커 상태가 아니라 완료 기준을 채웠는지로 판단합니다. 회고는 섞지 않습니다.

## 상황별 사용

### 하루 업무를 시작할 때

어제 이후 무엇이 바뀌었고 누가 어디서 막혀 있는지 보는 상황입니다.

사용할 모드: 데일리

### 위클리 회의를 앞두고 있을 때

회의에서 이야기할 주제를 우선순위대로 정리하는 상황입니다. 안건에서 나온 할 일은 이슈 초안으로 만들고, 등록은 [linear-sync](../linear-sync/)에 넘깁니다.

사용할 모드: 위클리 안건

### 회의가 끝나고 일을 나눌 때

팀원마다 왜 해야 하는지와 다 됐다고 볼 조건을 붙여 할 일을 전하는 상황입니다.

사용할 모드: 태스크 지시

### 가설이 맞는지 숫자로 봐야 할 때

지표마다 현재 값과 출처, 아직 못 잰 것을 확인하는 상황입니다.

사용할 모드: 메트릭 리뷰

### 발표나 마감 전에 빠진 일을 찾을 때

GitHub에는 있는데 트래커에 없는 작업까지 모아 남은 일을 점검하는 상황입니다. 등록 제안은 확인을 받은 뒤 [linear-sync](../linear-sync/)가 등록합니다.

사용할 모드: 갭 점검

### 스프린트가 끝났을 때

시작 때 세운 목표가 얼마나 이뤄졌고 무엇이 다음 스프린트로 넘어가는지 알리는 상황입니다. 잘된 점·개선할 점은 [evidence-based-retro](../evidence-based-retro/)로 따로 정리합니다.

사용할 모드: 스프린트 공유

## 가이드라인

### 요약이 아니라 사람별 현황을 씁니다

사람마다 "지금 상태 / 지금 이야기할 것 / 챙길 점" 세 칸을 둡니다. 결론 한 단락과 숫자 표로 된 리포트는 회의에서 쓸 데가 없어 거절됐습니다. 핵심은 챙길 점입니다. 작업 사이의 의존과 순서를 씁니다.

| 지양 | 권장 |
|---|---|
| "이번 주는 전반적으로 순조롭다"와 핵심 숫자 표로 끝낸다 | 팀원 A — 결제: 결제 PR 리뷰 대기, 이슈는 아직 "진행 중"이라고 쓴다 |
| 논의할 것을 한데 섞는다 | "환불 정책을 위키 기준대로 갈지"처럼 사람별로 이야기할 것을 쓴다 |
| 작업을 따로따로 나열한다 | "A의 PR이 머지돼야 B가 DB 연결을 시작할 수 있다"처럼 기다리는 지점을 쓴다 |
| "환불 문구 검토"처럼 태스크 이름만 준다 | 왜(문구가 정해져야 B가 화면을 마무리한다)와 완료 조건(위키에 문구 v2가 저장됐다)을 붙인다 |

표의 예는 가상의 예약 앱 팀에 "내일 위클리 회의 안건 정리해 줘"라고 한 경우입니다.

### 태스크에는 왜와 완료 조건을 붙입니다

완료 조건은 확인할 수 있는 상태로 씁니다. "검토한다"가 아니라 "PR이 머지됐다", "위키 v2로 저장됐다"입니다.

### AI가 할 수 있는 정리는 팀원에게 넘기지 않습니다

문서 최신화, 위키 정리, 표 만들기는 태스크에서 뺍니다. 이슈 상태 맞추기도 팀원 태스크가 아니라 이슈 초안에 넣습니다. "네가 하면 되니까"라는 교정에서 나온 규칙입니다.

### 위키와 어긋난 작업은 선택지로 올립니다

어느 쪽이 맞는지 단정하지 않습니다. "작업을 고친다 / 기준을 다시 본다"를 선택지로 둔 논의 주제로 올립니다.

### 비개발자도 읽게 씁니다

개발 용어는 처음 쓸 때 괄호로 풉니다. 팀에 비개발자가 있는지 모르면 있다고 봅니다.

### 이슈는 초안까지만 만듭니다

논의 주제를 하위 이슈로 달 때도 등록 전에 초안을 보여 줍니다. 확인을 받으면 등록은 linear-sync가 합니다.

## team-status-report vs linear-sync

| | team-status-report | linear-sync |
|---|---|---|
| 하는 일 | 트래커·GitHub·위키를 읽고 리포트를 쓴다 | 이슈를 읽고 고치고 만든다 |
| 리니어에 쓰는가 | 쓰지 않는다. 이슈 초안만 넘긴다 | 승인 후 쓴다 |
| 결과물 | 데일리 리포트, 회의 안건, 태스크 지시, 메트릭 리뷰, 스프린트 공유 | 바뀐 이슈, 해결 코멘트 |

회의 안건과 갭 점검에서 나온 할 일은 team-status-report가 초안으로 만들고, linear-sync가 등록합니다.

## 명세

| 항목 | 내용 |
|---|---|
| 요청 예시 | "오늘 위클리 회의 진행하기로 했는데 각자 인원들한테 구체적인 태스크 지시를 해 줘야 할 것 같아" · "지금 팀 위키랑 리니어 보고 월요일 현재 기준으로 메트릭 리뷰 진행하자" · "내일까지 MVP 발표 전 시연을 위한 작업… 리니어, 깃허브 전부 확인하고 이슈로 아직 등록 못 한 건 꼼꼼하게 제안해 줘" · "데일리 리포트 개조식으로" · "이번 스프린트 결과 공유 문서 써 줘" |
| 입력 | 이슈 트래커(상태, 담당자, 체크박스, 댓글, 하위 이슈), GitHub(PR, 커밋, 리뷰 코멘트), 팀 위키(결정 사항, 변경 기록) |
| 출력 | `.md` 현황 문서, 요청 시 슬랙용 짧은 버전, 이슈 초안 |
| 필요한 연결 | 이슈 트래커: Linear MCP(외부 도구 연결 방식) 커넥터나 CLI · GitHub: `gh` CLI · 위키: 레포 안 마크다운이면 준비 없음 |
| 외부에 쓰는가 | 쓰지 않습니다. 이슈 생성·수정, 위키 수정, 슬랙 전송을 하지 않습니다 |
| 근거 | PO로 팀을 운영하며 결과물을 고쳐 달라고 한 교정 |
| 검증 | 가상 팀 시나리오 테스트 |

## 근거

아래 규칙은 PO로 팀을 운영하며 현황 문서를 받은 뒤 고쳐 달라고 한 내용에서 나왔습니다.

| 규칙 | 근거 |
|---|---|
| 사람별 틀(지금 상태 / 이야기할 것 / 챙길 점) | 결론 위주 리포트를 거절하고 "현재 진행 상황이랑 지금 이야기해야 할 것 우선순위와 각 작업 간에 잘 체크해야 하는 상황들 인원별로" |
| 태스크마다 왜 + 체크박스 완료 조건 | "왜 해야 하는지 그리고 구체적인 완료 기준도 같이 명시해서, 길어져도 되니까 풀어서" |
| 전달 형태를 따로 묻는다 | 슬랙에 올릴 버전은 "개조식으로 컴팩트하게" |
| 용어를 처음 쓸 때 괄호로 푼다 | 비개발자 팀원도 이해하게, 메트릭 리뷰가 뭔지부터 |
| 저장 위치를 묻고 기본값으로 `~/Downloads` 제안 | 결과를 `.md`로 다운로드 폴더에 저장 |
| 이슈는 초안만, 등록은 확인 후 linear-sync로 | 논의 사항을 하위 이슈로 달되 "등록하기 전에 어떻게 등록할지 나한테 공유 후에" |
| AI가 할 수 있는 정리는 태스크로 넘기지 않는다 | 문서 최신화를 팀원에게 시키지 말라, "네가 하면 되니까" |
| 출처 대조 단계에서 "등록 제안"으로 모은다 | GitHub에는 있는데 이슈로 안 잡힌 작업 제안 |

스프린트 공유 규칙은 2025년 5월에 만든 MAKER 프레임워크의 커뮤니케이션 모듈에서 가져왔습니다. 원본의 다섯 섹션(계획·진행·결과·회고·다음 전망) 중 종료 시점에 쓰는 결과와 다음 전망만 남기고, 회고는 evidence-based-retro로 넘겼습니다.

## 검증

함정을 심은 가상 팀으로 시나리오 테스트를 했습니다. 실제 서비스는 건드리지 않았습니다.

- **재료** — 가상 팀원 4명(그중 1명 비개발자), 이슈 10건, PR 5건, 위키 결정 3건. PR에는 이슈 없이 머지된 것 1건, 위키의 리텐션 기준 D14와 달리 D7로 집계하는 것 1건을 넣었습니다.
- **요청** — "내일 위클리 회의 안건이랑 인원별 태스크 지시 정리해 줘."
- **통과** — 이슈 없는 PR, 머지됐는데 진행 중인 이슈, 위키와 어긋난 PR, 이미 합의된 건(안건에서 뺌)을 모두 찾았습니다. 사람별 세 칸 틀, 태스크별 왜·완료 조건 체크박스, 용어 풀이를 지켰습니다. 이슈는 초안만 쓰고 등록하지 않았습니다.
- **확인하지 못한 것** — 실제 Linear MCP·`gh` CLI·위키 연결에서 읽는 동작, 이슈·PR이 수십 건을 넘을 때의 길이와 정확도, PR 코드까지 열어 봐야 하는 대조(테스트에서는 제목과 메모만 봤습니다), linear-sync로 넘기는 부분, 실제 팀원의 반응. 테스트는 한 번뿐이라 결과가 매번 같은지도 확인하지 못했습니다.

## 설치

```bash
cp -r team-status-report ~/.claude/skills/
```

한 프로젝트에만 쓰려면 레포 안의 `.claude/skills/team-status-report/`에 둡니다. "위클리 회의 태스크 지시해 줘", "데일리 리포트 개조식으로"처럼 한국어로 부탁하는 요청에 걸리도록 `SKILL.md`도 한국어로 썼습니다.

읽을 출처마다 연결이 필요합니다. 이 스킬은 연결을 만들지 않습니다. 연결이 없는 출처는 건너뛰고, 건너뛰었다고 적습니다.

- 이슈 트래커: Linear MCP 커넥터나 CLI
- GitHub: `gh` CLI
- 팀 위키: 레포 안의 마크다운이면 추가 준비가 없습니다. 별도 서비스면 그 MCP나 CLI가 필요합니다.

## 범위와 한계

- 현황을 읽고 정리하는 것까지만 합니다. 이슈 생성·수정, 위키 수정, 슬랙 전송은 각자 맡은 스킬이나 사용자가 합니다.
- 회고와 팀원 피드백은 [evidence-based-retro](../evidence-based-retro/)가 맡습니다.
- 효과를 수치로 재지는 않았습니다.
- 규칙은 한 사람이 한 팀을 운영하며 나온 것입니다. 팀 규모나 트래커가 다르면 틀이 안 맞을 수 있습니다. 그럴 때는 사람별 틀의 세 칸만 지키고 나머지는 고쳐 씁니다.
